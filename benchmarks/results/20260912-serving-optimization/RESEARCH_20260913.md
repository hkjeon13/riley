# Riley serving: 측정 종료와 구조 중심 개선 후보 조사

조사일: 2026-09-13. 범위: arXiv 논문, 프로젝트 공식 문서·저장소. 이번 작업은 조사까지이며 아래 제안은 구현하지 않았다. 웹 문서는 rolling 문서이므로 실제 도입 시 release/commit과 선택된 kernel을 고정해야 한다.

**연구 범위 수정:** 사용자의 후속 지시에 따라 4090 지원 여부를 기술 선정 기준으로 사용하지 않는다. 아래 기존 4090 기준 우선순위와 headroom은 현재 실험 환경의 분석으로 한정한다. 전체 연구는 hardware-independent runtime, Hopper/Blackwell 실행층, 다중 GPU/노드 serving을 함께 다룬다. 후속 격리 호환성 검사는 별도 기록이며 새 serving 성능 측정은 아니다.

## 판단

### 하드웨어 확장 및 테스트 정책 — 사용자 후속 지시 반영

현재 테스트 GPU가 RTX 4090이라는 이유로 multi-GPU, Hopper, Blackwell에 필요한 기능의 설계·구현을 보류하지 않는다. 해당 하드웨어에서만 실행 가능한 테스트는 명시적으로 skip하고 나머지 작업을 진행한다. 이 정책은 하드웨어 부재에 대한 예외이며, 실제 실행한 테스트의 실패를 무시하는 예외는 아니다.

| 검증 범위 | 현재 처리 | 이후 필요한 증거 |
|---|---|---|
| 공통 Rust 로직, ABI, execution/KV ownership, CPU 상태 전이 | 현재 환경에서 실행 | 지원 backend 모두 같은 계약 유지 |
| 4090 지원 CUDA 경로 및 serving 회귀 | 현재 GPU에서 실행 | 기존 정확성·latency·throughput 기준 |
| Hopper 전용 instruction/pipeline | SM90 장비가 없으면 runtime 테스트 skip; 가능한 build 검증 수행 | 실제 Hopper 실행, 수치·수명 검사, 동일 GPU의 경쟁 엔진 비교 |
| Blackwell 전용 instruction/pipeline | 필요한 capability를 가진 장비가 없으면 runtime 테스트 skip; 가능한 build 검증 수행 | 해당 Blackwell GPU에서 같은 검증 및 serving 비교 |
| multi-GPU collectives, peer access, KV transfer, compute/communication overlap | GPU 수·topology 요구가 충족되지 않으면 장비 의존 테스트 skip; 계획·상태 전이 검증은 실행 | 실제 GPU 수·NVLink/PCIe/network topology를 명시한 correctness·failure·성능 검증 |

테스트는 필요한 capability와 관측한 capability, skip 이유를 기록해야 한다. architecture family 이름만으로 instruction·통신 지원을 가정하지 않는다. compile-only, mock 기반 테스트, 실제 GPU 실행, serving benchmark를 구별한다. build toolchain이 없어 컴파일도 못 했으면 그 사실을 별도로 기록한다.

지원하지 않는 feature는 dispatch 단계에서 명시적으로 거부하거나 검증된 fallback을 선택한다. fallback이 실행된 테스트를 전용 backend 통과로 집계하지 않는다. CI에서 skip은 pass와 별도 상태로 집계하고, 장비가 제공되는 실행에서는 필요한 테스트가 skip으로 빠져나가지 않도록 조건을 검사한다. 구현 완료와 해당 장비에서의 검증 완료를 따로 보고하며, skip된 성능 테스트로 최종 serving 목표 달성을 주장하지 않는다.

프레임워크 이름 외에 HBM·CUDA 연산·GPU compiler 키워드로 확장한 [메모리 및 연산 연구](HBM_CUDA_RESEARCH_20260913.md)를 별도로 정리했다. Welder/MCFuser의 연산 간 데이터 재사용, Stream-K/LeanAttention의 작업 분할, ThunderKittens/ParallelKittens의 pipeline 표현을 추가 후보로 평가한다.

전체 설계의 핵심 후보는 **비동기 실행 runtime, hardware별 attention/persistent backend, prefill/decode 분리 및 KV 이동 계층**이다. 연구 우선순위는 구조적 효과와 적용 workload로 정하고, 4090에서 바로 검증할 수 있는 순서는 별도로 정한다. 기존 kernel의 load/warp/layout 조정을 계속하는 방식에서 벗어나, 엔진이 일을 배치하고 실행하는 단위를 바꾸는 방향이다. 다만 어떤 논문의 배수도 Riley의 예상 개선율로 사용하지 않는다.

기존 trace의 시간 비중을 적용하면 **attention 교체만으로 목표 전체를 해결할 계획은 충분하지 않다.** 아래 headroom 계산에 따라 attention backend와 비동기 실행을 중기 설계의 두 축으로 삼고, persistent execution은 별도 타당성 실험으로 둔다.

Riley는 이미 continuous batching, paged KV, mixed prefill/decode, CUDA Graph, GPU greedy sampling을 갖고 있다. 이 기능들을 단순히 추가하자는 제안은 새로운 방향이 아니다. 차이는 **검증된 다양한 shape의 backend를 활용하는가, 다음 iteration을 CPU 결과 처리와 겹치는가, 연산 사이의 GPU 경계를 줄이는가**에 있다.

## 현재 측정에서 확정된 것

[V56 serving 결과](V56_SERVING_RESULTS.md)의 Round62는 SmolLM2-135M BF16 / 단일 RTX 4090 / 같은 workload에서 V51·V52·V56·vLLM을 비교했다. 12,288 요청 실패 0, Riley reference 대조 9,216건 일치. 이는 Riley reference와의 일치이며 vLLM과 출력이 모두 동일하다는 뜻은 아니다.

| workload | V56 throughput 대 vLLM | V56 TPOT 대 vLLM |
|---|---:|---:|
| C16 fixed | +20.22% | +6.46% 느림 |
| C16 natural | +0.69% | +5.46% 느림 |
| C32 fixed | +9.82% | +27.03% 느림 |
| C32 natural | −12.69% | +25.04% 느림 |

C32 natural P99도 vLLM보다 16.34% 높다. V56은 이전 V52 대비 throughput −1.80%~+1.44%로 혼재한다. 두 번의 역순 비교는 후보 선별 자료이며 긴 안정성·통계적 우위를 입증하지 않는다. **최종 성능 목표 미달이며 V56을 일반 baseline으로 승격하지 않는다.** V51 일반 reference와 V52 비교 기준을 보존한다.

V54/V55는 mixed kernel 이득이 전체 decode 손실 또는 거의 중립으로 이어졌고 되돌렸다. V56은 decode graph의 kernel 수를 336→276으로 줄였지만 serving 향상은 작았다. 이 이력은 kernel 개선 자체가 무의미하다는 뜻이 아니라, 현재 방식의 성능 예측력이 부족하다는 근거다.

마지막 V57 primitive와 V56 working-set 측정도 완료했다. [마무리 기록](MEASUREMENT_CLOSEOUT_V57.md)에 원자료·판정이 있다. V57은 application에 통합하지 않았다. Blender는 종료 상태를 유지한다.

## 프레임워크에서 가져올 설계

### 하드웨어 범위를 넓힌 주요 연구 축

| 연구 축 | 바꾸는 실행 구조 | 필요한 조건 | Riley의 설계 접점 |
|---|---|---|---|
| FA3 / FA4 | 비동기 data movement·MMA·softmax pipeline | 각각 Hopper / Blackwell 중심 | attention backend와 plan을 runtime에서 분리 |
| MPK / megakernel | 연산 간 경계를 넘어 GPU 내부 task 실행 | 구현별 지원 GPU·SM 자원 조건 | 실행 plan, device task graph, completion 계약 |
| PD disaggregation / Dynamo·NIXL | prefill·decode worker를 분리하고 KV 이동 | 복수 GPU, topology에 맞는 전송 수단 | KV export/import, request handoff, routing, admission |
| DeepEP / expert parallelism | MoE token dispatch·combine과 통신 중첩 | MoE 모델·다중 GPU/노드 | 모델 실행 분할, 통신 backend, expert scheduler |
| Speculative/MTP | 한 target 검증으로 여러 token 진행 | draft 또는 MTP 지원 모델과 수용률 | verifier, KV commit/rollback, variable token step |

이 표의 항목은 서로 대체재만은 아니다. 분리 serving 위에 hardware별 attention, 비동기 scheduler, speculative decoding을 조합할 수 있다. 다만 각 효과를 더해서 예상 배수를 만들지는 않는다. MoE 방식은 현재 dense SmolLM2에 적용할 기능이 아니라 엔진의 모델 범위를 확장할 경우의 연구 축이다.

**FA3/FA4:** FA3는 Hopper의 TMA와 비동기 Tensor Core 실행을 활용해 data movement와 계산을 겹친다. FA4는 Blackwell에서 matmul 처리량에 비해 느리게 증가하는 shared-memory·exponential 처리 성능을 고려해 pipeline과 softmax를 함께 재설계한다. Riley가 참고할 것은 특정 warp 숫자가 아니라 backend별 pipeline 설계와 수치 계약이다. backward 최적화나 attention TFLOPs를 serving throughput 증거로 사용하지 않는다. [FA3](https://arxiv.org/abs/2407.08608), [FA4, 2026](https://arxiv.org/abs/2603.05451).

**분리 serving:** Dynamo는 prefill과 decode를 독립 worker로 운영하고 NIXL로 KV를 전달하는 구성을 제공한다. 연구 질문은 단순히 worker를 나누는가가 아니라, prefill burst가 decode tail latency에 주는 영향을 줄이면서 KV 이동 비용과 pool 불균형을 감당할 수 있는가다. Riley에는 KV serialization/layout 계약, 전송 완료 증명, request handoff 및 실패 시 처리, KV 위치를 고려한 routing이 필요하다. [Dynamo 분리 serving](https://docs.dynamo.nvidia.com/dynamo/dev/kubernetes/disaggregated-serving/overview), [NIXL](https://github.com/ai-dynamo/nixl).

**MoE 통신:** DeepEP는 expert parallelism의 dispatch/combine을 위한 통신 라이브러리다. 큰 MoE serving에서는 kernel 하나의 속도보다 통신과 expert 계산의 중첩이 핵심 후보가 된다. 실제 검증에서는 GPU 수뿐 아니라 NVLink/RDMA topology, expert placement, routing 불균형을 동일하게 고정해야 한다. [DeepEP 공식 저장소](https://github.com/deepseek-ai/DeepEP).

### 검증 장비와 최종 비교 조건

4090은 현재의 회귀·프로토타입 장비다. Hopper/Blackwell 단일 GPU 및 다중 GPU 구성은 별도의 검증 대상으로 기록한다. 현재 없다는 이유로 연구에서 제외하거나, 반대로 원격 장비에서 실험했다고 주장하지 않는다. 새 GPU를 확보했을 때는 **그 GPU에서 Riley와 vLLM/TRT-LLM/SGLang을 같은 모델·precision·workload로 비교**한다. GPU 교체 자체의 이득을 엔진 개선율에 포함하지 않는다.

분리 serving은 총 GPU 수와 topology를 맞춘 aggregated baseline과 비교하고, throughput뿐 아니라 SLO goodput·P99·KV transfer bytes·worker utilization을 평가한다. 저정밀·speculative·MoE 조건도 별도 축으로 명시한다. 이는 기존 목표의 동일 조건 비교를 유지하면서 연구 범위를 넓히는 방법이다.

### 분리 serving을 고정 전제로 삼지 않는 설계

DistServe는 prefill/decode 간 간섭을 줄이는 것뿐 아니라 단계별 자원 배분과 parallelism을 다르게 선택하는 데 초점을 둔다. 따라서 두 서버를 띄우는 것만으로 논문의 설계를 재현한 것이 아니다. [DistServe, OSDI 2024](https://arxiv.org/abs/2401.09670).

TaiChi는 TTFT·TPOT SLO에 따라 aggregation과 disaggregation의 장점이 달라진다고 분석하고 두 구성을 통합하는 방식을 제안한다. Riley의 설계도 aggregated·split·hybrid를 비교 가능하게 유지하는 편이 타당하다. 이는 해당 논문에서 얻은 설계 방향이며 모든 workload에서 hybrid가 우월하다는 실측 결론은 아니다. [TaiChi, 2025](https://arxiv.org/abs/2508.01989).

Mooncake는 KV를 GPU worker 내부 자원으로만 취급하지 않고 CPU DRAM·SSD까지 포함한 cache 계층과 scheduling을 연결한다. 반복 prefix를 많이 쓰는 장문·multi-turn workload에서 검토할 만하다. 논문은 과부하 시 early rejection도 다루므로, 성공한 요청의 latency만 비교하면 같은 serving 품질을 비교하지 못할 수 있다. [Mooncake 논문, 2025 개정](https://arxiv.org/abs/2407.00079). 공식 구현은 SGLang·vLLM·TensorRT-LLM의 KV transfer 및 cache 계층과 연결되는 사례를 제공한다. [Mooncake 구현](https://github.com/kvcache-ai/Mooncake).

다음은 문헌에서 도출한 **Riley 설계 제안**이며 아직 구현하지 않았다.

| 영역 단위 batch | 함께 설계할 변경 | 성공을 판단할 증거 |
|---|---|---|
| KV 이동 및 소유권 | model/revision/dtype/layout 식별자, page export/import, 비동기 transfer 완료, 실패·cancel 시 회수 | 전달 후 full-model 결과 대조, 진행 중인 page 재사용 없음, 비용을 포함한 serving 결과 |
| Cache 및 routing | prefix identity, local/remote 조회, transfer 대 재계산 비용 선택, evict/backpressure | cold/warm/mixed hit workload 각각의 TTFT·tail·전송량·실패율 |
| 배치 및 placement | 단계별 parallelism, prefill/decode pool 비율, mixed fallback, SLO 기반 admission | 같은 총 GPU·topology·arrival stream에서 aggregated/split/hybrid goodput 비교 |

KV identity에는 token prefix 외에 positional encoding, adapter, cache precision 등 결과에 영향을 주는 조건을 포함해야 한다. 전송 완료와 destination에서 사용할 준비가 됐다는 사실도 별도 상태로 관리해야 한다. 네트워크 복사 완료만으로 layout 변환·연산 의존성이 모두 끝났다고 가정하지 않는다.

전송과 재계산 선택의 출발점은 `KV bytes / 실효 대역폭 + 고정 전송 지연 + layout 처리 비용`과 destination의 예상 재계산 시간을 비교하는 것이다. 전체 K/V를 저장하는 dense GQA 모델의 논리 KV 크기는 `2 × layers × tokens × KV heads × head_dim × dtype_bytes`로 계산하되, sharding·replication·alignment와 MLA 같은 다른 cache 형식은 별도로 반영한다. 이 식은 측정 대신 사용할 성능 예측값이 아니라 전송량 산정과 실험 설계에 쓰는 근사다.

최종 goodput 비교에는 **도착한 전체 요청 수, accepted/rejected/failed 수, 두 SLO를 함께 만족한 요청 수**를 기록한다. 한 엔진이 요청을 더 많이 거절해 얻은 latency 개선을 일반 성능 승리로 취급하지 않는다. 기본 비교의 admission/rejection 조건을 맞추고, 과부하 정책 비교는 별도 결과로 보고한다.

| 대상 | 확인한 설계 | Riley에 유효한 차이 | 주의점 |
|---|---|---|---|
| vLLM V1 | batch/backend에 따라 full·piecewise graph 실행을 선택 | 하나의 graph 전략을 고정하기보다 backend별 shape dispatch·padding 비용까지 함께 설계 | 현재 Riley도 graph를 사용하므로 graph 도입 자체의 이득을 주장할 수 없음 |
| TensorRT-LLM | CPU 후처리와 다음 GPU step 중첩; context FMHA·decode masked MHA/XQA 선택 | 실행 파이프라인과 attention algorithm 선택을 독립적인 설계 축으로 취급 | XQA는 model configuration 제약이 있음. SmolLM2와 SM89 조합은 실제 선택 여부 확인 필요 |
| SGLang | 한 batch 앞선 scheduling, future token/event 처리; RadixAttention | CPU scheduler 비용을 GPU 시간에 숨기고 공유 prefix 계산을 재사용 | overlap의 EOS/cancel 수명 관리 필요. prefix 재사용이 없는 workload에는 cache 이득이 제한됨 |
| FlashInfer | paged/ragged attention, 다양한 backend와 mixed attention | Rust 제어 계층을 유지하고 attention 실행층의 범용성과 튜닝 자산을 활용 | SM89 지원은 모든 API 지원을 뜻하지 않음. Rust용 안정 C ABI가 있다고 가정하지 않음 |

근거: [vLLM CUDA Graph 설계](https://docs.vllm.ai/en/latest/design/cuda_graphs/), [TensorRT-LLM overlap scheduler](https://nvidia.github.io/TensorRT-LLM/features/overlap-scheduler.html), [TensorRT-LLM attention](https://nvidia.github.io/TensorRT-LLM/features/attention.html), [SGLang scheduler](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4/), [RadixAttention](https://www.lmsys.org/blog/2024-01-17-sglang/), [FlashInfer 공식 저장소](https://github.com/flashinfer-ai/flashinfer).

아직 동일 조건의 TensorRT-LLM/SGLang 측정은 없다. 위 표는 설계 비교이며 성능 순위가 아니다. 최신 웹 설계와 현재 설치된 vLLM 0.27.1의 실제 경로도 구별해야 한다.

## 우선 후보와 적용 범위

### 1. FlashInfer 기반 attention 실행층과 POD-Attention

FlashInfer는 다양한 sequence 길이·KV 구조에 맞춘 attention 실행을 제공한다. POD-Attention은 compute 중심 prefill과 bandwidth 중심 decode를 같은 SM에서 함께 실행하도록 자원을 배분한다. 단순히 두 단계를 같은 요청 batch에 넣는 것보다 깊은 수준의 중첩이다. [FlashInfer 논문, 2025](https://arxiv.org/abs/2501.01005), [POD-Attention 논문, ASPLOS 2025](https://arxiv.org/abs/2410.18038), [공식 POD API](https://docs.flashinfer.ai/api/pod.html).

**추천 이유:** Riley의 mixed attention과 decode attention을 따로 고치다 상쇄되는 문제를 실행 backend 단위로 다룰 수 있다. 단일 GPU에서도 검토할 가치가 있다. 현재 batch 구성과 POD의 자원 배분 방식이 같다고 가정하지 않는다.

다음 하나의 backend batch로 묶을 범위는 (1) Rust→C++/CUDA adapter와 stream·buffer 소유 계약, (2) 기존 paged KV의 무복사 연결 또는 명시적 변환 비용 계측, (3) plan/workspace 재사용 및 graph capture 호환성, (4) pure decode와 mixed/POD의 shape dispatch다. C ABI wrapper는 새로 설계해야 하는 통합 작업이다.

SM89에서 사용할 attention backend, BF16, head dimension 64, Q:KV head 비율, page size, causal append가 모두 지원되는지 먼저 확인한다. FlashInfer의 최신 BF16 GEMM 기능 전체까지 4090에서 된다고 확장 해석하지 않는다. 공식 저장소도 기능별 지원 차이를 명시한다. PDL API는 SM90 이상 제약이 있어 현재 목표에서 제외한다. [지원 범위](https://github.com/flashinfer-ai/flashinfer), [attention API](https://docs.flashinfer.ai/api/attention.html).

### 2. 한 iteration 앞서는 비동기 scheduler와 GPU 상태 관리

SGLang은 다음 batch 준비를 GPU 실행과 겹치고 future token으로 의존성을 처리한다. TensorRT-LLM도 이전 step의 stop 검사·응답 처리를 다음 step 실행과 중첩하며 여분의 decode step이라는 tradeoff를 명시한다. [SGLang 설계](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4/), [TensorRT-LLM 설계](https://nvidia.github.io/TensorRT-LLM/features/overlap-scheduler.html).

Riley의 GPU sampling만으로 이 구조가 완성되지는 않는다. 제안 batch는 (1) 다음 token/sequence 상태를 GPU에서 전달, (2) metadata·completion buffer 이중화, (3) CUDA event 기반 iteration 수명 관리, (4) HTTP 응답·stop/cancel 처리와 다음 실행의 중첩이다. EOS 이후 계산 결과를 외부로 내보내지 않으며 KV page는 마지막 사용 event 전까지 재활용하지 않아야 한다.

작은 모델에 적합한 후보지만 효과는 남아 있는 iteration 사이 host bubble의 크기에 제한된다. V56 profile의 graph 내부 gap 감소와 graph 사이 CPU 지연은 다른 값이므로 섞어 계산하지 않는다. 이는 구조 변경을 선택한 뒤 필요한 검증 항목이지 또 다른 미세 튜닝 반복의 출발점이 아니다.

### 3. MPK/Mirage 방식 persistent execution: 가장 큰 구조 실험

MPK는 연산을 SM 단위 task graph로 낮추고 GPU 내부 scheduler가 하나의 persistent kernel 안에서 실행한다. CPU launch 수를 줄이는 것에 더해 연산 경계를 넘는 pipeline과 의존성 기반 실행이 핵심이다. 2026-06 개정 논문은 GPU 내부 admission·page metadata 관리도 설명한다. [MPK 논문 v2](https://arxiv.org/html/2512.22219v2).

이는 현재의 kernel-per-operator + CUDA Graph 구조를 바꾸는 후보다. 다만 논문 실험은 **A100/H100/B200, offline batched inference, prompt 64/output 1024, batch 1~16**이다. 4090 C32 자연 종료·온라인 arrival 성능은 입증하지 않았다. 논문의 최대 1.7배는 해당 실험값이며 Riley 예상치가 아니다. README의 다른 배수와 혼합하지 않는다. [실험 조건 §6.2–6.3 및 artifact](https://arxiv.org/html/2512.22219v2).

제안 실험은 먼저 SM89의 task kernel·shared-memory 자원 적합성을 판정하고, attention+MLP 한 layer의 task 실행/의존성/버퍼 재사용을 묶어 확인한 뒤 전 layer로 확대하는 것이다. serving adoption에는 동적 batch, cancellation, KV 회수, streaming completion까지 필요하다. 단일 고정 batch demo만으로 성공 처리하지 않는다. 지금 즉시 전체 엔진을 재작성할 근거는 부족하다.

### 4. NanoFlow/POD에서 가져오는 자원 중첩과 SLO 기반 batch 정책

NanoFlow는 operation 단위 nano-batch와 자원 배분으로 compute·memory·network 사용을 중첩한다. 단순한 CPU overlap보다 범위가 넓다. Riley에서는 network 부분을 제외한 compute/memory 중첩 아이디어가 대상이며, 작은 모델에서 나누는 비용이 이득보다 클 수 있다. [NanoFlow, 2024](https://arxiv.org/abs/2408.12757).

Sarathi-Serve는 chunked prefill과 decode를 멈추지 않는 schedule로 throughput/latency 균형을 다룬다. Riley는 이미 chunking과 mixed batching이 있으므로 새 기능처럼 추가하지 않는다. backend 변경 후 실제 mixed batch 시간 예산에 맞춘 admission, chunk 크기, graph bucket 정책을 함께 설계하는 데 참고한다. [Sarathi-Serve, OSDI 2024](https://arxiv.org/abs/2403.02310).

### 5. Speculative decoding: 큰 모델·긴 출력에서 별도 후보

EAGLE-3는 여러 layer의 feature를 활용하는 draft와 target 검증으로 한 번에 여러 token을 진행한다. 순차 decode 횟수 자체를 줄인다는 점에서 구조적인 방법이다. 그러나 SmolLM2-135M은 target 자체가 작아 draft·verification·KV rollback 비용을 상쇄할 여지가 작을 수 있다. 이는 Riley 적용성에 대한 추론이다. [EAGLE-3, 2025](https://arxiv.org/abs/2503.01840).

2026년 연구도 production vLLM에서 verification 비용과 workload별 acceptance 변동을 지적한다. 큰 배수만 보고 우선 도입하지 않는다. 적합한 draft checkpoint 유무, acceptance length, verification latency, C32 throughput을 함께 보아야 한다. [Speculative Decoding: Performance or Illusion?, 2026](https://arxiv.org/abs/2601.11580).

정확성은 greedy token 검증 및 일반 sampling의 target 분포 보존을 각각 다룬다. draft를 쓰면 정확성이 자동으로 보장된다고 가정하지 않는다. 더 큰 target 모델의 평가 축을 정한 뒤 검토할 순서다.

## 먼저 명확히 할 correctness 계약

현재 Riley reference는 BF16 중간 probability/partial의 rounding 순서까지 고정한 exact 검사를 포함한다. FlashAttention류 backend는 같은 수학적 attention을 계산해도 reduction 순서 때문에 이 reference와 byte-exact하지 않을 수 있다. 기존 검사를 조용히 tolerance로 바꾸어 통과시키지 않는다.

현행 compatibility 경로의 exact 검사는 보존한다. 새로운 backend에는 별도의 수치 검증 계약 초안을 먼저 만든다: FP32 reference 대비 오차 분포, full-logit 비교, greedy 불일치 위치와 누적 영향, batch 구성 변화에 따른 재현성, 길이·mask·RoPE 경계, NaN/Inf 정책, padding·KV 격리. 수치 허용치와 품질 기준은 결과를 본 뒤 맞추지 말고 사전에 정한다. 이 문서는 계약 변경의 실행 승인이 아니다.

SGLang도 batch invariant 연산과 deterministic inference를 별도 과제로 다룬다. 따라서 다른 엔진의 기본 backend가 현재 Riley exact 계약과 같다고 가정하면 안 된다. [SGLang deterministic inference](https://www.lmsys.org/blog/2025-09-22-sglang-deterministic/).

## 다음 작업의 실행 순서와 판정

1. **비교 조건 고정:** 현재 135M/BF16 회귀 축은 유지한다. 더 큰 모델 축은 엔진 지원과 메모리 예산을 확인해 별도로 정하고, 각 축에서는 네 엔진의 checkpoint/tokenizer/dtype/KV dtype/출력 규칙을 동일하게 고정한다. SGLang·TensorRT-LLM의 해당 조합 지원부터 확인한다.
2. **backend 구조 batch:** adapter, KV 연결, plan 재사용, shape dispatch를 한 묶음으로 평가한다. 단일 attention 수치만이 아니라 전체 model forward와 HTTP serving까지 연결한다.
3. **비동기 실행 batch:** token 상태 전달, metadata 이중화, event 수명 관리, 응답 후처리 중첩을 함께 검증한다. cancellation/EOS/동적 admission을 포함한다.
4. **MPK 타당성 판정:** SM89 이식 범위와 scheduler 비용을 확인하고 serving까지 갈 수 있는 경우에만 확대한다. 앞선 batch와 효과를 단순 합산하지 않는다.
5. **남은 성능 조정:** 구조 선택 후 남은 kernel·allocation·copy 병목을 profiling으로 좁힌다.

각 batch는 고정된 현재 baseline과 같은 날의 경쟁 엔진에 대해 교차 순서 반복한다. closed-loop C16/C32는 회귀 축이고, 실제 serving 판정에는 arrival-rate sweep, TTFT/TPOT SLO 내 goodput, P95/P99, 긴 출력·혼합 길이, memory 증가·실패율을 추가한다. C64 이상은 현재 지원 범위를 넘기므로 지원 구현과 검증 없이 결과를 주장하지 않는다.

큰 변화의 후보 선별 목표는 사용자의 +15% throughput/−10% latency 목표로 두되, 특정 workload 승리로 전체 통과시키지 않는다. 미세한 결과 차이는 반복 분산을 확인하고 보류한다. 논문 비교에는 하드웨어, 모델, precision, arrival 형태, baseline 버전을 함께 기록한다.

FlashInfer-Bench의 실제 serving trace를 활용한 평가 관점도 참고할 만하다. 이후 kernel 평가에는 실제 shape 분포와 model working set을 반영한다. 이는 구조 탐색을 대체하는 또 다른 microbenchmark 반복이 아니라, 선택한 구조의 효과를 잘못 판정하지 않기 위한 장치다. [FlashInfer-Bench, 2026](https://arxiv.org/abs/2601.00227).

이번 조사에서 프레임워크 설치·새 backend 구현·추가 serving 실험은 하지 않았다. 가장 먼저 진행할 구체적 후보는 **SM89 FlashInfer attention adapter와 기존 correctness 계약의 호환성 확인**이며, 가장 큰 연구 후보는 **MPK 형태의 GPU 내부 실행 구조**다.

## 추가 조사: Ada 대상 megakernel과 비교 엔진의 버전 경계

**Ada-MK (2026-05)**는 L20(SM89)에서 shared-memory 자원을 고려한 offline DAG 탐색과 고정 실행 경로를 사용하고, TensorRT-LLM prefill과 megakernel decode를 결합한다. MPK의 동적 GPU scheduler를 그대로 이식하는 것 외에 **shape별 사전 결정 실행**이라는 연구 방향을 추가한다. 실험은 Qwen 1.5B/1.7B GPTQ-W4A16, batch 1~16, offline 모드다. vLLM 0.19.0·SGLang 0.5.10·TRT-LLM 1.1.0rc5와 비교하므로 현재 135M BF16/C32 HTTP 성능의 증거가 아니다. 읽은 논문에서 저자 구현의 공개 저장소를 확인하지 못했다. 당장 가져다 쓸 backend보다 설계 참고자료로 분류한다. [Ada-MK 논문 §4–5](https://arxiv.org/html/2605.11581v1).

Riley 적용 시의 제안은 GPU의 동적 task scheduling과 shape별 고정 task 실행을 같은 후보로 혼합하지 않고 비교하는 것이다. 고정 경로는 자원 계획을 단순화할 수 있지만 실제 serving의 live row·context·admission 변화에 대한 dispatch가 필요하다. 이 효과는 미측정이다.

TensorRT-LLM 공식 migration 문서는 TensorRT engine backend 제거와 PyTorch execution backend로의 전환을 설명한다. 따라서 최신 TensorRT-LLM 비교를 예전 `trtllm-build` 기반 절차로 계획하면 안 된다. 한편 별도 support-matrix 페이지에는 25.06 container/10.11 TensorRT 정보가 남아 있어, URL에 버전이 없다는 이유로 두 문서가 같은 release를 설명한다고 간주하지 않는다. **비교할 release와 해당 release의 GPU/model/backend 지원을 함께 고정**해야 한다. [Migration](https://nvidia.github.io/TensorRT-LLM/latest/legacy/tensorrt-backend-removal.html), [support matrix](https://nvidia.github.io/TensorRT-LLM/reference/support-matrix.html).

원격 checkpoint의 `architectures`는 `LlamaForCausalLM`, `model_type`은 `llama`, tied embeddings=true이며 9 Q heads/3 KV heads다. SGLang 공식 소스에는 Llama 구현이 있지만 이 작은 shape의 실행 성공까지 증명하지 않는다. 현재 확인한 vLLM venv에는 SGLang/TensorRT-LLM 패키지가 없었다. 다른 환경 전체를 조사한 결과는 아니다. [SGLang Llama 소스](https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/models/llama.py).

## 기존 증거로 계산한 개선 여지

새 GPU 측정 없이 `raw/profile-v56/native-trace-v56/analysis.json`의 middle-80% 구간을 재집계했다. prefill/mixed와 decode의 graph span 합을 분모로, mapped attention 및 GQA scores/values kernel 시간 합을 분자로 사용했다. RoPE·KV write는 attention에 포함하지 않았다. 단계별 median을 더하거나 profiler의 synchronize 시간을 CPU 낭비 시간으로 간주하지 않았다. [입력 SHA256과 계산값](raw/architecture-headroom.json).

| 조건 | attention / GPU graph 시간 | attention 2배 가정 시 graph 속도 증가 | attention 4배 가정 시 graph 속도 증가 |
|---|---:|---:|---:|
| C16 natural trace | 29.81% | +17.52% | +28.80% |
| C32 natural trace | 31.32% | +18.57% | +30.70% |

계산식은 `1 / (1 - f + f / s)`다. 나머지 연산·batch 구성·gap이 그대로이고 backend 통합 비용이 없다는 가정이다. **이는 graph 시간의 민감도 계산이며 serving 예측이나 실현 가능한 상한의 실측이 아니다.** queueing·CPU 작업·동적 batch 변화는 반영하지 않는다.

Round62 C32 natural throughput 10,433.829 tok/s에서 vLLM 11,950.605 tok/s와 동등하려면 Riley 기준 +14.54%, vLLM보다 15% 높으려면 +31.72%가 필요하다. TPOT 2.874 ms는 동등까지 −20.01%, vLLM보다 10% 낮추려면 −28.01%가 필요하다. throughput 격차 −12.69%를 그대로 필요한 증가율로 쓰면 기준 분모가 달라 틀린다.

따라서 FlashInfer를 범용 attention 기반 확보의 첫 후보로 유지하되, 그 하나를 최종 성능 해결책으로 취급하지 않는다. 비동기 scheduling은 host 구간, persistent execution은 연산 경계와 중간 메모리 이동이라는 별도 축을 다룬다. 두 방식의 효과를 지금 더해서 예상 개선율을 제시할 근거는 없다. 향후 구현 batch의 성능 판단은 계속 실제 serving 지표로 한다.
