# Genuine multi-sequence decode: first N2/N4 batch

This is an implementation proposal, not a performance result. Implement one coherent batch spanning complete-prompt scheduling, a shared graph owner, genuinely concurrent GPU rows, and aggregate completion. Start with two active sequences, then qualify four using the same implementation. A decode iteration must execute its ready rows in one captured GPU graph; a host loop replaying the existing M1 graph once per request does not satisfy this proposal.

Update at 2026-09-12 11:49 KST: Round14 is still running. Its first four candidate/baseline pairs consistently show Batch8 throughput ratios of 0.9419–0.9423 and median TPOT ratios of 1.0730–1.0735. These are provisional individual-pair observations, not a completed campaign result. **Batch7 remains the accepted parent for the proposed multi-sequence implementation.** The first independent-row attention probe therefore extends its separate two-warp attention kernel, keeping precise RoPE/KV publication separate. References below to the fused Batch8 variant describe an optional alternative that must be reconsidered after paired profiling; numerical qualification alone does not select it. Scheduler and packet prototypes are CPU preparation only; the projection and independent-row attention probes have not run on the GPU.

The motivation is the accepted source's active1 queue, observed in [CONCURRENCY_SCREEN.md](CONCURRENCY_SCREEN.md): Riley C1 delivered 922.821 output tok/s with median first-text 5.156 ms; offered C2 delivered 933.788 tok/s with first-text 38.811 ms. These are HTTP first-visible-text measurements, not token TTFT. Only the C1 comparator pair completed; vLLM C2/budget128 failed the exact-text warmup gate. There is no valid concurrent vLLM ratio from that screen. The measurements used batch7, not the later batch8 fusion candidate. Batch8 has fresh numerical/model proof, but its serving performance was still unmeasured when this plan was written.

The existing [CONCURRENCY_NEXT_BATCH.md](CONCURRENCY_NEXT_BATCH.md) describes general scheduler seams and a serial replay bridge. The proposal below replaces that execution approach with N-row projections and kernels while retaining its useful separation between admission, device execution, and publication.

## Scope and execution contract

Keep the bound SmolLM2-135M BF16 geometry, P128 prompt, output limit 1–32, fixed-maximum KV admission, and the existing numerical contract. Preserve accepted F107/P128/M1 plus its qualified token-observation HTTP API as the C1 oracle and explicit rollback path. Introduce a separate opt-in decode capacity of 2 or 4; assign its implementation/signature identity only after the source is frozen. Do not silently widen the old M1 qualification.

There are two legal iteration shapes:

| Shape | Requests represented | Input and output contract |
|---|---:|---|
| `Prefill128` | 1 | Exactly positions 0–127, one output at position 127; existing P128 numerical path |
| `DecodeN` | 1–capacity | One input and one output per distinct request; independent positions 128–159 and independent KV block tables |

Do not mix prefill and decode rows in one plan. Do not batch prompts together in this first change. Sequential complete-P128 admissions followed by truly batched decode are useful without implementing multi-prompt prefill. Do not wait for a full decode bucket: dispatch the ready rows immediately. For capacity 4, capture decode buckets 1/2/4; three active rows use bucket 4 with one explicitly inactive row. The graph's request-row dimension is independent of P128's token-position dimension.

Keep one engine owner thread, one stream, one shared KV pool and one copy of the immutable model/packed weights. There must be one descriptor upload, one graph launch and one existing completion synchronization per decode iteration, with bulk output transfer. No hot allocation, heuristic search or recapture on a change of active count.

## Four linked implementation changes

### 1. Complete-P128 admission and bounded progress for ready decoders

Change `Scheduler::select_candidates` in `crates/riley-scheduler/src/scheduler.rs` through an explicit execution-shape policy, leaving the general scheduler policy intact for other backends. Today decode-first subtraction can leave 127 tokens for a prompt; the aged-prefill branch also reserves one token for decode and can select 127. Merely raising `max_active_sequences` therefore violates the current graph's complete-P128 contract.

For this profile, select either one complete eligible prompt or up to the configured number of ready decode rows. A token budget of128 can represent either shape for capacity ≤4; `max_prefill_chunk_tokens=128` must remain exact. Admission must promise all 160 positions per request before execution: at block size16, capacity 2 requires at least 20 physical/promise blocks and capacity 4 at least 40. Distinguish per-request logical block capacity 10 from the aggregate physical pool and flattened metadata capacity.

When both queues are ready, alternate one complete prefill iteration with at least one decode iteration; preserve ready-time/request-ID ordering within each class. This admits queued requests while ensuring decode progress, without waiting for the current100 ms aging threshold. The policy should explicitly track the previous dispatched shape and advance it only on an actual dispatch. It must not spin on an inadmissible prompt or count a rejected plan as progress. Measure the added prefill pause in active requests' token latency; bounded progress is not a latency guarantee.

Retain `Scheduler::prepare_plan` reservations and immutable block-table snapshots. `PreparedLlamaIteration` in `crates/riley-scheduler/src/execution.rs` already represents multiple rows and dense output slots. `PreparedLlamaBatchMetadata::validate` in `crates/riley-runtime/src/llama/batch.rs` already rejects duplicate sequence tags, duplicate physical blocks across the entire iteration, and non-dense/duplicate output slots. Reuse those checks before encoding the native packet.

### 2. One owner, versioned per-request metadata and a cold bucket catalog

Add a separate multi-sequence graph owner/module beside `OwnedLlamaDecodeExecutor` in `crates/riley-runtime/src/llama/graph_decode_full.rs`, rather than changing the meaning of its single-row `execute` and `greedy_token` APIs. A proposed `OwnedLlamaMultiDecodeExecutor` retains a single `OwnedGraphResourceReservation` and the existing `FullDecodeParents` ownership discipline. Factor immutable packed weights from the bucket-specific scratch/plans currently combined in `PackedDecodeParents` (`graph_decode_packed.rs`). Share its 60 weight parents; do not allocate another model per request or bucket.

The owner contains one bundle of P128 and decode 1/2/4 handles under one ledger. Its signature binds the bucket catalog, physical/logical capacities, packet/output schema, exact plans and numerical implementation. Native handle selection must use the freshly validated packet and the captured bucket identity. Registry entries must not manufacture independent ownership of the same leases. Allocate all plans and exact-size scratch for each captured bucket before capture; pinned staging and host output workspaces may use the maximum transfer size. Close every exec/graph before releasing any shared parent or plan. Partial capture failure and unknown completion retain the existing conservative cleanup policy.

The bucket size is cold launch geometry, but active count must be read from the freshly staged device header at byte24. Do not capture active count as a scalar kernel argument: one bucket4 graph must handle transitions between three and four active rows without recapture or node-parameter updates. Every inactive guard may read that common header first, but must return before accessing its row metadata, Q/KV or barriers. Positions, tokens, block maps and output slots likewise come from the current packet, not the packet used during capture. A direct-launch arithmetic probe does not prove freshness across retained graph replays; separately test repeated bucket4 captures with fresh3→4→3 packets and changed positions/maps before owner qualification.

The initial implementation should use separate exact-size decode1/2/4 scratch under the same ledger, sharing weights and KV only. `canonical_gemm_bf16_graph_state_is_valid` in `kernels/src/gemm.cu` requires each whole input/output parent byte length to equal the plan length: a maximum-N parent cannot bind a smaller bucket merely by passing its prefix. `bind_reserved_gemm_state` also explicitly rejects M≠1. Add a separately checked bucket binding entry for qualified M2/M4 plans and exact parents while preserving the M1 function. Sharing maximum-N device scratch would instead require a new checked span/prefix state contract, including offsets, lengths, alignment, aliasing and lifetime; that additional scope is not the default plan.

Introduce a distinct C recording/transfer contract through `kernels/include/riley_cuda.h`, `kernels/src/graph_resources.cu`, `crates/riley-cuda/src/ffi.rs` and `crates/riley-cuda/src/graph_resources.rs`. Preserve the existing ABI. The new packet should have an explicitly serialized header with version/magic, stage, bucket size, active count and replay identity, followed by fixed-capacity row records. Each active row carries its sequence identity, token, position, output slot, block count, physical IDs and valid counts. Use a separate P128 token payload. Define byte offsets, widths and checked lengths centrally; do not serialize Rust struct padding.

Validate **every row before any staging copy or GPU submission**: legal homogeneous stage, exact token counts, vocabulary bounds, position range, dense output slots, unique sequence identities, exact live/valid counts, within-pool physical IDs and cross-row block exclusivity. Reject unrecognized versions, bucket/count disagreements, duplicate rows, aliases and nonzero inactive/padding fields. Decode positions can differ between rows; there is no shared `end_position + 1 - rows` interpretation. Inactive bucket rows contain zero inputs, skip all KV/output publication, and cannot report success as active rows.

The device result is an array bound to the current replay and dense output slots: per-row argmax/report/status plus optional full logits. Clear output readiness before execution and validate the complete result before exposing any getter. Echo/check the replay and row mapping so a shorter iteration cannot consume stale output from a previous larger bucket. The full-logits payload alone is `active_count × 49,152 × 2` bytes: 196,608 for N2 and 393,216 for N4. Size staging for the maximum encoded packet/result, using checked arithmetic. The GPU-greedy serving path should continue avoiding full-logits D2H.

### 3. True N-row projections, attention and output kernels

All numerical operations need independent-request row semantics, including O, down and the final head; batching only the two packed projections is insufficient. Here N denotes request rows (the GEMM M dimension); projection weights are stored as `[output_width,input_width]` and the operation is `Y = X Wᵀ`. Prepare exact bucket plans at startup and capture each projection once per bucket, not once per row.

| Operation | Independent-row layout or work | Concrete source seam |
|---|---|---|
| Embedding | N token IDs → BF16 `[N,576]`; initialize inactive rows deterministically | `kernels/src/primitives.cu`; new descriptor-aware row entry |
| RMSNorm/residual | BF16 row 576; FP32 residual row 576 =2,304 bytes | `graph_numerics_precise.cu` norm row wrappers; verify offsets/initial versus residual paths |
| Packed QKV | `[N,576] × [960,576]` → `[N,960]` | `graph_decode_packed.rs`, `kernels/src/gemm.cu` and graph bindings |
| RoPE/KV and attention | Independent row positions/tables; preserve Batch7 attention's 64-thread CTA and extend its grid to 9×2×N | `graph_numerics_precise.cu`, `graph_numerics.cu`, `ffi_internal.hpp`, `graph_resources.cu` |
| O | `[N,576] × [576,576]` → `[N,576]` | Bucket-specific GEMM plan/binding |
| Packed gate/up and SwiGLU | Projection `[N,3072]`; gate/up each 1536 within that row; product `[N,1536]` | Packed plan plus a packed-stride SwiGLU entry |
| Down | `[N,1536] × [576,1536]` → `[N,576]` | Bucket-specific GEMM plan/binding |
| Final norm/head/argmax | Norm row 576, head output `[N,49152]`, one complete report/token per active row | Norm, head plan, row argmax and bulk result publication |

Packed QKV byte stride is 1,920, with Q/K/V byte offsets 0/1,152/1,536 within each row. Packed gate/up byte stride is 6,144, with gate/up offsets 0/3,072. **The existing `compiled_swiglu_rows` assumes separate contiguous gate and up arrays, each with a 1,536-element row stride. Passing the packed GU parent and an offset pointer would read the wrong row for N>1.** Add an explicit packed-stride entry preserving the existing scalar expression and BF16 conversions.

`CudaContext::prepare_gemm_anchored` (`crates/riley-cuda/src/gemm.rs`) and `select_anchored_deterministic_algorithm` (`kernels/src/gemm.cu`) can test the existing opaque M1 algorithm against M2/M4 descriptors with `cublasLtMatmulAlgoCheck` and no heuristic fallback. This is a useful first candidate, not numerical proof. The current `reserved_packed_decode_gemm_plan_matches` and `graph_decode_packed.rs::validate_plan` bind M1 and exact sizes/algorithm metadata. Add separately qualified bucket identities; do not loosen that M1 gate. Hash complete dimensions, layouts, algorithm/workspace/reduction options and runtime identity for every bucket.

Run a bounded projection feasibility probe before completing the owner integration: all 30 actual checkpoint layers, packed QKV/GU plus O/down, and the actual final-head weight; N2/N4 heterogeneous row inputs and inactive-row cases; compare every output word with independently executed accepted M1. Rows at input offsets 1,152 or output offsets 1,920 are not 256-byte aligned. Copy oracle inputs to their own correctly aligned allocations instead of relying on unsupported borrowed subspans. Poison/guard all outputs and verify input/weight immutability. Matching the opaque algorithm ID does not establish identical reduction order for M2/M4.

If these plans fail exact comparison, reject them and stop this batch for a separate arithmetic feasibility decision. There is no accepted compiled decode-projection kernel whose row grid can simply be extended: accepted decode projections use opaque cuBLASLt code, and the compiled prefill GEMV/M16 paths have different arithmetic and position contracts. A custom multi-row projection would be a new numerical implementation and additional scope, requiring its own exact oracle probes before integration. Do not use a tolerance or serial host replay to make the gate pass. Preserve the accepted M1 plans/library identity and P128 compiled kernel bodies as standalone oracles.

For the selected Batch7 path, precise RoPE/KV publication completes on the same stream before attention. Attention reads its row's rotated Q, position and block table; it writes only that row's 576-element output and does not modify KV. The feasibility probe compares against separately allocated, aligned accepted M1 executions. It must verify the entire shared KV pool remains unchanged. Inactive-row guards must be uniform and precede metadata/input reads and all CTA barriers.

If later profiling justifies the optional fused variant, each CTA instead reads its row's packed raw Q/K/V and uses Batch8's qualified mixed-FMA/BF16 conversion. Q publication is unique per query head and KV publication per KV head within each row; current-token reads bypass global cache through local K/raw V. That variant needs separate probes and full-model proof. It is not implied by the Batch7 attention-only probe.

Existing RoPE/KV/attention `*_rows` wrappers represent consecutive positions of one sequence and cannot substitute for this operation. Independent-element norm helpers are reusable only after checking row strides; sharing the word “rows” is not a layout contract.

### 4. Aggregate completion, configuration and serving integration

Update the graph branch of `execute_llama_iteration_graph` in `crates/riley-scheduler/src/execution.rs`: it currently calls a singular owner and appends one `greedy_token`. Download/validate all active row statuses first, then fill its existing dense output workspace once. For CPU sampling, retain all `output_count × vocab` logits; for GPU sampling, consume exactly one validated token per slot. Reserve workspaces before dispatch and reuse them. Any malformed/stale row invalidates the iteration before any token is published.

Reuse `Scheduler::complete_iteration`'s full-result/prepublication validation and reservation settlement. “Atomic completion” here means no externally visible row token before the entire batch result is validated. It does **not** mean GPU KV writes can be rolled back. On a post-submission failure, contain all affected sequences and publish no batch output; if completion is unknown, retain their KV/leases until quiescence is established. Cancellation of one row during execution must neither free its blocks early nor discard successful unrelated requests. Preserve the scheduler's existing cancellation settlement and per-request token event routing after commit.

Wire explicit capacity/stage bounds through `crates/riley-runtime/src/llama/executor/config.rs`, `executor/owner.rs`, `crates/riley-runtime/src/llama/batch_executor.rs`, `crates/riley-server/src/main.rs`, and `CudaEngineResources::prepare` in `crates/riley-server/src/engine.rs`. Current profile guards require `max_rows==1`/active1, and batched-prefill detection depends on `max_input_tokens==128`; these must become separate concepts. Keep ordinary eager/default paths unchanged. Keep the base single-row forward/P128 resources available while the new owner adds N-row scratch and plans. Check the new executor supports the exact scheduler shape before accepting a request.

The server already sizes pending/sample/output workspaces using output capacity and publishes request-specific committed events. Audit those capacity assumptions at construction and ensure event order/index is maintained separately per request. Existing HTTP workers8/waiting64 can exercise offered C≤8 with active2/4; HTTP transport changes and extra engine threads are outside this batch.

## Qualification and acceptance

Finish the four changes as one optimization batch, with early arithmetic feasibility as a go/no-go gate. Required evidence is broader than a projection speed test:

1. **CPU contracts:** mixed-ready queues never produce 127-token prefill; full P128 admission, immediate partial decode buckets and bounded class progress; duplicate/stale rows/slots and cross-request block aliases rejected; capacity/overflow checks; all-result validation before publication; one-row cancellation, failed dispatch and unknown completion containment. Exercise 1→2→4→3→1 transitions and new requests joining between decodes.
2. **GPU numerical proof:** fresh aligned M2/M4 projection probes; independent-request fused attention across positions 128–159, distinct maps and poisoned current KV; then actual full-model N2/N4 runs with different prompts, positions and output lengths. Compare full logits, every committed token, all initialized KV bytes and row statuses against independent accepted C1 runs. Include slot permutation, N3 padding, cancellation/reuse, malformed descriptors before mutation, guard regions and zero allocations after close. Carry the existing P128/full-model 96-KV, retained6/invalid42, legacy/profile and server tests forward with fresh source/binary receipts; old results are lineage only.
3. **Execution evidence:** capture inventory proves one decode launch/completion per iteration and row-aware kernels/plans; report bucket occupancy, active sequence count, cold allocation/capture cost, resident KV/scratch/plan bytes and any idle padded work. Disable diagnostic events during serving timing. Passing a standalone probe is not a full serving correctness claim.
4. **Matched serving:** establish new N2 and N4 baselines at offered C1/2/4/8 with identical model/input/output and declared lane capacities/budgets. Requalify each vLLM control's raw IDs/text/usage before measuring; C2/budget128's rejected equality result cannot be repurposed as a control, and the old unrun C4/C8 settings are not evidence. Use the frozen token-aware client contract for actual committed-token TTFT/TPOT; retain first-visible-text as a separately named metric. Report common-wall successful-token throughput, request/failure/timeout counts, P95/P99 E2E and token latency, queue delay, and occupancy. Repeat selected valid controls with fresh process pairs and at least 1,000 retained requests per lane before an acceptance decision.

Compare against a fresh accepted active1/F107 baseline with the qualified token-observation API and the properly qualified vLLM lanes. The first decision is whether true N2/N4 execution reduces the observed queue penalty and improves throughput without correctness or C1 latency regression. The overall target remains vLLM-or-better throughput/latency and stable high-concurrency tails; no result in this document establishes it. If improvement is absent, profile projection, attention, head and admission costs by bucket before selecting another batch.

## Rollback and boundaries

Use a cold-start opt-in for the new owner; rollback restarts with the unchanged accepted active1/F107 path, budget128/chunk128 and its qualified source/binaries. Do not switch a live request between owners or fall back after a potentially mutating failed graph replay. A new bucket that fails numeric/plan validation must fail preparation without changing the existing M1 qualification.

Keep distinct source/build/probe/model/HTTP/measurement receipts. Record the exact four inherited HTTP token files when creating the new source snapshot; do not imply an API proof automatically covers a different native implementation. No remote state or production file was changed to write this plan. Speculative decoding, multi-prompt prefill, KV compression, paged-cache sharing, attention arithmetic changes and HTTP worker redesign are outside this batch.
