## 1. 판정 기준과 측정 방법

| 항목 | 기준 |
|---|---|
| 서빙 | 일반 HTTP `/v1/completions`로 로드·서빙 |
| 정합성 | C1/C8/C32에서 fixture 15개 프롬프트의 출력 토큰이 동시성과 무관하게 동일(15/15), FP32 HF greedy 기준 일치가 HF BF16 eager·vLLM보다 나쁘지 않음 |
| 성능(필수) | 8셀(C1/C8/C16/C32 × fixed/natural), warm-up 32 + 측정 192, 같은 실행에서 vLLM과 순서를 바꿔 2회 측정한 평균. C8/C16/C32 처리량 ≥ vLLM, TPOT p50 ≤ vLLM, 전 셀 TTFT p50 ≤ vLLM. C1은 처리량·TPOT ±3% 이내면 동률 |
| TTFT p95/p99 | 개선 시도, 안 되면 근거와 함께 종료 |
| 안정성 | 8셀 각 300초 지속 부하 + 취소 + 재요청 + 자원 회수 |
| 도전 | 처리량 +10%, TPOT p50 −5% |

- 호스트: `aws-a100`, A100-SXM4-40GB 8장 공유 호스트(다른 사용자가 GPU 2–5와 CPU를 계속 사용), 드라이버 550.127, CUDA 12.4 툴킷(cuBLAS 12.4.5.8), Xeon 8275CL.
- vLLM: 0.27.1+cu129 릴리스 휠, torch 2.13.0+cu129, prefix cache 끔, `--gpu-memory-utilization 0.6`.
- 판정 측정은 GPU 한 장에서, 내 다른 작업이 호스트에 없을 때 돌렸다. 다른 사용자의 프로세스가 같은 GPU에 보인 레인은 표시하고 제외하지 않는다(지금까지 해당 레인 없음).
- 측정 스크립트: `a100_matrix.py`(8셀 매트릭스, 실행 전 `plan.json` 기록), `a100_verdict.py`(위 기준으로 판정), `a100_ab.py`(Riley끼리 A/B와 출력 해시 비교), `a100_hf_token_check.py`·`a100_fp32_ref.py`(정합성), `a100_stability.py`(안정성), `a100_prof*.py`(nsys 진단).
- "스크리닝"이라고 적은 측정은 세 모델을 GPU 세 장에서 동시에 돌린 Riley 단독 A/B로, 채택 판단용이고 판정용이 아니다.

## 2. D1 — Qwen2.5-Instruct 1.5B / 3B / 7B

### 2.1 출발점 (4090용 설정 그대로, A100용 조정 없음)

`qwen2-5-1-5b-instruct-matrix-attempt01`, `qwen3b-matrix-attempt02`, `qwen2-5-7b-instruct-matrix-attempt01`.
처리량 Riley/vLLM: 1.5B 0.92–1.35, 3B 0.87–1.11, 7B 0.88–0.98. TPOT p50은 3B 8셀 중 7셀, 7B 8셀 전부에서 vLLM보다 느렸다.

### 2.2 원인 분석

nsys로 3B c32-natural의 스텝을 Riley와 vLLM 양쪽에서 비교했다(`d1-prof-3b-c32-natural-attempt01`, `d1-prof-vllm-3b-c32-natural-attempt02`).

| 32행 순수 디코드 스텝 | Riley | vLLM |
|---|---|---|
| GPU 연산 시간 | 7.49 ms | 7.56 ms |
| 스텝 사이 GPU 유휴 | 약 0.4–0.5 ms | 약 0.1 ms |
| gate/up 투영 | GEMM 2회 × 40.5 µs | 병합 GEMM 1회 74.4 µs |

- GPU 연산은 이미 같거나 빨랐고, 차이는 (a) 호스트 쪽 스텝 사이 대기, (b) vLLM의 gate|up 병합 GEMM, (c) A100에서 대부분 anchor로 떨어지던 GEMM 알고리즘 표였다.
- 스텝 그래프를 새 형상마다 기록할 때 스텝 하나가 약 8.7 ms 멈추고, c32 측정 구간(약 5초) 안에 8–10번 일어났다(`RILEY_HOST_STEP_TRACE=1` 계측, `d1-hosttrace-3b-attempt03`).
- 7B·1.5B는 hidden이 2048이 아니어서 RMSNorm이 느린 256-스레드 커널로 돌고 있었다(7B 스텝당 14 µs × 56회, `d1-prof-7b-c8-natural-attempt01`).
- vLLM은 요청 묶음이 동시에 끝나고 동시에 들어와 prefill이 드문 큰 스텝에 몰린다(스텝 주기 p10–p95가 6.9–7.8 ms로 거의 일정). Riley는 스텝당 256토큰 예산으로 prefill을 나눠 넣어 전체 스텝의 약 27%가 혼합 스텝이다. prefill 토큰당 비용은 Riley가 더 낮았다(약 23 µs 대 42 µs).

- 꼬리를 vLLM 수준으로 내리려면 스텝당 토큰 예산을 256보다 크게 해야 하고, 그러려면 2단계 어텐션 경로의 dense 행 상한(256)과 256행 초과 GEMM 동등성 표가 함께 바뀌어야 한다. 이번 범위에서는 하지 않고 위 근거로 종료한다.

producer 구조만 바꾸는 시도 일곱 번은 모두 1% 안팎이거나 손해였다(뒤의 두 개는 옵션으로 코드에 남겼고 기본값은 꺼져 있다). 마지막 줄의 dense 커널은 그 자체로는 느렸지만 3.5의 실행 격자 변경과 합쳤을 때 효과가 났다. 측정으로 확인한 사실(Qwen3-0.6B natural, `prof11/18/19/21-*`):
decode만 있는 스텝의 producer는 C1 7.0 µs, C8 14.9 µs, C32 32.4 µs이고 prefill이 섞인 스텝은 127 µs(페이지 용량 64) / 108 µs(용량 34)다. merge는 5–8 µs / 26 µs.
즉 손해는 prompt 행에서 난다: 행 × 페이지 × KV head마다 CTA 하나라서 397토큰 프롬프트의 한 청크가 레이어당 CTA 1.7–2.4만 개가 된다.
prompt 행을 dense 커널로 옮겨도 per-page producer의 prefill 스텝 시간은 103 µs로 남았다(`prof26-*`). 즉 prompt 행의 연산량이나 블록 수가 아니라 실행 격자(페이지 용량 × KV head × dense 행 256) 쪽 비용인데, "실행된 warp 수 + 일한 warp 수"의 단순 모형으로는 측정값들이 다 맞지 않는다.
다음에 이 항목을 다시 열 때는 end-to-end 변형을 더 만들기보다 producer 실행을 따로 재는 GPU 마이크로벤치마크(행 수·용량·활성 페이지·prompt 행 비율을 바꿔 가며)부터 해야 한다.

### 3.5 natural 워크로드 격차의 원인과 해소 (진행 중)

원인(측정으로 확인): prefill이 섞인 기록 스텝은 per-page tensor-core producer를 `페이지 용량 × KV head × dense 행 256`개의 1-warp 블록으로 실행한다(레이어당 약 13만 블록, Qwen3-0.6B natural). 이 커널의 시간을 정하는 것은 prompt 행의 연산이 아니라 블록을 내보내는 속도(블록당 약 0.6 ns)였다. prompt 행을 다른 커널로 옮겨도 격자가 256행을 덮는 한 시간이 그대로였고(`prof26-*`), 그래서 3.4의 구조 변경들이 효과가 없었다.

해소(`--prompt-attention dense-v1`, 바이너리 `riley-mc-c4638491`):
1. prompt 행은 전부 일반화한 prompt 행 커널로 처리한다(16행 × 4페이지가 CTA 하나, 임의 헤드 구성, head 128/64). prompt 행의 반올림이 per-page 경로와 달라진다(4페이지 구간 단위 online softmax, 확률을 BF16으로 반올림). 배치·청크와 무관하다는 성질은 그대로다.
2. per-page producer는 "prompt 행이 아닌 행"의 목록(디바이스 버퍼, 스텝마다 갱신)을 따라 실행해서 격자의 행 축이 256이 아니라 동시 시퀀스 수 이하가 된다.
3. prompt 행 커널의 페이지 적재를 16바이트 로드로 한다.

  가장 큰 차이는 RMSNorm이다. 폭이 256의 배수가 아닌 모델(896, 960, 576)은 256스레드 커널을 쓰는데, 스레드마다 전역 메모리 로드 3–4개를 차례로 기다리고 residual을 썼다가 다시 읽는다. 256의 배수 폭에 쓰던 1024스레드 형태(비트 동일)를 이 폭들에도 쓰도록 넓혔다. 폭 576은 main에 이미 같은 목적의 전용 커널이 있어 896·960 등이 대상이다. GPU 테스트(`wide_general_rms_norm_gpu`, 폭 512–4096, 4095·1000 포함)에서 기존 커널과 다른 비트 0개(A100 `mc-native-test-42`, RTX 4090에서도 같음). C1 효과 측정(`c1norm43`)은 작업 호스트를 RTX 4090으로 옮기면서 중단했다.
  그다음은 GEMM의 split-K 구성(anchor 재선정 대상에 이 모델의 형상을 추가할 예정)이다.

- Riley의 argmax는 BF16 logit에서 같은 값이면 낮은 토큰 id를 고른다. 위 동률 분기에서는 이 규칙이 FP32와 다른 쪽을 골랐을 수 있다.

레버(`--greedy-tie-break fp32-rescore-v1`, 기본은 `lowest-token-v1`):

- LM head의 FP32 누산값을 BF16으로 반올림하는 것은 단조라 순서를 뒤집지 않고 합칠 뿐이다. 그래서 행의 최댓값을 공유하는 토큰만 다시 본다.
- 그 토큰들을 출력 행의 정규화된 hidden과 LM head 행의 FP32 내적(고정 순서)으로 다시 계산해 가장 큰 쪽을 고른다. 같으면 낮은 id, 후보가 64개를 넘으면 기존 규칙이다.
- 동률이 없는 행은 토큰이 같다. 한 행의 선택은 그 행에만 의존해 배치 불변이다.
- argmax 커널 안에서 동률 여부만 추가로 추적하고, 동률인 행에서만 두 번째 패스를 돈다.
- GPU 테스트 `fp32_tie_break_rescores_only_tied_maxima_per_row`(`bf16_argmax_gpu`): 동률 없음·2개·3개·상한 밖·FP32 동점·64개 초과, gathered와 index map, 행 단독 실행이 CPU oracle과 같다. 6/6 통과(`mc-native-test-79.log`, 바이너리 `riley-mc-e432223e`).

`tw88`/`tw89` 결과(`riley-mc-b74361d3`): 두 window 모두 12개 모델 불변 15/15이고, FP32 일치가 모든 모델에서 `tb81`(정확한 동률만)과 같다(Qwen3-0.6B 13, SmolLM2-360M 13, SmolLM2-1.7B 12, 나머지 9개 충족). 채택 조건의 "미달 모델이 줄어든다"를 만족하지 못해 채택하지 않는다.

- 해석: 남은 분기에서는 Riley 자신의 hidden 상태로 FP32 내적을 다시 계산해도 Riley의 토큰이 이긴다. 차이는 argmax나 LM head의 반올림이 아니라 그 앞의 hidden 상태(BF16 레이어 연산)에서 생긴다.
- FP32 미달 세 모델(Qwen3-0.6B HF BF16 대비 −1, SmolLM2-360M HF BF16·vLLM 대비 −1, SmolLM2-1.7B vLLM 대비 −1)에 대한 레버: (1) 동률 FP32 재점수 — Qwen3-0.6B 12 → 13, 나머지 두 모델 변화 없음; (2) BF16 1·2칸 window 재점수 — 세 모델 모두 변화 없음. 두 레버가 연속으로 남은 격차를 줄이지 못해, 이 항목은 이 근거로 **종료(근거와 함께)**로 둔다. 세 모델 모두 15개 중 1개 차이이며, HF BF16·vLLM과 같은 성격(FP32 차이 0.2 이하의 근소한 분기, `fm78`)이다.

- DeepSeek-R1-Distill은 표에서 뺐다. HF 기준에 BOS를 붙이면 vLLM(BOS 없음)과 비교가 성립하지 않고, R1-Llama는 HF 토크나이저 자체가 깨져 Riley·vLLM 모두 0이다. Riley 단독 값은 R1-Qwen 1.5B 82, 7B 17, 14B 122다.

### 6.4 Qwen3-14B와 DeepSeek-R1-Distill-Llama-8B

- Qwen3-14B: sm80 GEMM 등가 표에 5120x34816(gate|up), 17408x5120(down), 5120x151936(LM head)이 없어 anchor 구성으로 돌았다(M=1 gate|up 334.6 vs 255.8 µs). `gemm-equiv-a100-attempt03`의 항목을 `kernels/src/gemm.cu`에 넣은 뒤 `qual-nv-qwen3-14b-attempt04`에서 8셀 모두 충족(c1-fixed TPOT 22.5 vs vLLM 22.3 ms).
- DeepSeek-R1-Distill-Llama-8B: `tokenizer.json` post_processor에 BOS 템플릿이 없고, BOS는 `tokenizer_config.json`의 `add_bos_token`에서 온다. 로더가 템플릿을 선택 사항으로 받고 이 메타데이터의 BOS를 쓰도록 고쳤다(`tokenizer.rs`, `model.rs`, `qwen.rs`). `qual-nv-r1-llama-8b-attempt03`에서 8셀 모두 충족.
- 이로써 단일 GPU 충족 모델은 22개에서 24개가 됐다([성능 표](model-coverage-a100-perf-table.md)).

### 6.5 단일 GPU 한계와 Qwen2.5-32B tensor parallel

- 단일 GPU: Qwen2.5-32B-Instruct BF16(약 65 GB)은 40 GB A100 한 장에 Riley와 vLLM 모두 올라가지 않는다(`evidence/limit-Qwen2.5-32B-Instruct-gpu4`). 14B가 한 장의 상한이다.
- TP=2(GPU 6·7, NVLink, `--tensor-parallel-devices 6,7`) 대 vLLM `--tensor-parallel-size 2 --gpu-memory-utilization 0.9 --generation-config vllm`, `evidence/tp2-q25-32b-gemm4-attempt01`(바이너리 `bin/riley-tp-gemm4`):
  - TTFT p50은 8셀 모두 낮다(0.57–0.89배).
  - C32는 처리량·TPOT 모두 앞선다(fixed 549.7 vs 512.4 tok/s).
  - C1은 처리량 3–5 %, C8은 1–4 % 뒤처지고 TPOT은 둘 다 4–5 % 길다. C16은 fixed가 앞서고 natural은 TPOT +1.1 %다. 그래서 필수 기준은 미충족이다.
  - 모든 셀에서 반복·동시성에 관계없이 출력이 같다.
- 설계, 개선 시도(GEMM 표 항목 추가 +1.1 %, 복사 통합 기각)와 다음 후보는 [tensor-parallel 설계](tensor-parallel-design.md#status-2026-10-31)에 있다.
