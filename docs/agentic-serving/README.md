# Riley 에이전트 추론과 대규모 서빙 이정표

Riley의 목표는 긴 입력과 짧은 도구 호출이 이어지는 작업에서 **사용자가 최종 답변을 읽기 시작하는 시간과 끝까지 받는 시간을 함께 줄이는 것**이다. 이미 스트리밍 중인 답변의 속도도 유지해야 한다. 설계는 Riley에서 관측한 재계산량과 실행 비용으로 결정한다. 후보를 고정한 뒤 vLLM을 동일 조건에서 비교해 decode 경쟁력을 판정한다.

도구가 반환한 수치와 출처로 최종 답변의 첫 문장을 확정하는 선택 경로도 검증했다. Coder-7B CPU에서 인용과 첫 문장을 함께 지킨 사례는 0/2에서 2/2로 늘었다. 모델이 바로 이어 쓴 설명 두 건은 p95의 뜻을 누락하거나 틀렸다. 지시를 보강하면 두 건 모두 95번째 백분위를 설명했지만 생성량이 늘고 90단어를 초과했다. 최종 답변의 속도와 품질을 함께 충족하는 기본 경로는 계속 검증 중이다. [1단계 답변 원문과 비교](01-workflow-baseline.md#도구에서-확인한-수치로-최종-답변을-시작하는-실험)

최종 스트리밍에서는 텍스트 조각의 중복 JSON 처리를 제거했다. 모델 연산 없이 16개 클라이언트가 같은 64조각을 받을 때 마지막 콘텐츠 p95는 4.83~4.96ms에서 4.12~4.41ms로 줄었다. 단일 조각의 CPU 절감량은 기존 A100 토큰 간격의 약 0.025%여서, 워크플로의 큰 지연을 해소할 우선순위는 도구 이후 대기와 prefill로 유지한다. [3단계 CPU·HTTP·GPU 측정 범위](03-mixed-scheduling.md#최종-답변의-gpu-생성과-http-전달-비용)

**Coder-7B 엔진 교차 검증.** 11월 26일 AWS A100 4·5번에서 Riley와 vLLM을 역순으로 기동했다. 동일 입력·캐시 적중량의 고정 64토큰 decode에서 Riley/vLLM TPOT 비율은 0.246~0.260이었다. C16 자연 종료의 최종 완료 p95는 vLLM 20.35~20.79초에서 Riley 9.41~9.49초로 줄었고, 두 엔진의 전체 176건이 기본 정답 검사를 통과했다. 물리 다중 노드 시험과 고객 카나리에는 배포 인벤토리와 해당 서비스의 트래픽 범위가 필요하다. **11월 25일 Coder-7B 검증.** 최종 호출에서 page와 fixed-tile의 첫 콘텐츠 대기 차이 217~219ms 중 99.6% 이상은 GPU prefill에서 발생했다. 기본 varlen 프로파일의 fixed-tile에서 100ms 도구 대기를 활용하자 장문 세 작업은 최종 prefill 한 스텝을 줄여 첫 콘텐츠를 약 90ms 앞당겼다. 이미 1,344토큰을 재사용하던 작업은 추가 176토큰을 준비해도 첫 콘텐츠 이득이 2ms 미만이었다. 별도 일반 바이너리에서 500ms 대기 힌트를 적용한 재생 클라이언트는 기존 독자가 있는 두 작업의 최종 완료를 171~220ms 앞당겼다. [클라이언트 적용 결과](02-prefill-and-reuse.md#coder-7b-재생-클라이언트의-조건부-적용) [02의 100ms 도구 대기 실험](02-prefill-and-reuse.md#coder-7b에서-도구-대기-100ms를-실제-prefill에-사용한-결과) · [05의 지표 검산](05-production-qualification.md#운영-지표에서-prefill과-decode의-gpu-시간-확인)

01에서 고정한 연쇄와 지표를 이후 단계가 공유한다. 02에서 KV 재사용률이 충분하면 세션 API 개발을 건너뛰고 새 입력 실행 비용을 본다. 03에서 스케줄 변경의 이론적 이득조차 작으면 02의 실행기 후보로 돌아간다. 04는 검증한 단일 GPU 구성을 복제하며, 05에서 실제 노드 경계와 장애를 추가한다. 단계마다 새 기능을 채택할 필요는 없다. 후보가 탈락하면 근거와 다음 가설도 단계의 결과로 남긴다.

**11월 25일 기준 실행 우선순위.** 두 ID가 명시된 조회에는 검증한 원본 레코드 선택기를 적용할 수 있다. 필드·연산·반환 형식이 정해진 집계는 도구가 전체 목록을 읽어 정확한 JSON을 직접 구성한다. 자유 형식 장문 검색은 02의 정답 기준과 03의 최종 완료 지연이 다음 판정 대상이다. Coder-14B 스케줄러 후보는 RAG 보호 목표를 통과했지만 짧은 C32와 동시 도구 반환의 완료 기준이 남아 있다. 서비스 인수에는 04의 복제본·테넌트 부하와 05의 실제 다중 노드·고객 트레이스가 필요하다.

**긴 경로의 KV 캐시 게시.** 첫 KV 블록이 다른 두 경로를 256토큰씩 교대로 연장하는 Apple M4 시험에서 경로당 32K의 CPU 게시 시간은 0.929→0.080ms였다. Coder-7B 스케줄러 재생 72개 조건의 캐시 적중·퇴출·배정·완료 순서는 모두 일치했다. 11월 26일 AWS A100 5·6번의 실제 Qwen 7B 응답 136개에서도 생성 토큰과 캐시 계수가 일치했다. 30K 콜드 요청의 완료 시간은 두 GPU 모두 약 42초였다. [CPU 측정과 재생](02-prefill-and-reuse.md#첫-kv-블록이-다른-긴-경로를-교대로-게시할-때) · [A100 교차 검증](02-prefill-and-reuse.md#aws-a100-두-장의-32k-프로파일-교차-검증)

**다중 세션 라우팅.** 혼합 라우팅 시험 144개에서 세 정책은 모두 같은 44/48개 작업이 정답·지연 기준을 통과했고, 긴 prefill을 보류할 조건은 0회였다. 보류 정책은 과부하용 후보로 유지한다. [혼합 라우팅 측정](04-replicas-and-tenants.md#일반-혼합-부하에서-보류가-실제로-필요한-빈도)

**최종 답변의 형식과 완료 시간.** 한 호스트의 A100 두 장에서 수치 세 문장과 출처 설명을 나누어 지시한 후속 시험을 했다. 정답·지연·첫 문장을 지킨 작업은 59→64/64, 양쪽 정답 59개에서 첫 콘텐츠 p95는 2.233→2.273초, 완료 p95는 4.338→3.979초였다. 요구한 괄호 인용 위치까지 맞춘 답변은 45/64였고 정확히 90단어인 후보는 0/64였다. 강제 형식의 기본 경로 채택을 보류했다. [두 교차 시험과 판정](03-mixed-scheduling.md#부하-중-최종-답변의-수치출처문장-형식)

**두 추가 모델의 decode 판정.** A100에서 Qwen2.5-3B와 Coder-7B가 각각 동일한 실제 최종 입력·64토큰·동일 캐시 적중량으로 vLLM과 두 번의 교차 비교를 통과했다. 콘텐츠 TPOT 중앙값 비율은 각각 0.923~0.962와 0.978~0.993이었다. 3B의 긴 도구 결과에서는 자연 종료 시 Riley가 40토큰 더 써서 두 번 모두 약 0.14초 늦었다. 출력 ID까지 같은 입력은 3B가 0/4, Coder-7B가 1/4였다. [모드·시드·토큰 대조](03-mixed-scheduling.md#qwen25-3b와-coder-7b의-동일-길이-최종-decode)

**자연 종료의 남은 격차.** 긴 이력의 다섯 작업 중 Riley가 늦은 경우는 다른 세션이 답변을 읽는 동안 긴 도구 결과가 돌아온 작업이었다. 다섯 번의 교차 기동에서 최종 호출 제출까지 −8ms, 제출 뒤 첫 콘텐츠까지 +72ms, 이후 마지막 콘텐츠까지 +376ms였다. Riley가 32토큰 더 생성한 효과가 컸다. [작업별 지연 분해](03-mixed-scheduling.md#자연-종료의-044초-차이가-발생한-구간)

**긴 도구 결과의 최종 응답.** 도구 호출을 끈 최종 턴에서도 긴 결과에만 앞선 도구 설명을 유지하자, Qwen 7B의 긴 이력에서 재사용량은 32→3,136토큰, 최종 요청의 첫 콘텐츠 대기는 약 450→230ms가 됐다. 두 A100의 세 시드에서 워크플로 완료는 0.28~0.91초 빨라졌고 먼저 답하던 사용자의 콘텐츠 간격도 5% 보호 한도 안이었다. 자연어 설명에서 근거 밖의 결론이 남아 이 정책과 새 요청 필드는 실험 단계에 둔다. [정확한 지연·답변 검사](02-prefill-and-reuse.md#긴-도구-결과에만-적용한-시험과-답변-품질)

**최종 답변의 수치 정확성.** Qwen 7B 생성 행의 점수 반올림 한 곳을 바꾼 뒤 A100 두 장에서 72회 교차 시험했다. 9개 입력에서 독립 모델과 전체 생성 토큰 일치는 3→9건, 출처·금액 정답은 3→5건이었다. 기존 정답 한 건을 잃어 공통 설정 승격 기준에 실패했다. [03의 토큰·응답·속도 비교](03-mixed-scheduling.md#최종-답변-토큰이-달라진-위치에서-attention-수치-재현)

**복제본 선택 비용.** 04의 재생 클라이언트가 메시지 이력을 한 번만 읽도록 바꿨다. 두 A100에서 수집한 요청 270건을 복원해 기존과 같은 키·라우팅 점수를 확인했다. 합성 400메시지의 선택 시간 중앙값은 로컬에서 52.35→0.95ms, AWS 서빙 호스트의 단일 CPU 코어에서 207.97→3.18ms로 줄었다. [입력별 비용과 검증 범위](04-replicas-and-tenants.md#이력이-길어질-때-복제본-선택의-cpu-비용)

**서버에 반영한 요청 준비 개선.** 같은 프롬프트를 만드는 과정에서 도구 스키마·메시지 복사를 줄였다. AWS CPU에서 도구 32개 중 하나를 지정할 때 준비 시간은 443→199µs였다. Qwen 7B의 A100 정상 응답 336개에서 토큰·도구 결과를 보존했다. 두 GPU의 전체 HTTP 완료 중앙값은 개선 방향이 달랐다. [서버 변경과 측정 범위](02-prefill-and-reuse.md#채팅-프롬프트-준비-중-도구-스키마-복사-제거)

**다른 라우터가 GPU를 채웠을 때.** 한 호스트의 A100 두 장에서 8개 GPU 슬롯과 8개 HTTP 워커가 모두 스트리밍에 쓰이면 부하 조회도 밀렸다. HTTP 워커를 하나 늘린 실험 바이너리에서 외부 활성 8개를 확인하고 유휴 복제본으로 보내자 5,745토큰 후속 요청의 첫 콘텐츠가 두 비교 모두 약 2.10초에서 0.46초로 줄었다. 다른 사용자의 콘텐츠 간격 p95는 등록한 5% 한도 안이었다. 같은 9개 워커에서 두 라우터가 에이전트 작업 32개를 실행했을 때 상태 조회를 켜면 두 입력군의 목표 충족 처리량은 각각 1.7%, 2.1% 낮았다. 일반 혼합 부하의 기본값은 유지한다. [포화 재현과 실험 바이너리 비교](04-replicas-and-tenants.md#서로-다른-클라이언트가-한-복제본을-채울-때)

**포화 우회와 기존 답변 보호.** 외부 호출 64개가 한 복제본에 도착하면 캐시가 있어도 후속 요청의 첫 콘텐츠까지 약 9.5초가 걸렸다. 다른 GPU에서 즉시 재계산하면 약 0.49초였지만 그곳에서 진행 중인 답변의 콘텐츠 간격 p95가 약 11.9→21.6ms로 늘었다. 대안 GPU의 부하를 지켜보며 최대 1.5초 보류하는 재생 정책은 라우터 대기를 포함해 약 1.61초에 첫 콘텐츠를 보내면서 상대의 간격을 약 11.9ms로 유지했다. 5,745토큰 입력에서 한 토큰을 생성한 결과다. 실제 도구를 두 번 호출하고 자연 종료한 별도 작업에서도 16개 외부 도착에서 완료가 9.22→5.73초, 9.38→5.86초로 줄었다. 160개 도착에서 기존 정책은 두 건 모두 최종 호출을 거절당했고 후보는 둘 다 끝까지 전달했다. [자연 종료 결과와 설명 품질](03-mixed-scheduling.md#과부하-중-도구가-돌아올-때-자연-종료한-최종-답변) · [두 GPU의 여덟 짝 비교](04-replicas-and-tenants.md#부하-표본이-만료됐고-다른-gpu에서-사용자가-이미-답변을-읽을-때)

**실험의 지연 목표.** 01의 Qwen 7B 합성 연쇄는 사용자가 요청한 시점부터 최종 답변의 첫 콘텐츠까지 10초, 마지막까지 18초, 최종 콘텐츠 도착 간격 p95는 150ms로 사전 등록했다. 같은 입력과 출력 길이의 decode 비교는 Riley/vLLM 지연 비율 상한을 1.00으로 정했다. Coder-14B의 RAG 첫 콘텐츠 p95는 별도 부하에서 1.15배 이내가 목표다. 고객 서비스의 절대 지연과 피크 도착률은 운영 트레이스로 정해야 한다. **결과 기록.** 각 단계에 날짜, 소스·바이너리·모델 해시, 하드웨어와 부하, 입력과 시각표 지문, 원본 위치, 대조·후보 값, 제외한 실행과 이유, 판정(통과/보류/기각)을 남긴다. 같은 GPU에서 실행 순서를 바꾸고 기준끼리도 반복한다. 신뢰구간은 독립 실행 단위로 산출하며 변동이 효과보다 크면 보류한다. 먼저 합성 연쇄로 인과관계를 검증하고 운영 결론에는 대표성이 확인된 익명화 트레이스를 사용한다.

**첫 교차 실험.** 같은 A100에서 캐시 끔→켬→켬→끔 순으로 새 서버를 사용해 20개 작업·60개 호출을 완료했다. 네 실행 모두 한 세션이 최종 답변을 받던 중 다른 세션의 긴 도구 결과가 실제 제출됐다. 보존된 입력과 Riley 토크나이저로 적중 가능량을 검산했다. 보류 시드에서 넓은 순수 prefill 후보는 긴 이력의 최종 답변 시작 p95를 약 6%, 완료 p95를 약 2.5% 줄였다. 기준 Riley는 동일 길이 decode에서 vLLM과 경쟁했으나, 긴 이력의 자연 종료 작업에서는 최종 답변이 약 0.54초 늦게 끝났다. 도구 대기 실험 두 쌍에서는 500ms 동안 2,880토큰을 추가 재사용해 완료가 177·183ms 빨라졌고, 대기가 0이면 124·116ms 늦어졌다. 조건부 적용 보류 시드 36개 작업이 유효했고, 상대가 스트리밍하는 긴 대기에서 최종 완료가 184~263ms 단축됐다. ## 실험 설계에 참고한 공개 연구

InferCept는 외부 도구로 생성이 멈춘 동안 KV를 보존·교체·재계산하는 선택의 비용을 다룬다. Riley에서는 대기 중 다음 턴의 템플릿이 바뀌어 실제로 사라지는 prefix와 그 준비 비용을 측정했다. Agentix는 여러 모델 호출로 이어진 프로그램의 실행 이력을 스케줄러에 전달한다.
