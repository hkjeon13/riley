# 03. 긴 prefill과 최종 답변 decode의 동시 처리

[전체 이정표](README.md) · 선행 [이력 재사용과 신규 prefill](02-prefill-and-reuse.md) · 다음 [복제본과 테넌트](04-replicas-and-tenants.md)

**시작 조건.** 단일 GPU 기준선과 각 턴의 신규 입력 비용이 있어야 한다. 모델 한 개를 한 GPU에서 서비스하며, 한 세션의 긴 도구 결과가 다른 세션의 최종 답변과 겹치는 구간을 대상으로 한다.

1. **멈춘 요청을 스텝에 연결한다.** 요청별 decode 미배정, 배정됐으나 긴 혼합 스텝이 끝나기를 기다린 경우, GPU 결과가 준비된 후 SSE 전달이 늦은 경우를 나눈다. 기존 RAG 기록은 추적한 꼬리 요청에서 혼합 스텝 노출을 확인했고, 기존 스텝 순서를 고정한 projection 개선에는 상한이 있었다. 워크플로 연쇄에서도 같은 현상이 있는지 첫 단계에서 검증한다. [혼합 스텝 분석](../../benchmarks/evidence/20261124-w3-pure-prefill-window/verified.json) · [projection 개선 상한](../../benchmarks/evidence/20261124-w3-wide-projection-profile/verified.json)
2. **이전 선택이 다음 스텝을 바꾸는 리플레이를 만든다.** 기존 고정 스텝 재생을 출발점으로 삼는다. prefill이 끝난 요청은 다음 스텝의 활성 decode에 추가하고, 요청이 완료되면 제거한다. 새 prefill 행 수·활성 decode 수·KV 길이별 스텝 시간을 02에서 얻은 값으로 예측한다. 기존 정책·접수 순서·같이 입장한 요청의 순환 정책을 재생해 보류 시드에서 개선과 회귀 방향을 확인한다. 짧은 트레이스에서는 미래를 아는 이상적 배정으로 최대 이득도 추정한다. [기존 재생기](../../benchmarks/evidence/20261124-w3-prefill-deadline-capacity/verify.py) · [순환 정책 실측](../../benchmarks/evidence/20261124-w3-prefill-cohort/gpu-verified.json)
3. **후보는 한 가지 결정만 바꾼다.** 다음 결과를 늦출 수 있는 시간 안에서 처리할 prefill 양을 고른다. 활성 스트림의 마지막 토큰 이후 경과시간, 다음 스텝 비용, prefill을 끝낼 때 새로 생기는 decode 부하를 함께 본다. 오래 대기한 prefill의 진행을 보장하고 후보에서 늘어난 대기도 요청별로 기록한다. 출력 전달 단계가 원인이라면 전송 경로를 우선한다. [스케줄러의 실행 계획](../../crates/riley-scheduler/src/scheduler.rs)
4. **후보를 고정한 뒤 경쟁 비교를 한다.** Riley 기존·후보를 같은 바이너리의 스위치로 비교할 수 있으면 실행 순서를 반대로 반복한다. vLLM은 실제 버전·실행 옵션과 모델 파일을 고정하고 양쪽 모두 동일한 캐시 기회와 메모리 예산을 갖게 한다. 실제 출력 길이·종료 사유를 확인해 길이가 다른 응답의 decode 값을 단순 비교하지 않는다. 도착 부하를 맞춘 진단과 선행 응답에 따라 후속 요청이 발생하는 종단 연쇄를 각각 측정한다.

**산출물과 통과.** 현재 Riley 대비 최종 답변 시작·완료 p95 개선, 정확한 도구 호출과 최종 답변, 등록한 vLLM decode 동등성 기준을 함께 만족해야 새 정책을 채택한다. 첫 토큰을 늦게 발행해 간격만 좁히는 효과는 최초 요청 기준 절대시간으로 식별한다. 기존 짧은 C32와 긴 RAG도 회귀 확인에 포함한다. 리플레이 오차가 후보 간 차이보다 크면 실측으로 되돌린다. 단일 GPU의 달성 한계가 확인되면 해당 부하와 상한을 기록하고, 이후 복제본 구성과 같은 총 GPU 예산으로 prefill/decode 분리도 비교할 수 있다.

## 현재 실행과 판정 범위

네 세션 실험에서는 한 사용자의 최종 답변 첫 콘텐츠가 도착하면 나머지 세 세션이 각각 이미 받은 도구 결과를 제출한다. 128·256·512·1,024행에서 훈련 시드 101·111과 보류 시드 761을 분리했다. 비용 모형은 스텝의 prefill 행 수·동시 decode 수·문맥과 관측 시간을 사용하며, prefill이 끝난 세션은 다음 스텝부터 decode로 전환한다. 256행 첫 실행에서 보류 시드 네 답변은 정상이고 훈련 시드 101의 한 답변이 결과 검사를 실패했다. 해당 실패를 원본에 유지한다. 512행 첫 기동은 기본 형상 목록의 마지막 값이 256인 탓에 CLI가 거부했다. 너비에 맞춰 목록을 생성하도록 수정해 재시험했다. [측정 등록](../../benchmarks/evidence/20261124-agentic-serving/cohort-registration.json) · [리플레이](../../benchmarks/evidence/20261124-agentic-serving/replay_cohort.py)

첫 vLLM 0.27.1+cu129 실행에서는 이름을 지정한 도구 호출 완료 사유로 `stop`을 반환했다. 완료 사유와 실제 도구 페이로드를 각각 기록하고, 정확히 하나의 유효한 호출인지 검사하도록 드라이버를 수정했다. 이후 두 엔진이 같은 최종 요청을 받아도 기본 템플릿 옵션 때문에 vLLM 입력이 218토큰 길었다. 이 실행으로 decode 동등성을 판정할 수 없다. 후속 비교에는 vLLM의 `--exclude-tools-when-tool-choice-none`을 적용한다. 자연 종료 워크플로와 별도로, 기존 Riley 실측에서 재구성한 동일 최종 요청·64토큰·200ms 간격의 고정 부하로 decode 범위를 맞춘다. [비교 조건 등록](../../benchmarks/evidence/20261124-agentic-serving/aligned-registration.json)

### 동일 입력·출력 길이에서 측정한 최종 답변 속도

A100 6번, Qwen2.5-7B-Instruct BF16, 보류 시드 761에서 256행 Riley 기준과 vLLM을 두 번씩 새로 기동했다. 네 최종 요청의 입력 토큰 ID 전체 해시는 두 엔진에서 일치했고 입력 길이는 306·2,546·3,072·5,312였다. 각 엔진에서 두 스트림이 겹치는 고정 부하를 이력 길이별로 세 번 반복했다. 모든 측정 스트림은 64개의 토큰을 생성했다. 별도로 자연 종료까지 실행한 40개 워크플로는 도구 호출·최종 답변 검사를 통과했다.

| Riley 기준 / vLLM | 두 교차 비교의 네 조건에서 관측한 비율 범위 |
|---|---:|
| 최종 답변의 토큰당 시간 중앙값 | 0.981–0.994 |
| 최종 가시 콘텐츠 도착 간격 p95 | 0.967–0.988 |

긴 이력 두 요청의 64개 생성 토큰 ID는 엔진 간 달랐다. 추가 이력이 없는 두 요청에서는 일치했다. 각 비교에 독립 서버 기동이 두 쌍이므로 모집단의 신뢰상한은 아직 확정하지 않는다. 추후 승격에는 넓은 순수 prefill 후보의 고정 decode 대조와 보호 워크로드 검증도 포함한다. ### 네 최종 답변이 동시에 진행될 때의 선택

시드 761에서 네 답변 모두 정확성 검사를 통과했다. 아래 시간은 첫 세션의 최종 prefill이 GPU에서 시작된 순간을 원점으로 삼아, 네 세션 중 마지막이 해당 지점에 도달할 때까지의 실측이다. 각 행은 한 번의 동시 도착 실험이다. 일정한 행 수를 항상 허용하는 탐색 조건으로, 순수 prefill만 넓히는 02의 후보와 구성이 다르다.

| 허용 행 수 | 마지막 세션의 첫 토큰 생성 | 네 답변 모두 생성 완료 |
|---:|---:|---:|
| 128 | 895ms | 3,036ms |
| 256 | 589ms | 2,711ms |
| 512 | 556ms | 2,728ms |
| 1,024 | 516ms | 2,725ms |

256행에서 1,024행으로 늘렸을 때 마지막 세션의 생성 시작이 73ms 빨라졌고 마지막 완료는 14ms 늦어졌다. 보류 시드의 기준 정책 재생 오차는 완료 시각 기준 최대 약 97ms여서 256·512·1,024 사이의 완료 시간 차이보다 크다. 이 데이터로 혼합 스텝의 일괄 확대나 30ms 마감 정책을 채택하지 않는다. 학습용 두 시드에서 GPU 스텝 1,834개를 사용했다. 시드 101의 네 작업 중 하나가 모든 너비에서 결과 검사를 실패했고, 111과 761은 모두 통과했다. 128행 첫 기동이 기본 plateau 경계 128·192 때문에 거부돼 경계를 64·96으로 지정했다. 이 시험의 동시 세션 수는 해당 정책의 최소 decode 행 수보다 작다. [원본](../../benchmarks/evidence/20261124-agentic-serving/cohort-raw.tar.gz) · [인과 재생 결과](../../benchmarks/evidence/20261124-agentic-serving/cohort-verified.json)

다음 실측은 02의 순수 prefill 후보를 대상으로 한다. 같은 GPU의 vLLM과 다섯 쌍의 독립 기동을 등록하고, 별도 GPU에서 기존 Coder-14B 짧은 C32·긴 RAG의 입력과 도착 시각을 재생한다. 측정 시작 전에 표본 수와 허용 폭을 고정했다. [후보 판정 조건](../../benchmarks/evidence/20261124-agentic-serving/promotion-registration.json)

### 사용자가 최종 답변을 다 받을 때까지

자연 종료 워크플로의 긴 이력 조건에서 기준 Riley의 최종 답변 시작 p95는 1,670·1,671ms, 완료 p95는 3,917·3,912ms였다. 같은 두 쌍의 vLLM 값은 시작 1,507·1,512ms, 완료 3,369·3,374ms였다. 첫 비교의 가장 느린 작업에서 Riley는 185개, vLLM은 153개 토큰을 생성했고 해당 최종 요청 제출부터 가시 콘텐츠 시작까지도 448ms와 377ms로 차이가 났다. 이 사례에서 전체 완료 지연을 설명하려면 입력 재처리와 실제 답변 길이를 모두 봐야 한다. 최종 요청의 동일 길이 진단과 자연 종료 결과를 함께 유지한다. [자연 종료 원본](../../benchmarks/evidence/20261124-agentic-serving/aligned-raw.tar.gz)

### 기존 Coder-14B 짧은 요청과 긴 RAG 보호 시험

동일한 A100 7번에서 256행 기준→순수 prefill 확대→확대→기준 순서로 기동했다. 매회 보존한 RAG 입력 64개와 C32 입력 192개의 실제 도착 시각표를 재생했다. 1,024개 요청이 완료됐고, 같은 입력의 기준·후보 출력 해시는 모든 쌍에서 같았다.

| 조건 | 첫 교차 비교 | 역순 비교 |
|---|---:|---:|
| 긴 RAG 시작 p95, 기준 → 후보 | 2,517 → 2,580ms | 2,505 → 2,531ms |
| 후보 RAG 시작 p95 / 보존된 동일 시각표의 vLLM | 2.121배 | 2.081배 |
| C32 토큰당 시간 중앙값, 후보 / 기준 | 0.999배 | 1.000배 |
| C32 출력 처리량, 후보 / 기준 | 0.999배 | 1.001배 |

기존 RAG의 1.15배 목표를 통과하지 못했다. C32의 등록된 성능 허용 폭은 두 쌍 모두 충족했으나 첫 기준 실행의 도착 오차 p95는 허용 3ms를 넘어 3.036ms였다. 역순 쌍의 도착 오차는 양쪽 모두 허용 범위였다. 순수 prefill 확대는 7B 도구 연쇄에서 보인 이득만으로 공통 서빙 프로파일에 승격할 수 없다. [보호 부하 원본](../../benchmarks/evidence/20261124-agentic-serving/protected-raw.tar.gz) · [검산 결과](../../benchmarks/evidence/20261124-agentic-serving/protected-verified.json)

### Qwen 7B 후보와 vLLM의 다섯 기동 쌍

같은 A100에서 순서를 바꿔 10번 기동했다. 같은 입력 토큰과 64토큰 출력 조건에서 네 셀 전체의 Riley/vLLM TPOT 비율은 0.980~0.995, 콘텐츠 간격 p95 비율은 0.963~0.989였다. 쌍마다 두 지표·네 셀의 최댓값을 취하고 그 다섯 값의 최댓값을 구한 결과는 0.99544였다. 독립·동일 분포 기동을 가정한 최악 셀 중앙값의 단측 96.875% 상한이 사전 기준 1.00을 충족한다. 같은 장치에서 순차 실행한 범위이고, 긴 이력에서는 두 엔진의 출력 토큰 ID에 차이가 있었다.

자연 종료한 긴 이력 작업은 각 서버 기동에서 5개 모두 유효했다. 다섯 기동의 최종 완료 p95는 Riley 3.809~3.816초, vLLM 3.369~3.373초였다. 따라서 이 후보는 7B 동일 길이 decode 시험을 통과했고, 사용자가 끝까지 받는 시간에는 여전히 약 0.44초 차이가 있다. [사전 기준](../../benchmarks/evidence/20261124-agentic-serving/promotion-registration.json) · [원본에서 재집계한 결과](../../benchmarks/evidence/20261124-agentic-serving/promotion-decode-verified.json)

자연 종료 시험의 자동 유효 판정은 도구 이름·인자, 수치 세 개, 출처 두 개를 확인한다. 답변 본문도 읽어 보니 Riley가 p95 차이를 요청별 평균 개선으로 해석한 답변이 있었고, vLLM에도 요청의 95%가 정확히 해당 지연이었다고 해석한 답변이 있었다. 두 문장을 원본에서 검색한 수치는 중복 입력을 포함하며, 인용 지시 시험과 별개로 해석의 정확성을 평가할 필요가 있다. 이 실행의 유효 건수는 자동 검사 항목에 한정한다. ### 최종 답변의 생성 스텝을 줄일 여지

Riley가 실제 생성한 토큰 ID를 고정하고, 요청의 입력과 이미 확정된 출력 안에서 최근에 나온 같은 토큰열을 찾아 최대 4개를 제안하는 규칙을 검사했다. 다음 정답을 미리 본 뒤 제안을 고르는 방식은 허용하지 않았다. 일치한 제안만 채택하고 첫 불일치는 타깃 모델의 토큰으로 교체하는 가정이다. 입력·출력 토큰 지문이 확인된 네 가지 64토큰 조건에서 필요한 타깃 패스는 45~58회였다. 긴 이력과 긴 도구 결과가 함께 있는 셀은 64회에서 45회로 줄었다. GPU에서 여러 위치의 logits를 계산하고 불일치 KV를 되돌리는 비용은 아직 포함하지 않았다. 실제 생성 속도는 이 수치로 판정할 수 없다. 보류 시드의 자연 종료 답변에도 같은 제안 규칙을 적용한다. [제안 규칙과 표본 등록](../../benchmarks/evidence/20261124-agentic-serving/lookup-decode-registration.json) · [토큰 재생 결과](../../benchmarks/evidence/20261124-agentic-serving/lookup-fixed-verified.json)

여러 후보 토큰을 타깃 모델에서 검증하는 아이디어는 Lookahead Decoding과 REST 연구를 참고했다. 여기서 시험한 규칙은 같은 요청 안에서 이미 본 토큰만 사용한다. [Lookahead Decoding, ICML](https://proceedings.mlr.press/v235/fu24a.html) · [REST, NAACL](https://aclanthology.org/2024.naacl-long.88/)

8개 보류 시드에서 모델이 자연 종료할 때까지 원래 생성 토큰 ID를 수집했다. 첫 토큰을 고정한 뒤 나머지 ID를 재생하면 17.0~23.4%의 타깃 패스를 줄일 여지가 있었다. 각 패스가 기존 한 토큰과 같은 비용이라는 가정에서 가능한 단축은 약 0.27~0.44초다. 8개 중 7개가 기존 응답 검사를 통과했다. 이 결과는 GPU의 후보 검증 시간이 0이라는 가정에도 약 0.44초의 격차를 일관되게 메우기 어렵다는 뜻이다. 향후 다중 위치 검증의 실제 비용과 KV 롤백을 측정하기 전에는 서빙 기본값으로 추가하지 않는다. [보류 시드별 계산](../../benchmarks/evidence/20261124-agentic-serving/lookup-natural-verified.json)

Coder-14B 보호 시험에는 다른 원인이 작용한다. 실제 입력 해시와 네이티브 토큰 길이가 일치하는 RAG 64개를 재구성했다. 이전·미래 요청과 워밍업까지 모두 볼 수 있고 퇴출도 없다고 가정해도, 공통 16토큰 블록의 상한은 전체 174,144토큰 중 1,056개(0.61%)였다. 어떤 RAG 요청에서도 최대 32토큰이다. 같은 계산으로 짧은 C32에서는 13,917개 중 6,144개(44.15%)였다. RAG의 신규 입력에는 에이전트 연속 턴에서 확인한 캐시 개선폭을 적용할 수 없다. 이 부하는 신규 입력을 처리하는 GPU 실행 비용과 스케줄링을 별도로 개선해야 한다. [보호 입력별 상한 검산](../../benchmarks/evidence/20261124-agentic-serving/rag-reuse-verified.json)

Coder-14B의 다음 실행기 후보에는 목표 개선폭을 먼저 정했다. 이전 진단 기동에서 복원한 도착 시각표 두 개(각 64요청)를 그대로 두고, 요청마다 실제로 prefill이 실행된 시간만 일정 비율로 줄여 p95를 다시 계산했다. 자기 입력을 포함하는 스텝만 줄이면 두 시드에서 51.4%와 42.7%를 회수해야 1.15배 목표에 닿는다. 앞선 다른 사용자의 prefill까지 같은 비율로 빨라지면 필요한 단축은 각각 23.4%와 19.6%다. 더 늦게 도착한 요청만 앞세우지 않는다고 가정한 최선의 경우도 첫 시드에서 목표에 닿지 않았다. 이 계산은 배치 순서와 대기열을 고정한 민감도 분석이다. 다음 Coder 후보는 혼합 1,024행 스텝의 전체 실행을 적어도 약 20~24% 줄일 가능성이 있는지 먼저 재고, 통과하면 원래 도착 시각과 C32 스트리밍을 함께 재생한다. ### Coder-14B에서 스트리밍 여유를 긴 입력에 재배분한 결과

짧은 답변과 긴 RAG를 같은 두 GPU에 분산한 채로, 512토큰 이상의 긴 입력이 있고 decode 행이 8개 이하일 때만 최대 512행까지 prefill을 허용했다. 나머지 스텝은 기존 256행을 유지했다. 두 측정 구간의 각 복제본에서 실제 512행 실행이 각각 127~141회 발생했다. 혼합 요청 512개와 별도로 한 GPU씩 시험한 보호 요청 512개 모두 기존 Riley 응답 해시·길이·종료 사유와 일치했다.

* **두 GPU 혼합 부하.** 긴 요청의 첫 콘텐츠 p95가 1.002→0.940초, 1.003→0.967초로 6.2%와 3.6% 줄었다. 긴 요청의 스트림 간격은 약 43→71ms로 늘었고 짧은 답변 완료 p95는 2.51~2.52초를 유지했다. 긴 요청의 첫 콘텐츠는 vLLM의 1.168·1.175배로 목표 1.15배를 넘었다. 두 번째 비교는 앞서 기록한 vLLM 제출 오차도 초과했다.
* **기존 단일 GPU 보호 부하.** 같은 GPU7·도착 시각표에서 긴 RAG 첫 콘텐츠 p95는 1.914초, 보존한 vLLM은 1.216초로 1.573배였다. 같은 장치의 기존 256행 C32 두 실행과 비교하면 출력 처리량과 TPOT 중앙값은 0.2% 이내였고, 짧은 요청의 첫 콘텐츠 중앙값은 한 실행 대비 2.32% 느렸다. GPU6은 별도 실행에서 RAG p95 1.947초를 기록했고 같은 장치의 vLLM 기준은 이 기록에 없다.

이 후보는 공통 기본값에 반영하지 않았다. 비교 가능한 첫 쌍에서 1.15배까지 남은 차이는 약 15ms였지만, 기존 단일 GPU 보호 시험에서는 약 515ms가 남는다. 두 GPU 혼합 부하의 근접 결과를 단일 GPU 목표 달성으로 환산할 수 없다. ### 최종 답변 토큰이 달라진 위치에서 attention 수치 재현

Qwen2.5-7B BF16의 두 조회를 골라 마지막 prefill과 최초로 생성 토큰이 달라진 decode에서 28개 레이어를 기록했다. 서버에 실제로 들어간 토큰과 위치, 로그잇 최댓값과 실제로 전송한 토큰, 계측 전후 전체 응답을 대조했다. 첫 번째 레이어의 임베딩·입력 정규화·RoPE query가 같은데도 decode의 attention 출력은 두 경로 간 상대 L2가 49.49%, 6.46%였다. ### 자연 종료의 0.44초 차이가 발생한 구간

같은 A100에서 진행한 다섯 쌍의 원본에서 작업별 최초 제출, 최종 요청 제출, 첫·마지막 가시 콘텐츠 시각을 맞췄다. 긴 이력의 다섯 작업 중 Riley는 네 작업에서 먼저 끝났다. Riley가 늦은 작업은 다른 사용자가 이미 답을 읽는 동안 96쌍의 관측을 담은 도구 결과가 돌아온 경우였다. 다섯 기동 쌍의 중앙값으로 보면 최종 호출 제출까지 Riley가 8.3ms 빨랐고, 최종 호출의 첫 콘텐츠가 나오기까지 72.1ms 더 걸렸으며, 이후 마지막 콘텐츠까지 375.8ms 더 걸렸다. 전체 차이는 441.2ms였다.

이 요청은 Riley 185토큰, vLLM 153토큰이었다. 각 쌍에서 가시 스트리밍 시간을 `(완료 토큰 수 − 1) × 가시 TPOT`로 나타내고 두 엔진 평균으로 대칭 분해했다. 긴 출력의 기여는 +390.8ms, 토큰당 시간의 기여는 −15.0ms였다. 이는 관측된 합계의 분해다. 입력 표현을 바꾸면 생성하는 내용과 길이도 바뀌므로 prefill만으로 441ms를 회수할 수 있다고 추정할 수 없다. [다섯 쌍·50개 작업별 비교](../../benchmarks/evidence/20261124-agentic-serving/natural-final-decomposition.json)

도구 설명 표시를 양쪽 모두 유지한 별도 실제 시험에서 같은 시드 761의 최종 입력 토큰 지문이 Riley와 vLLM에서 일치했다. 두 A100에서 Riley의 최종 요청 첫 콘텐츠 대기는 21~23ms 더 길었고, 선행 턴은 19~22ms 빨랐다. 이후 마지막 콘텐츠까지 Riley가 264·350ms 더 걸렸다. ### 과부하 중 도구가 돌아올 때 자연 종료한 최종 답변

Qwen 7B의 200항목 이력에서 에이전트가 `list_reports`와 `read_reports`를 차례로 호출했다. 두 번째 도구가 계산하는 동안 이미 확정된 이력으로 한 토큰을 미리 생성했고, 그 비용을 작업 시간에 포함했다. 다른 에이전트가 반대 GPU에서 답변을 읽고 기존 GPU에는 스트림 8개가 진행 중일 때, 외부 요청 16개 또는 160개를 보냈다. 650ms 후 실제 도구 결과를 공개하고 최종 요청을 라우팅했다. GPU 두 장을 새로 기동해 시드별 정책을 바꿨다. 실험 기록에서 동적으로 생성한 도구 호출 ID까지 복원했고 해당 ID만 정규화한 최종 입력이 짝마다 같았다. [사전 기준](../../benchmarks/evidence/20261124-agentic-serving/natural-burst-registration.json)

### Qwen2.5-3B와 Coder-7B의 동일 길이 최종 decode

한 호스트의 A100 6번에 Qwen2.5-3B-Instruct, 7번에 Qwen2.5-Coder-7B-Instruct를 고정했다. 각 모델에서 동일 가중치·토크나이저를 쓰는 Riley와 vLLM을 순서를 바꿔 두 번씩 기동했다. 이전 7B 연구에서 실제 제출한 최종 요청 네 개를 그대로 재생했다. 짧거나 긴 이력에서 먼저 도착한 사용자와 200ms 뒤 긴 도구 결과를 받은 사용자가 동시에 답을 읽는 조건이다. 각 기동에서 먼저 네 요청의 입력·생성 토큰 ID를 수집하고 이후 응답에 ID를 싣지 않는 시간 측정에서 셀당 세 번씩 두 요청을 재생했다. 정해진 64토큰 진단과 별도로 각 기동에서 실제 도구 두 번과 자연 종료 최종 답변을 두 시드로 검사했다. [모델·부하·판정 등록](../../benchmarks/evidence/20261124-agentic-serving/model-decode-registration.json)

기존 7B 시험에 사용한 컨테이너 이미지가 호스트에서 사라져 첫 3B 기동이 모델 실행 전에 실패했다. 두 모델의 모든 측정에 앞서 검산한 동일 네이티브 Riley 바이너리(`13b589df…`)를 사용했다. Coder-7B의 첫 네이티브 기동은 4,932,751,008바이트 가중치 샤드가 기본 한도를 넘어 실패했다. 해당 모델에는 64GiB 읽기 한도를 명시하고 같은 샤드를 다시 열었다. 양쪽 모델의 모든 측정 기동은 8,192토큰 문맥, 8슬롯, 해당 모델의 KV 블록 4,096개에 해당하는 메모리를 사용하도록 구성했다. 실제 요청별 적중 수도 검사했다. [바이너리 변경 기록](../../benchmarks/evidence/20261124-agentic-serving/model-decode-native-amendment.json)

실험 바이너리에서 `native-bf16-varlen-v1`은 실행 로그에 `fixed-tile-unsplit-v1`을 남겼다. 현재 작업 트리에서도 `native-bf16-varlen-v1`은 fixed-tile, `native-bf16-v1`은 page를 선택한다. 최초 후속 등록의 기본값 설명에 오류가 있어 정정했다. 실행 경로별 영향을 보기 위해 두 교차 기동에 쓴 바이너리에서 attention 모드만 명시적으로 바꾸고 동일 요청을 다시 보냈다. 이 추가 Riley 기동은 모델당 1회이며 새로운 vLLM 기동과 짝짓지 않았다. vLLM 버전은 `0.27.1+cu129`였다. 모델당 4개 셀 × 두 기동 쌍에서 제출 본문과 렌더링한 입력 토큰이 일치했고, 각 시간 측정의 따뜻한 캐시 적중 수도 같았다. 도착 오차 최댓값은 0.39ms 미만이었다. 두 모델 모두 등록된 단기 decode 비교를 통과했다. 종전 7B 연구에서 요구한 5쌍의 독립 기동 기준이나 같은 생성 결과에 대한 보장은 별도다. 자연 종료 시험 16개(Riley 8개·vLLM 8개)는 모두 두 도구의 정확한 인자, 최종 수치·출처·자연 종료를 확인했다. 3B의 긴 결과에서는 Riley가 두 번 모두 176토큰, vLLM은 136토큰을 생성했다. Riley의 완료는 1.794·1.799초, vLLM은 1.654·1.652초였다. Coder-7B의 같은 입력은 Riley가 114토큰을 생성해 2.456·2.458초, vLLM이 108토큰을 생성해 2.470·2.465초였다. 최종 완료 시간은 모델당 두 시드에서 관측한 값이다.

**독립 토큰 대조.** 같은 가중치로 Transformers 5.22.1, BF16, SDPA, greedy 캐시 생성을 실행했다. 모델별 네 요청 모두 체크포인트의 채팅 템플릿으로 렌더링한 토큰 해시와 길이가 양쪽 서버와 같았다. 3B에서 Riley와 vLLM은 20~37토큰까지 같았고, 두 출력이 처음 갈라진 공통 이력을 다시 forward했을 때 최고 점수 토큰은 Riley 쪽 2개, vLLM 쪽 2개였다. Coder-7B에서는 1개 입력의 양쪽 64토큰 전체가 일치했다. 나머지 3개의 첫 분기에서는 전체 이력 재계산이 모두 vLLM 쪽 토큰을 가장 높게 평가했다. 독립 모델 자체가 이미 앞선 위치에서 다른 경로를 고른 경우도 있다. 실제 greedy 경로와 공통 이력에서의 점수는 각각 기록했다. [첫 분기와 독립 생성 결과](../../benchmarks/evidence/20261124-agentic-serving/model-decode-reference-verified.json)

**같은 바이너리에서 page 모드만 바꾼 대조.** vLLM과 64개 생성 ID가 전부 일치한 입력은 3B에서 fixed-tile 0/4 → page 1/4, Coder-7B에서 1/4 → 2/4였다. 독립 Transformers와 전체 64토큰이 같은 입력은 두 모드·두 모델에서 모두 0/4였다. page의 TPOT 비율 최댓값은 앞서 기동한 두 vLLM 서버와 비교해 3B 1.037, Coder-7B 1.027이었다. 이 단일 기동으로 page가 모든 셀에서 decode 동등성을 달성했다고 판정할 수 없다.

긴 결과가 돌아온 자연 종료 시드 762에서 3B의 최종 제출→첫 콘텐츠는 fixed-tile 첫 기동 98ms, page 269ms였다. 첫 콘텐츠 이후 스트리밍은 1,159→915ms로 짧아졌지만, 제출 전 단계와 첫 콘텐츠 지연을 포함한 전체 완료는 1.794→1.761초로만 줄었다. ### 최종 요청 도착 시 진행 중인 prefix 준비를 취소한 결과

배포 설정의 8개 슬롯, 1,024토큰 청크, KV 풀 4,096블록과 prefix 캐시 1,536블록을 적용한 실제 Riley 스케줄러로 이전 카탈로그 입력을 재생했다. GPU 실행 결과는 요청당 합성 토큰 하나로 고정했고, 각 스텝이 실제로 배정한 prefill 토큰 수와 완료 요청의 캐시 적중 수를 대조했다. 매 부하를 빈 캐시로 시작했다. 준비량 제한 후보는 1,024블록을 해당 부하의 긴 작업 수로 나누고 나머지 512블록을 남긴다. 전체 준비 입력이 몫을 넘으면 첫 이력 메시지 앞부분만 담은 유효한 채팅 요청 중 토큰 예산에 들어오는 것을 사용한다. 실제 최종 요청은 항상 원문 전체다. [준비 정책·도착 순서 등록](../../benchmarks/evidence/20261124-agentic-serving/first-tool-schedule-registration.json)

| 긴 작업 12개·짧은 독자 4개, 준비를 완료한 뒤 원래 순서로 최종 요청 제출 | 최종 prefill 행 | 준비 포함 총 prefill 행 | 가장 많이 다시 읽은 긴 작업 |
|---|---:|---:|---:|
| 준비 없음 | 34,959~34,966 | 34,959~34,966 | 3,071~3,074 |
| 전체 이력 준비 | 11,766~11,791 | 40,872~40,890 | 3,039~3,041 |
| 준비량 제한 | 19,183~19,190 | 32,235~32,242 | 1,746 |

전체 이력을 준비하면 최종 요청에 남는 총량이 가장 적었지만 캐시에서 밀려난 개별 사용자는 이력 대부분을 다시 읽었다. 준비량 제한은 그 최댓값과 총 계산량을 함께 줄였다. 최종 도착 순서를 뒤집으면 준비량 제한의 총량은 32,235~32,242행, 준비 없는 기준은 32,175~32,182행이었다. 총량의 우위는 도착 순서에 따라 바뀐다.

준비가 끝나기 전에 실제 결과가 도착하는 경우도 재생했다. 16개 도착에서 같은 전체 준비 요청을 보낸 뒤 **8회 반복이 끝난 경계**에 실제 요청을 제출했다. 남은 준비 12개를 계속 진행하면 최종 요청이 10,486~10,511행, 준비 포함 총 39,592~39,610행을 사용했다. 즉시 취소하면 최종 요청은 23,983~23,990행으로 늘지만 총량은 32,175~32,182행으로 줄었다. 두 입력군 모두 최종 요청을 제출한 뒤 마지막 작업 완료가 31→24회, 마지막 짧은 독자 완료가 25→16회였다. 아무 준비 없이 같은 순서로 제출하면 각각 35회와 24회였다. 실행기는 각 반복에 필요한 GPU 시간이 다르므로 이 횟수를 초나 속도 배수로 환산할 수 없다. 0·4·8·16회 경계, 정방향·역방향 결과와 개별 적중은 원본에 남겼다. 재생 클라이언트에서 두 도구를 앱이 직접 결정할 때 `--first-fixed-tool`로 첫 도구 대기부터 준비를 시작하고 `--cancel-on-final`로 남은 준비 연결을 최종 요청 제출 직전에 종료할 수 있다. 이는 전체 prefix 준비와 취소의 HTTP 경로다. 표의 작업별 예산 선택은 스케줄러 재생에서 시험했다. 로컬 HTTP에서 두 도구가 끝난 뒤 준비 연결이 종료되고 별도 최종 요청이 정상 완료되는 것을 확인했다. ## 최종 답변의 GPU 생성과 HTTP 전달 비용

Riley의 일반 채팅 스트림은 각 텍스트 조각을 completion JSON으로 직렬화한 뒤, 이를 파싱해 chat JSON으로 다시 직렬화했다. 직접 경로에서는 이미 검증한 요청 메타데이터와 생성 문자열로 chat SSE 프레임을 한 번 작성한다. 도구 구분자 필터와 스트림 순서 검증은 공유한다. 원시 토큰 ID·logprobs를 요청한 이벤트, 사용량과 종료 이벤트는 기존 인코더를 사용한다. [서버 구현](../../crates/riley-server/src/chat.rs) · [비교 재생기](../../crates/riley-server/examples/chat_stream_replay.rs)

A100 Coder-7B의 원본 출력 토큰에서 64조각씩 네 답변을 복원했다. 복원문이 실제 제출 기록과 같은지 SHA-256으로 대조하고, 각 답변의 모든 SSE 프레임을 바이트 단위로 비교했다. 도구 구분자가 여러 조각에 걸치거나 불완전한 경우 등 세 가지 입력도 일치했다. release 빌드에서 두 경로의 실행 순서를 번갈아 10회 측정했다. Linux 단일 CPU 코어에서 64조각 답변 하나를 직렬화하는 비용을 조각 수로 나눈 값은 **3.41~3.75µs → 0.57~0.59µs**, Mac에서는 **1.89~1.92µs → 0.30~0.31µs**였다. 이 수치에는 해당 스트림의 초기화와 종료·사용량 프레임도 포함된다.

Linux에서는 같은 바이너리로 실제 HTTP 서버와 TCP 클라이언트를 기동했다. 테스트 백엔드가 동일한 64조각을 즉시 공급했다. 클라이언트가 요청을 시작한 시점부터 마지막 텍스트 조각을 읽은 시점까지 측정했다. 기동당 250건, 총 1,000건에서 본문 64조각과 정상 종료·사용량이 일치했다. 각 칸은 두 번의 독립 기동에서 관측한 요청별 p95 범위다.

| 동시 클라이언트 | 기존 마지막 조각 p95 | 직접 직렬화 마지막 조각 p95 |
|---:|---:|---:|
| 1 | 1.03~1.06ms | 0.79~0.82ms |
| 8 | 2.71~2.85ms | 2.28~2.43ms |
| 16 | 4.83~4.96ms | 4.12~4.41ms |

동일 본문의 기존 A100 일반 스트림에서 사용자에게 보인 토큰 간격은 네 입력별 세 번의 중앙값이 **11.88~12.24ms**였다. Linux CPU에서 줄어든 직렬화 비용은 각 입력의 이 간격과 비교하면 **0.023~0.027%**에 해당한다. 이 비율은 별도 시험 간 규모 비교이며 GPU 종단 지연의 실측 개선율은 아니다. 트래픽이 몰리는 HTTP 구간에서는 직접 직렬화를 유지할 근거가 생겼다. 에이전트 완료 시간을 크게 줄이는 우선순위는 긴 도구 반환 후의 대기와 미계산 prefill에 둔다. ## 현재 CUDA 릴리스의 동일 장비 교차 시험 상태

11월 25일 현재 작업 트리를 AWS Linux에서 CUDA 12.4와 SM80 대상으로 다시 빌드했다. 실행 파일 SHA-256은 `40a58069b66b2f76bfe20a0f3decc0bd1b4f7f2e2a3ae80d6fc519dc40690c7e`이다. 동적 라이브러리 연결, CLI 버전, 실행 파일에 포함된 SM80 커널 이미지 15개를 확인했다. 기존 경로로 실험할 때 사용하던 바이너리의 해시도 별도로 유지한다.

이전 vLLM의 시작 실패 당시 기본 예약량은 36.23GiB, 여유 메모리는 31.05GiB였다. 후속 비교는 두 엔진의 KV 예산을 3,758,096,384바이트, 블록을 16토큰, 동시 슬롯을 8, 문맥을 8,192토큰으로 고정하고 vLLM의 시작 예약 비율을 0.92에서 0.75로 조정한다. 설치된 vLLM 0.27.1+cu129의 인자 파서에서 이 구성을 검증했다. 서버가 실제로 그 메모리 안에서 모델을 올리는지와 성능 영향은 기동 후 확인해야 한다.

11월 25일 GPU 6에서 vLLM, GPU 7에서 Riley의 앱 직접 실행을 시작하도록 각각 기존 제어기를 호출했다. 두 장 모두 다른 프로세스가 제어기의 허용 목록에 없어 자식 프로세스 생성 전에 거절됐다. 앞선 세 시험에서도 각 장치를 24회씩 확인한 기록이 있다. 이 실행의 모델 시작·완료는 0건이었다. ## AWS A100의 Coder-7B Riley와 vLLM 교차 결과

11월 26일 AWS A100 4번에서 vLLM→Riley, 5번에서 Riley→vLLM 순으로 새 서버를 기동했다. 체크포인트 리비전, BF16, 8,192토큰 문맥, 동시 슬롯 8개, 16토큰 블록과 KV 65,536토큰을 맞췄다. Riley는 위 SM80 릴리스와 등록된 wide prefill을, vLLM 0.27.1+cu129는 메모리 예약 0.75와 자체 배치 기본값을 썼다. 두 엔진의 GPU 프로세스를 기동부터 종료까지 2초 간격으로 확인했다.

고정 decode는 기동마다 308토큰과 3,071토큰의 동일 입력을 사용했다. 입력 ID 전체 지문을 별도 요청에서 대조했고, 세 번의 측정에서 각 요청이 64토큰을 생성했다. 짧은 입력은 304토큰, 긴 입력은 3,056토큰을 양쪽에서 재사용했다. 두 스트림은 200ms 간격으로 시작해 실제로 겹쳤으며 예정 시각 편차의 최댓값은 3.4ms였다. 긴 입력의 진단 생성 ID 64개는 일치했고 짧은 입력의 생성 ID는 달랐다.

| A100 | 고정 decode TPOT 중앙값, vLLM → Riley | 고정 decode 콘텐츠 간격 p95, vLLM → Riley |
|---|---:|---:|
| 4번 | 49.50~49.59 → 12.17~12.29ms | 99.06~99.16 → 15.02~15.55ms |
| 5번 | 46.08~47.16 → 11.91~11.96ms | 104.94~105.50 → 12.02~12.03ms |

범위는 짧은 입력과 긴 입력의 결과다. Riley/vLLM 비율은 TPOT 0.246~0.260, 콘텐츠 간격 p95 0.114~0.157로 두 장치의 네 조건이 모두 등록 상한 1.05를 통과했다.

자연 종료 워크플로는 네 기동에서 총 176건을 처리했고, 모두 두 도구 호출과 기본 정답 검사를 통과했다. 아래는 기동당 16개씩 두 번 도착한 32건의 결과다. 지연은 최초 예정 도착부터 측정했다.

| A100 | 최종 첫 콘텐츠 p95, vLLM → Riley | 최종 마지막 콘텐츠 p95, vLLM → Riley | 5초·8초·80ms 목표 충족, vLLM → Riley | 목표 충족 작업/GPU·시간, vLLM → Riley |
|---|---:|---:|---:|---:|
| 4번 | 13.24 → 7.81초 | 20.35 → 9.41초 | 0 → 9/32 | 0 → 1,621 |
| 5번 | 12.83 → 7.80초 | 20.79 → 9.49초 | 0 → 11/32 | 0 → 1,989 |

두 장치 모두 등록한 자연 종료 비교 기준을 통과했다. 이 판정의 범위는 고정한 릴리스·엔진 옵션과 카탈로그 부하다. 두 장치의 시험 프로세스와 임시 GPU 예약을 모두 해제했다.
