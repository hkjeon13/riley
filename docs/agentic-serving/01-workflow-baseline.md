**시작 조건과 목적.** 현재 Riley의 단일 GPU 서빙과 기존 도구 호출 API에서 출발한다. 중간 단계의 단축이 최종 답변에 도달하는지 확인할 기준선을 만든다. 첫 기능 검증 모델로 기존 도구 왕복 결과가 있는 Qwen2.5-7B-Instruct를 제안한다. Coder-14B는 기존 성능 현상 재현에 사용하고, 모델 간 절대시간은 따로 보고한다. [도구 호출 실측](../serving-validation.md) · [기존 왕복 검사](../../benchmarks/live/api_check.py)

## 재생할 최소 작업

1. 사용자가 두 문서의 차이와 근거 설명을 요청한다. 모델이 문서 목록 조회 도구를 부르고, 드라이버가 스트리밍 호출 인자를 합쳐 JSON과 스키마를 검증한 뒤 고정된 문서 ID 목록을 돌려준다.
2. 모델이 두 문서를 읽는 도구를 부르면 이전 메시지와 실제 호출 ID를 보존해 고정 본문을 추가한다. 짧은 본문과 긴 본문에 모두 확인 가능한 값 두 개를 심는다. 선행 도구 결과가 도착한 뒤에만 다음 모델 요청을 제출한다.
3. 최종 답변에서는 실제 가시 콘텐츠와 종료 사유를 수집하고 두 값의 비교·근거가 맞는지 검사한다. 짧은 중간 출력과 충분히 긴 최종 출력을 얻는지 실제 토큰 수로 확인한다. 출력 상한에 걸린 미완료 답변, 잘못된 도구 인자, 누락된 단계는 실패에 포함한다.
4. 단일 세션에서 콜드 시작, 같은 세션의 즉시 후속 턴, 도구 대기 뒤 재개를 비교한다. 이후 독립 세션을 겹쳐 긴 도구 결과가 다른 세션의 최종 답변 생성 도중 도착하도록 한다. 실행 순서·도구 대기·문서 내용·외부 세션 도착을 고정하고, 보류 시드는 후보 선택 뒤에 연다.

## 계측과 완료 기준

클라이언트 단조 시계로 작업 시작, 요청 제출, 호출 인자 완성, 도구 시작·종료, 최종 답변 첫·마지막 콘텐츠 시각을 남긴다. `workflow_id`, 턴 번호, 서버 요청 ID로 입장·템플릿 처리·토큰화·prefill·decode·전송 구간을 연결한다. CUDA 시간은 GPU 이벤트로 수집하고 서로 다른 시계의 절대값을 직접 빼지 않는다. 분기나 병렬 호출을 추가할 때는 종단 벽시계와 임계 경로를 보존한다.

**산출물과 통과.** 워크플로 입력·도구 응답·도착 시각표, 요청별 원본, 지연 요약표, 실패 분모, 독립 기준 반복의 변동 범위를 남긴다. 단일 세션과 혼합 부하 모두에서 첫 요청부터 마지막 응답까지 연결되고 같은 fixture의 결과 검사가 통과하면 02로 이동한다. 첫 실행에서 결정한 작업 길이와 동시성은 고정해 별도 시드에서 재측정한다.

## 첫 A100 워크플로 기준선

Qwen2.5-7B-Instruct BF16, A100-SXM4-40GB 한 장, 동일 가중치와 KV 4,096블록을 사용했다. 배포 이미지의 리비전은 `b7ca110fc`이며 체크아웃 `18cd37cef`와 `crates`, `kernels`, `deploy/docker`의 추적 소스가 일치했다. 기존 GPU 7 holder를 통해 실행마다 별도 서버를 시작하고 종료 후 같은 20GiB 예약으로 복귀한 사실을 확인했다. 캐시 끔은 CLI 옵션 생략이다. 첫 준비 실행에서 명시적으로 0을 전달하자 서버가 준비 전에 거부해 이 실행은 성능 표본에서 제외했다.

### 도구 호출 중 앱이 직접 결정할 수 있는 단계

Coder 카탈로그 부하의 `list_reports`는 이름이 지정됐고 인자는 빈 객체 하나다. `read_reports` 역시 이름이 지정됐고 두 필드는 각각 한 문자열만 허용한다. 기본 재생은 두 번 모두 모델을 부른다. 앱이 이 단계의 실행을 명시적으로 맡는 경우 재생 CLI의 `--dispatch-fixed-tools`를 선택할 수 있다. 로컬 단계에서는 별도 호출 ID를 만들고 실제 도구를 실행한다. 두 번째 실행 전에는 앞선 도구가 해당 보고서를 실제로 반환했는지 확인한다. 앱에 선택지가 남은 단계는 모델 경로를 따른다. 로그에서 앱의 호출 ID와 서버가 발급한 모델 응답 ID를 구별하며, prefix 통계에는 실제 모델 요청만 넣는다. A100 두 장에서 얻은 88개 작업(44개 입력을 두 번 실행)의 원본으로 확인했다. 공개 클라이언트의 선택 경로에서 도구 두 개를 실행하고 최종 전송 직전의 요청을 캡처했다. 176개 도구의 이름·인자·반환 데이터가 기존 모델 경로와 일치했다. 새 호출 ID를 사용해도 Coder 체크포인트로 렌더링한 최종 입력의 **토큰 ID 전체가 88/88건 같았다**. 포화 부하의 긴 작업에서 기존 두 중간 모델 요청을 기다린 시간의 합계 중앙값은 GPU별 3.22·3.32초였다. 이 값에는 다른 요청을 기다린 시간도 들어간다. 새 경로의 실시간 단축량은 GPU에서 별도로 측정해야 한다. ### 앱 직접 실행 후 Coder 체크포인트의 실제 최종 답변

도구 결정을 앱으로 옮긴 뒤에도 실제 최종 답변을 끝까지 받을 수 있는지 확인했다. Qwen2.5-Coder-7B-Instruct의 긴 이력 200개(시드 17101)와 빈 이력(17104)을 각 지시에서 재사용했다. 각 작업은 두 도구를 순서대로 실행하고 각각 500ms를 기다렸다. 허용된 64개 레코드에서 요청한 두 보고서 전문을 선택한 뒤 최종 호출 한 번을 HTTP로 보내고 스트림의 정상 종료까지 읽었다. Riley의 Rust 템플릿·토크나이저가 만든 입력 ID로 같은 체크포인트를 CPU FP32에서 실행했다. 각 답변은 저장된 생성 토큰을 별도로 디코딩해 수신한 전체 텍스트와 대조했다.

인용 지시가 없을 때 두 답변 모두 전후 측정값과 차이를 맞히고 지정한 첫 문장을 지켰지만 출처 ID를 누락했다. 최종 요청에 출처를 명시하라는 기존 지시를 추가하자 두 답변 모두 ID를 포함했다. 두 답변 모두 첫 문장의 측정값과 마침표 사이에 출처를 넣어 지정 형식은 깨졌다. 긴 이력의 답변은 별도 설명 문단을 만들지 않아 문단 단어 수가 0으로 집계됐다. 이 지표는 전체 답변 길이와 다르다. [기본 지시 원문·검산](../../benchmarks/evidence/20261124-agentic-serving/named-cpu-verified.json) · [인용 지시 원문·검산](../../benchmarks/evidence/20261124-agentic-serving/named-cpu-citations-verified.json)

## 도구에서 확인한 수치로 최종 답변을 시작하는 실험

보고서 두 개의 수치와 출처가 이미 반환된 시점에 앱이 첫 세 문장과, 두 측정값 바로 뒤에 출처를 붙인 설명의 첫 문장을 구성했다. 최종 요청의 새 선택 필드 `riley_assistant_prefix`에 이 문자열을 넣으면 Riley가 모델의 채팅 템플릿 끝에 이어 붙여 한 번에 토큰화한다. 서버는 이후 모델이 생성한 접미부를 스트리밍하고 앱이 전체 답변을 조립한다. 이 비교에서 첫 콘텐츠 타임스탬프는 모델이 생성한 접미부의 첫 SSE다. 수치가 없거나 두 레코드가 중복되거나 도구 호출 ID가 일치하지 않으면 앱은 전체 답변 생성을 사용한다. 앱이 시작 문장을 제공한 네 답변 모두 자연 종료했고 해당 문장에 들어간 수치와 출처가 정확했다. 단순 이어 쓰기의 긴 사례는 p95의 뜻을 빠뜨렸고, 짧은 사례는 이를 90번째 백분위로 잘못 설명했다. 두 사례 모두 생성 토큰이 64개 미만이어서 기존 품질 게이트도 실패했다. 후속 지시를 추가한 두 설명은 95번째 백분위와 측정값을 연결하고 기존 게이트를 통과했다. 다만 정확히 90단어인 설명은 없었고 빈 이력에서는 p95를 허용 가능한 최대 지연처럼 해석했다. 짧은 생성 토큰 수를 운영 성능 개선으로 인정하지 않는다. 실서비스 기본 정책 승격과 GPU 지연 판정은 보류한다.
