# 05. 다중 노드 부하와 운영 인수

[전체 이정표](README.md) · 선행 [복제본 라우팅과 테넌트 격리](04-replicas-and-tenants.md)

**시작 조건.** 두 독립 복제본에서 검증한 모델·이미지·라우팅·격리 구성을 고정한다. 운영 후보 부하의 세션 간격, 입력 증가량, 도구 대기, 최종 출력 길이, 테넌트 편중을 익명화한 통계로 등록한다. 실제 서비스 트레이스가 없으면 합성 조건과 검증 가능한 규모를 명시한다. 기존 저장소에는 Docker 이미지, readiness와 서버 내부 계수가 있다. ## 인수와 릴리스

실행 전 허용 지연·결과 오류율·거절률·복구 시간·피크 도착률·시험 기간을 운영 시나리오별로 등록한다. 공개 API는 워크플로 ID로 턴별 추적이 가능해야 하고, 지표에는 고객 프롬프트 본문을 넣지 않는다. 전체 GPU 할당시간을 비용 분모로 삼아 모델 적재와 여유 복제본 비용도 포함한다.

결과에는 모델·리비전, 노드와 GPU 수, 소프트웨어 버전, 검증된 최대 동시 작업·도착률, 먼저 한계에 닿은 자원, 미검증 장애 유형을 적는다. 소규모 카나리에서 사용자 최종 답변 지연·오류·거절·비용을 이전 버전과 비교한다. 등록 기준을 넘으면 이전 이미지·라우팅 정책으로 되돌려 **복귀 후에도** 최종 답변을 끝까지 받는지 확인한다. 실제 트래픽 전환은 해당 서비스의 별도 릴리스 절차에서 수행한다.

**완료 판정.** 정상 부하, 피크, 교체, 장애, 복구에서 원본 요청과 서버 상태가 연결되고 예산·지연·정확성 기준을 통과한 구성만 운영 인수 대상으로 기록한다. 합성 다중 노드 시험 통과, 실제 트래픽 카나리 통과, 운영 전환 완료를 각각 날짜와 함께 전체 이정표에 반영한다.

## 단일 호스트 운영 시험

04의 순차 분배 기준 구성으로 독립 A100 복제본을 기동한다. 최종 답변을 받는 동안 기존 복제본을 신규 라우팅에서 제외하고, 그 답변의 실제 종료를 기다린 뒤 기존 프로세스를 내린다. 같은 GPU에 대체 프로세스를 올려 준비 확인을 마친다. 다른 복제본이 일부 콘텐츠를 발행한 순간 해당 시험 컨테이너의 프로세스 장애를 주입하고, 끊긴 스트림의 종료 상태와 대체 경로의 새 요청을 추적한다. 시험 오케스트레이터의 SQLite 기록에서 동일 논리 작업에 대한 도구 효과가 중복 저장되는지도 검산한다. 이 시험은 단일 호스트의 프로세스 경계를 검증한다. [시험 조건](../../benchmarks/evidence/20261124-agentic-serving/operations-registration.json)

별도 30분 부하에서는 기본 초당 0.5개, 3분마다 20초 동안 초당 2개의 에이전트 작업을 도착시킨다. 도구 대기와 취소·저속 수신을 섞고 작업별 결과, 초기·후기 p95, KV·할당 추세와 종료 회수를 기록한다. [부하 등록](../../benchmarks/evidence/20261124-agentic-serving/soak-registration.json)

### 복제본 교체와 장애 후 복구 결과

A100 두 장의 시험 복제본에서 기존 스트림을 끝까지 전송한 뒤 그 프로세스를 내렸다. 대체 복제본이 준비되기까지 101.49초가 걸렸다. 살아 있던 다른 복제본은 최종 답변 콘텐츠 4개를 발행한 직후 프로세스가 종료됐다. 실제 종료 코드는 137이었고 클라이언트는 종료 사유·SSE 완료 이벤트 없이 끊어진 응답을 실패로 기록했다. 준비된 복제본으로 명시적으로 새 요청을 보내 장애 주입 후 4.54초에 도구·최종 답변 검사를 모두 통과했다. 동일한 논리 작업의 도구 호출은 네 번 관측됐고 SQLite에 기록된 효과는 `list_reports` 한 번과 `read_reports` 한 번이었다. 두 정상 종료 프로세스는 활성 요청·KV·네이티브 할당을 모두 회수했고 세 프로세스의 예약 반환을 확인했다.

**결합 인수 판정은 실패다.** 신규 라우팅과 원래 구성으로 다시 보낸 시드 762의 두 답변은 모두 HTTP 200·SSE 완료였고 수치 68·17·51ms가 맞았다. 두 답변 모두 지시한 보고서 이름을 빠뜨렸다. 전달 성공과 사용자 응답의 정확성을 함께 요구하는 기준에서 두 건을 실패로 유지한다. 이 시험의 복귀는 원래 256행 구성으로의 라우팅 복귀다. 이 실행에서는 호스트 장애와 서로 다른 이미지 간 복귀를 시험하지 않았다. [검산 결과](../../benchmarks/evidence/20261124-agentic-serving/operations-verified.json) · [프로세스·요청·저장 원본](../../benchmarks/evidence/20261124-agentic-serving/operations-raw.tar.gz)

서비스 주소를 받으면 같은 합성 연쇄를 인증된 HTTPS 인그레스에서도 실행할 수 있다. 예를 들어 `python3 benchmarks/live/agent_workflow.py "$RILEY_SERVICE_URL" "$RILEY_MODEL" --bearer-env RILEY_TRIAL_TOKEN --seed 761 --history-entries 200 --out workflow.json`을 사용한다. 드라이버는 시스템 인증서 검증을 사용한다. 서비스 루트·경로 접두사·`/v1` 기점에서 인증된 스트리밍 요청이 도달하는 것을 로컬 TLS 서버로 확인했다. 실제 배포 대상의 노드 배치와 외부 경로는 별도로 검증한다. [드라이버](../../benchmarks/live/agent_workflow.py)

복구 드라이버의 후속 버전에서는 논리 작업 ID·턴별로 도구 입력과 실제 결과를 한 트랜잭션에 저장한다. 재시도 시 저장된 값을 읽어 모델에 전달한다. 로컬에서 8개 스레드의 중복 요청, 프로세스 재시작에 해당하는 저장소 재열기, 별도 작업 ID, 같은 키의 다른 입력 거부를 검증했다. 첫 GPU 장애 시험은 SQLite 효과의 중복 방지까지 확인한 버전이다. 도구 결과 재사용까지 포함한 GPU 재시험은 별도 결과로 기록한다. 시드 762·783·797의 자료명 누락에는 최종 턴에서 원본 ID의 인용 위치를 지정하는 후보를 대조하며, 처음 쓰는 시드 세 개도 같은 판정에 포함한다. [인용 후보의 등록 조건](../../benchmarks/evidence/20261124-agentic-serving/citation-registration.json)

### 실서비스 메타데이터로 확인한 문맥 길이와 도구 대기

Liu 외의 GitHub Copilot 코딩 에이전트 공개 자료(CC BY)에서 2026-06-01 UTC의 번호순 첫 8개 샤드를 재집계했다. 표본은 비기업 사용자의 4,000개 세션, 사용자 턴 16,190개, 모델 호출 122,323개다. 실패 상태 1,534개와 토큰 수가 빠진 성공 호출 1,816개를 길이 분포에서 제외했다. 이 표본은 특정 Riley 고객의 트래픽을 대표하지 않는다. [Microsoft 공개 자료와 라이선스](https://github.com/Azure/AzurePublicDataset/blob/master/GitHubCopilotCodingAgentDataset2026.md) · [Liu 외, Agentic Coding in the Wild](https://arxiv.org/abs/2608.00101)

| 성공 호출 중 토큰 수를 아는 118,973개 | 중앙값 | p95 |
|---|---:|---:|
| 입력 토큰 | 55,753 | 161,654 |
| 출력 토큰 | 170 | 1,859 |
| 원본 서비스의 미적중 입력, 캐시 수치가 유효한 호출 | 1,181 | 56,989 |

등록한 8,192 문맥·384 출력 예산에 길이상 들어가는 호출은 1,623개(**1.36%**)였다. 32,768 문맥·2,048 출력으로 넓혀도 31,574개(**26.54%**)다. 익명화된 원래 모델의 토큰 수에 대한 계산이다. 따라서 두 A100 복제본의 합성 소규모 결과로 산업 워크로드 전체 성능을 예측할 수 없다. 긴 이력의 재사용, 처음 보는 수만 토큰의 실행 비용, 긴 최종 답변의 완료 지연을 각각 검증해야 한다.

도구 대기는 오전 기록으로 도구 조합별 하위 10% 시간을 학습하고 오후에 검증했다. 요청 ID가 여러 호출에서 반복돼, 동일한 직전 ID와 확정 가능한 시간 순서가 있는 배치만 사용했다. 검증한 52,887개 배치에서 실제 350ms 이상은 19,886개였다. 긴 대기로 예측한 4,706개 중 87개가 실제로는 짧았다. 이 규칙은 오판을 줄였지만 실제 긴 대기의 약 23%만 골랐다. 이 수치만으로 Riley의 GPU 시간 절감을 추정하지 않는다. [원본 지문·재집계 조건](../../benchmarks/evidence/20261124-agentic-serving/public-trace-registration.json) · [전체 통계·시간 리플레이 표본](../../benchmarks/evidence/20261124-agentic-serving/public-trace-verified.json)

독립 GPU 대조에는 8K 범위 16개와 확장 범위 8개의 입력 길이·출력 예산을 고정했다. 원본에 없는 문장은 합성했고 모델에 넣기 전에 Riley 토크나이저로 24개 모두의 입력 길이를 확인했다. 서버가 실제로 관측한 길이, 출력 조기 종료와 거절은 별도로 기록한다. [재현용 입력 명세](../../benchmarks/evidence/20261124-agentic-serving/public-shapes.json)

### 출처 누락과 장문 수용 범위 재시험

출처 이름 두 개와 수치를 모델에 주입하지 않고, 반환된 각 보고서를 이름으로 인용하라는 지시를 덧붙였다. 이전 실패 시드 3개와 새 시드 3개를 기동 순서를 바꿔 검사했다. 기존 지시는 6/12, 명시 지시는 12/12에서 도구 호출·정답 수치·두 출처 검사를 모두 통과했다. 장애 복구 중에도 같은 결과가 유지되는지는 운영 시험에서 별도로 판정한다. [교차 검증](../../benchmarks/evidence/20261124-agentic-serving/citation-verified.json)

공개 표본에서 131,072 문맥·2,048 출력 예산에 들어가는 성공 호출은 토큰 수가 알려진 118,973개 중 102,738개(86.35%)였다. 원본 문자열이 없어 실제 GPU에는 토큰 수와 출력 예산을 맞춘 합성 문자열을 보낸다. Qwen 32K와 Llama 128K의 최초 기동은 기본 varlen 프로파일의 fixed-tile attention이 허용하는 8,192 문맥을 초과해 준비 단계에서 거절됐다. Qwen의 기존 page attention 경로는 32,768 문맥·256행으로 별도 시험한다. 128K는 모델이 허용하는 길이, Riley가 실제로 수용하는 길이, 그 길이에서 검증한 정확성을 각각 기록한다. [공개 표본](../../benchmarks/evidence/20261124-agentic-serving/public-trace-verified.json) · [장문 보충 실험 등록](../../benchmarks/evidence/20261124-agentic-serving/public-long-registration.json)

### Qwen 7B에서 실제로 수용한 32K 입력

동일한 24개 입력과 출력 예산을 A100 한 장에서 재생했다. 8K 구성은 범위 안의 16개를 완료했고 확장 입력 8개는 모두 HTTP 400이었다. 32K page 경로에서는 24개 모두 정상 종료했고 서버가 보고한 입력과 생성 토큰 수가 각각 등록값과 일치했다. 확장 입력의 실제 길이는 18,520~30,828토큰, 요청 제출부터 첫 가시 콘텐츠까지는 9.17~21.88초였다. 합성 본문에 실제 서비스의 긴 KV 이력이 없는 상태에서 측정한 값이다. [요청별 원본](../../benchmarks/evidence/20261124-agentic-serving/public-shapes-raw.tar.gz) · [수용 범위 검산](../../benchmarks/evidence/20261124-agentic-serving/public-shapes-verified.json)

### 배포한 엔드포인트에서 같은 연쇄를 재생하는 방법

토폴로지 파일에 같은 모델을 제공하는 복제본마다 직접 접근할 URL, 물리 노드 이름, 전용 GPU 수를 넣는다. 텐서 병렬 복제본은 그 복제본에 할당한 GPU 수를 적는다. 인증이 필요한 경우 환경변수 이름을 지정한다. 다음은 두 노드의 예시다.

```json
{"model":"m","replicas":[
  {"node":"node-a","gpu_count":1,"url":"https://replica-a.example/v1","bearer_env":"RILEY_A_TOKEN"},
  {"node":"node-b","gpu_count":1,"url":"https://replica-b.example/v1","bearer_env":"RILEY_B_TOKEN"}
]}
```

```sh
python3 benchmarks/live/agent_fleet_replay.py inventory.json run-01.json \
  --policy round-robin --waves 1 2 4 8
```

기본 정책은 순차 분배다. 제출 건수, 두 도구와 최종 답변의 검증 결과, 요청마다 선택한 복제본, 최종 답변 시작·완료 p95, 부하 구간의 GPU·시간당 목표 충족 작업 수를 남긴다. 노드 라벨과 GPU 수는 운영자가 제공한 값이다. 물리적으로 구분된 노드인지, GPU를 다른 복제본과 공유하는지는 배포 인벤토리와 대조해야 비용 분모를 해석할 수 있다. 활성 슬롯을 반영하는 후보를 시험할 때는 각 항목에 서버에 설정한 `max_active_sequences` 양의 정수를 추가한 뒤 `--policy capacity`를 사용한다. [재생 클라이언트](../../benchmarks/live/agent_fleet_replay.py)

앱이 확정된 도구 호출을 직접 수행하는 배포는 같은 인벤토리·도착 순서·시드로 두 모드를 재생한다. 다음 예에서 각 모드는 44개 작업을 제출한다. 도구 두 단계는 정상 실행하고 최종 답변을 스트리밍으로 받는다. 동일 부하의 실제 운영 비교에는 모드마다 같은 초기 캐시 상태를 준비하고 실행 순서를 뒤집어 반복한다.

```sh
python3 benchmarks/live/agent_fleet_replay.py inventory.json model.json --waves 4 8 16 16
python3 benchmarks/live/agent_fleet_replay.py inventory.json app.json --waves 4 8 16 16 --dispatch-fixed-tools
```

작업마다 예정 도착 시각과 실제 시작의 차이(`start_lag_ms`)를 남긴다. `scheduled_first_p95_ms`와 `scheduled_last_p95_ms`는 기본 정답을 충족한 작업의 예정 도착부터 첫·마지막 콘텐츠까지이고, `scheduled_slo_completed`는 전체 제출 중 정답과 첫 콘텐츠 10초·마지막 18초·콘텐츠 간격 p95 150ms를 모두 지킨 건수다. `scheduled_warm_goodput_per_gpu_hour`는 이 건수를 관측 시간과 배정 GPU 수로 나눈다. 같은 크기의 부하를 반복해도 각 작업 ID와 시드는 고유하다. 운영 비교는 제출 건수와 목표 충족 건수를 함께 읽어 실패 요청까지 반영한다.

로컬 HTTP 복제본 두 개로 CLI를 실행해 앱 모드 24개 작업에서 최종 모델 요청 24회, 기본 모드 3개 작업에서 모델 요청 9회를 수신했다. 시작 지연을 주입한 별도 테스트에서 실제 시작 기준으로 통과한 한 건이 예정 도착 기준으로는 기한을 넘겼다. 이 시험의 검증 범위는 클라이언트의 전송·집계다. 물리 다중 노드의 성능과 장애 복구는 운영 인벤토리에서 측정해야 한다. [검증 코드](../../benchmarks/evidence/20261124-agentic-serving/test_named_fleet.py)

같은 체크포인트의 네이티브 프로파일러를 준비하면 실제 HTTP 경로에서 복제본별·작업별 준비 예산을 지정할 수 있다. 다음 예에서 단위는 16토큰 블록이다. 앱은 이미 결정된 도구를 직접 실행하고 첫 도구 대기 중 준비 요청을 최대 640토큰으로 제한한다. 복제본이 여러 개면 이 옵션의 기본 배치는 세션 고정이다.

```sh
cargo build --locked --release -p riley-server --features server --example qwen_prompt_profile
python3 benchmarks/live/agent_fleet_replay.py inventory.json bounded.json \
  --dispatch-fixed-tools --waves 4 8 16 16 --preview-budget-blocks 80 40 \
  --prompt-profiler target/release/examples/qwen_prompt_profile --tokenizer-dir "$CHECKPOINT_DIR"
```

`preview_budget`에는 복제본별 최대 예약량·종료 후 잔여량·토크나이저 불일치 여부를 남긴다. 작업의 `preview`에는 실제 수신 완료 여부, 신청한 블록 수, 로컬 토큰 수, 서버 사용량, 취소·생략 사유가 남는다. Llama 3 체크포인트는 `--llama3`를 추가한다. [복제본별 수신과 실패 복구 검증](04-replicas-and-tenants.md#복제본별-준비-요청-예산과-최종-요청-배치)

### 32K를 넘긴 장문 검색 실험

별도로 빌드한 Llama 3.1 8B BF16 실험 바이너리는 D128 page attention의 허용 길이를 확장하면서 배치 행을 32 이하로 제한하고 기존 작업공간 크기 검사를 유지한다. A100 40GB 한 장에서 131,072 문맥으로 기동했고, 입력 209토큰과 45,281토큰 각각에서 앞·뒤에 넣은 서로 다른 값을 순서대로 찾아냈다. 첫 가시 콘텐츠는 각각 108ms와 68.18초였다. 45K 입력의 기능 확인이며 지연이 커서 서비스 후보 승격은 보류한다. 더 긴 공개 표본의 수용 및 성능을 추가 측정한다. ### 긴 생성의 마감 시간과 스트림 오류

배치 메모리 안에서 실행 가능한 요청이라도 서버의 생성 마감 시간을 넘길 수 있다. 첫 112,106토큰 시험에서 구버전 수집기가 스트림 오류 프레임에도 응답 ID가 있다고 가정해 중단됐다. 원본에 오류 코드가 남지 않아 그 실행의 실패 원인은 확정할 수 없다. 수집기를 수정해 스트림 오류 내용을 보존하고 서버에는 입장 대기와 별도로 생성 마감 시간을 설정하는 `--request-timeout-ms`를 추가했다. 기존 서버 기본은 120초이고 명시적 값은 1~3,600,000ms다. 스트리밍과 비스트리밍 생성 모두에 적용한다. 긴 마감 허용은 수용 조건이며 응답 속도 개선과 별도로 평가한다. [서버 변경](../../crates/riley-server/src/main.rs) · [단축 및 연장 마감 대조](../../benchmarks/evidence/20261124-agentic-serving/long-deadline-registration.json)

1초 마감 대조에서 209토큰 문맥의 두 값을 108ms에 읽기 시작해 정상 완료했다. 45K 요청은 HTTP 200 스트림을 열었지만 콘텐츠가 나오기 전에 오류 코드 `timeout`이 왔다. 수정한 수집기는 이를 실패로 기록했다. [오류 프레임·짧은 대조 검산](../../benchmarks/evidence/20261124-agentic-serving/short-deadline-verified.json)

900초 생성 마감을 설정한 독립 기동에서 공개 표본의 네 입력이 모두 정상 스트리밍 종료했고 입력 토큰 수는 네 건 모두 일치했다. 112,106토큰은 첫 콘텐츠 339.51초·마지막 콘텐츠 342.53초, 83,768토큰은 199.90초·204.82초, 44,034토큰은 65.25초·69.54초였다. 세 건은 등록한 출력 길이까지 생성했다. 46,080토큰 입력은 첫 콘텐츠 70.39초·마지막 콘텐츠 90.77초로, 허용한 출력 1,301토큰 중 633토큰에서 모델이 자연 종료했다. 같은 기동의 45,281토큰 검색은 앞뒤 두 값을 맞혔다. 112K 구간은 합성 내용으로 길이 수용을 입증한 범위이고, 이 지연으로 운영 성능을 충족한다고 판정할 근거는 없다. 실험용 128K attention 변경과 서버의 생성 마감 옵션은 독립 변경이다. [원본](../../benchmarks/evidence/20261124-agentic-serving/long-resume-raw.tar.gz) · [요청별 검산](../../benchmarks/evidence/20261124-agentic-serving/long-resume-verified.json)

실험 빌드에서 같은 Llama 112,106토큰 요청은 fixed-tile attention으로 첫 콘텐츠 97.39초·마지막 98.84초를 기록했다. 45,281토큰 검색은 26.49초에 첫 콘텐츠를 보였고 두 참조값을 맞혔다. Qwen 7B는 32K 안에서도 24K 반복 배경 검색에 실패했다. 서비스 인수 시에는 문맥 길이·출력 예산에 들어가는지와 함께 자료의 앞뒤에 있는 값을 최종 답변이 출처에 맞게 인용하는지 확인한다. [모델별 결과](../../benchmarks/evidence/20261124-agentic-serving/long-tile-verified.json)

### 11월 25일 · 서로 다른 이미지로 단일 호스트 롤백

기존 배포 이미지와, 그 이미지의 Riley 실행 파일만 검증된 새 릴리스로 교체한 로컬 Docker 이미지를 사용했다. GPU6의 이전 버전 → GPU7의 새 버전 → GPU6에서 새로 기동한 이전 버전 순으로 요청을 보냈다. 각 컨테이너에서 Docker 이미지 ID와 실제 실행 중인 `/proc/1/exe` 해시를 확인했고, 모델 디렉터리만 마운트했다. 새 버전은 해당 버전에서 추가한 요청 제한 시간 옵션도 받아들였다.

* 이전 버전을 새 요청 대상에서 빼기 전에 시작된 스트림은 끝까지 수신했다. 새 요청은 새 버전에서 완료됐다.
* 이전 이미지의 대체 인스턴스를 기동해 실제 준비가 되기까지 103.59초가 걸렸다. 대체 인스턴스를 준비한 뒤 새 버전에서 최종 답변 네 조각을 받았을 때 해당 프로세스만 강제로 종료했다. 종료 코드는 137이었고, 클라이언트는 불완전한 스트림을 실패로 기록했다.
* 실패 주입부터 준비된 이전 버전에서 도구와 최종 답변을 다시 완료하기까지 5.35초가 걸렸다. 복구 답변과 롤백 뒤 새 답변은 모두 요청한 수치·출처를 포함했다. 영속 저장소에는 네 번의 시도에서 서로 다른 도구 효과 두 건만 커밋됐다.
* 정상 종료한 두 인스턴스는 활성 요청·KV·네이티브 할당을 모두 반환했고 세 프로세스의 전용 GPU 예약 반환을 확인했다. 검증 범위는 한 호스트의 실제 프로세스, 로컬 Docker 이미지 두 버전, 클라이언트가 명시적으로 수행한 라우팅 전환이다. 고객 트래픽과 호스트 간 장애는 운영 인수가 남아 있다. [이미지·실행 파일·워크플로 대조](../../benchmarks/evidence/20261124-agentic-serving/image-rollback-verified.json) · [원본 기록](../../benchmarks/evidence/20261124-agentic-serving/image-rollback-raw.tar.gz)

### 운영 재생 기록에서 최종 완료 시간을 분해하는 방법

인벤토리 재생의 출력 파일을 다음 명령에 넣으면 파동별 제출·성공·목표 충족 수와 완료 작업별 네 구간의 시간을 확인할 수 있다.


네 구간은 선행 모델 호출과 클라이언트 처리, 도구 실행 대기, 최종 요청 제출부터 첫 가시 콘텐츠, 첫 콘텐츠부터 마지막 콘텐츠까지다. 첫 구간에는 라우팅·호출 사이의 시간도 들어간다. 세 번째 구간은 HTTP·대기·prefill을 포함한다. 각 작업의 네 값은 해당 작업의 실제 완료 시간과 합계가 맞으며, 구간별 p95는 서로 다른 작업에서 나올 수 있다. 이전 기록에 시각이 부족하면 해당 작업의 분해 값을 비워 두고 완료·실패 분모는 유지한다. 두 A100에서 기록한 6개 기동, 90개 제출 중 성공 78개 전부에서 합계를 검산했다. [분해 도구](../../benchmarks/live/summarize_agent_workflow.py) · [원본 대조 결과](../../benchmarks/evidence/20261124-agentic-serving/fleet-breakdown-verified.json)

`reported_final_prefix_cache`는 서버가 최종 요청의 캐시 사용량을 보고한 작업만 모아 입력·적중·미적중 토큰 합계와 토큰 가중 적중률을 계산한다. 위의 Riley 성공 78건에서는 원래 사용량과 합계가 맞았다. 사용량 세부 정보가 없는 vLLM 원본 5건에서는 보고 건수 0, 미보고 건수 5, 적중 토큰은 `null`이었다.

### 여러 라우터가 동일한 GPU 풀을 사용할 때

`agent_fleet_replay.py`의 `--policy observed-capacity`로 각 엔드포인트의 `/readyz` 부하 정보를 쓰는 실험을 재현할 수 있다. 인벤토리는 각 복제본의 `url`, `node`, `gpu_count`, `max_active_sequences`를 지정한다. 인증을 쓰면 `bearer_env`에 환경변수 이름을 넣는다. 같은 모델·테넌트의 요청을 해당 인벤토리의 모든 복제본이 처리할 수 있어야 한다. [인벤토리 사용법](#배포한-엔드포인트에서-같은-연쇄를-재생하는-방법) · [실험 코드](../../benchmarks/live/agent_fleet_replay.py)

GPU가 포화될 때 상태 신호의 도착 시간도 검증해야 한다. 현재 재생 클라이언트는 라우터마다 최대 8개 복제본을 동시에 조회하고, 한 라운드가 끝난 뒤 100ms 쉬며, 500ms가 지난 표본은 사용하지 않는다. 복제본과 라우터 수가 늘면 조회량도 함께 증가한다. 실제 클러스터에서는 결정 시 표본 나이, 오래된 표본을 사용하지 못한 비율, 상태 조회에 사용한 HTTP 용량, 라우터 간 동시 배치 충돌, 실제로 큐에 들어간 시간을 측정한다. 전용 상태 포트나 노드별 수집기를 채택할지는 이 측정과 장애 복구 결과로 결정한다. [단일 호스트에서 확인한 포화 현상](04-replicas-and-tenants.md#서로-다른-클라이언트가-한-복제본을-채울-때)

**과부하 인수 시험의 설계.** 상태 조회 워커 하나를 추가한 실험 구성이 8개 생성 슬롯 포화를 감지한 뒤에도 일반 HTTP 요청은 그 워커를 함께 쓴다. 같은 8개 생성 스트림을 유지하고 외부 도착 수를 기존 과부하 시험의 16·64·160개로 올린다. 라우터별로 상태 조회 성공·시간 초과·표본 만료, 실제 활성 수와 결정 시 표본의 차이, 거절·재시도, 상대 스트림의 마지막 콘텐츠와 p95 간격을 함께 기록한다. 같은 입력으로 노드 간 왕복 지연과 한 노드 단절을 추가하면, 프로세스가 살아 있으나 상태 전달이 끊긴 경우까지 판정할 수 있다. [8슬롯 결과](../../benchmarks/evidence/20261124-agentic-serving/headroom-verified.json) · [기존 과부하 원본](../../benchmarks/evidence/20261124-agentic-serving/crossover-raw.tar.gz)

### 8개 슬롯에 외부 요청 16·64·160개가 한꺼번에 도착한 결과

### 서버가 POST 본문보다 먼저 보낸 HTTP 429 기록

클라이언트가 요청 본문을 쓰기 전에 Riley의 HTTP 접수 대기열이 가득 차면 리스너가 바로 429를 전송하고 연결을 닫을 수 있다. 이때 이전 재생 클라이언트는 본문 쓰기의 `BrokenPipeError`에서 종료돼 같은 연결에 도착한 응답을 읽지 못했다. 재생 클라이언트가 이 오류에 한해 같은 연결에서 최대 250ms 동안 이미 전송된 오류 응답을 읽도록 변경했다. 읽어 낸 상태 코드만 기록하고 POST 재전송은 0회다. 오류 응답을 확인할 수 없는 경우는 전송 실패로 집계한다. [재생 클라이언트](../../benchmarks/live/agent_workflow.py) · [사전 등록](../../benchmarks/evidence/20261124-agentic-serving/early-rejection-registration.json)

A100 두 장에서 기존 스트림 8개를 유지하고 복제본당 한꺼번에 160개씩 요청했다. 양쪽 GPU에서 클라이언트 버전을 교환했고 출력 한도 16·64토큰을 시험했다. 버전별 제출 640건과 실제 생성 완료 516건은 같았다. 기존 클라이언트는 HTTP 429를 31건, 상태 코드가 없는 쓰기 실패를 93건 기록했다. 변경 후에는 429를 124건 기록했고, 이 중 93건은 쓰기 실패 직후 같은 연결에서 읽은 서버의 실제 응답이었다. 이 측정이 개선한 지표는 **과부하 거절 분류**다. ### 운영 지표에서 prefill과 decode의 GPU 시간 확인

서버의 `/metrics`와 정상 종료 보고서에 `batch_shapes.by_phase`를 추가했다. 같은 프로세스에서 두 번 수집한 값의 차이로 해당 구간의 prefill 전용, decode 전용, 혼합 스텝 수와 처리 토큰 수·GPU 실행 시간을 얻는다. 혼합 스텝은 하나의 배치로 실행한 시간을 한 번 기록한다. 고객 프롬프트나 요청 ID를 추가로 수집할 필요가 없다. 워밍업을 제외하려면 준비 완료 뒤의 계수를 시작점으로 잡는다. 프로세스 재기동 때는 새 구간을 시작한다. [필드 정의](../configuration.md)

Coder-7B를 올린 A100 한 장에서 실제 HTTP 응답의 전후 계수를 독립적으로 기록한 스텝 로그와 대조했다. 두 이력 길이의 고정 출력 비교, 도구를 두 번 호출하는 작업 여섯 개, 별도 입력 지문 조회를 포함한다. 자연 종료한 답변 여섯 개가 기본 수치·출처 검사를 통과했다. [검산](../../benchmarks/evidence/20261124-agentic-serving/iteration-phase-verified.json) · [측정 원본](../../benchmarks/evidence/20261124-agentic-serving/iteration-phase-raw.tar.gz)

| 스텝 유형 | 스텝 | 처리한 입력 토큰 | decode 행 | GPU 시간 |
|---|---:|---:|---:|---:|
| prefill 전용 | 63 | 34,624 | 0 | 2.661초 |
| decode 전용 | 1,676 | 0 | 1,950 | 19.946초 |
| 혼합 | 6 | 54 | 6 | 0.085초 |

총 1,745개 스텝에서 세 유형의 12개 계수가 정수 나노초까지 일치했다. 기존 batch bucket 지표의 스텝 수와 GPU 시간 합계도 일치했고 정상 종료 보고서가 마지막 계수를 보존했다. 이 표는 고정 출력과 자연 종료가 섞인 시험 전체의 누계다. 특정 사용자의 최종 응답 대기나 클러스터 GPU 할당 비용은 각각 클라이언트 시각과 할당 시간으로 측정한다. 소스 변경과 단일 호스트 시험까지 확인했다. 운영 이미지 배포와 다중 노드 수집은 후속 인수 범위다.

### 워커 대기와 GPU 대기를 운영에서 구분하기

서버의 `/metrics`와 정상 종료 JSON에서 `http_worker_queue.dequeued_connections`, `wait_ns_total`, `wait_ns_max`를 읽을 수 있다. 연속 표본의 총 대기 차이를 처리 연결 수 차이로 나누면 해당 구간의 평균 큐 대기가 나온다. 분모가 0이면 그 구간에는 관측이 없다. 최대값은 프로세스 기동 이후의 값이다. 시간은 접수한 소켓을 큐에 넣기 직전부터 워커가 꺼낼 때까지다. 헬스 체크와 지표 조회도 처리 연결 수에 포함되며 즉시 거절한 연결은 과부하 계수에서 확인한다. 지표 조회 자체도 같은 워커를 기다리므로 표본이 늦거나 조회가 만료된 구간은 게이트웨이의 지연·거절 기록과 함께 읽는다. 운영 바이너리는 집계값만 기록한다. [API 지표 정의](../api.md#get-metrics) · [서버 설정](../configuration.md#capacity)

같은 호스트의 A100 두 장에서 네 번 기동해 매번 145개 연결의 개수·대기 합계·최댓값을 진단 로그와 검산했다. 네 부하 구간의 증분도 서버 표본과 일치했다. 워커 8개에서 프로세스 전체 최장 대기는 3.96~4.11초, 16개에서는 0.034~0.039ms였다. 긴 요청은 워커 대기가 사라진 뒤에도 기한을 넘겼다. 증설을 판단할 때는 HTTP 대기와 함께 **예정 도착부터 최종 답변까지 기한을 지킨 건수**를 본다. [고정 부하와 판정](03-mixed-scheduling.md#최종-호출이-http-워커를-기다린-시간)

### 앱과 CPU 모델 워커를 서로 다른 호스트에 둔 종단 확인

Darwin 호스트의 앱이 카탈로그 도구를 두 번 실행하고, AWS Linux 호스트의 Qwen2.5-Coder-7B-Instruct CPU 참조 서버와 HTTP로 통신했다. 원격 리스너는 loopback에 바인딩했고 SSH 포트 포워딩으로 연결했다. 앱의 네이티브 프로파일러와 원격 워커가 각각 준비 요청을 렌더링했다. 시드 17101과 256토큰 예산에서 **164토큰 준비 요청과 3,072토큰 최종 요청**이 각각 원격에 도착했다. 두 도구가 각각 실제 6초를 기다렸다. 앱에서 관측한 준비 스트림은 최종 요청을 보내기 5.55초 전 종료했다.

서버에서 완성된 KV 중 160토큰을 재사용했고 첫 최종 forward에는 2,912토큰이 들어갔다. 출력 88개 토큰 전체가 같은 입력의 준비 없는 실행과 같았고, 최종 스트림이 자연 종료했다. 기존 답변의 세 측정값과 출처 누락도 유지됐다. 이 시험은 실제 두 호스트의 앱→단일 CPU 모델 워커 경로를 검증했다. 대조군과 후보의 시간 차, 여러 GPU 노드의 용량, 외부 로드밸런서와 카나리는 각각 해당 토폴로지에서 측정해야 한다.
