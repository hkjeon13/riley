# 02. 대화 이력 재사용과 새 입력의 prefill

[전체 이정표](README.md) · 선행 [워크플로 기준선](01-workflow-baseline.md) · 다음 [혼합 스텝과 decode](03-mixed-scheduling.md)

**시작 조건.** 01의 연쇄에서 각 턴의 렌더링된 입력, 도착 시각, 출력 검사를 재현할 수 있어야 한다. 이 단계에서는 실제로 GPU가 다시 읽은 토큰 수와 소비한 시간을 구한다.

## 현재 경로와 실험 축

Riley는 완전한 16토큰 prompt KV 블록을 공유한다. 마지막 prompt 토큰은 실행하며 decode가 쓴 블록은 게시하지 않는다. CPU 토큰화가 따뜻한 캐시의 지연에 크게 기여한 기록도 있다. 따라서 캐시 적중률, GPU prefill 시간, 사용자 대기를 각각 잰다. [캐시 동작과 실측](../prefix-cache.md) · [캐시 운영 검사](../../benchmarks/live/operational_check.py)

| 실험 축 | 첫 비교 | 고정할 조건 |
|---|---|---|
| 이전 이력 길이 | 짧은 이력과 긴 이력에 동일한 도구 결과 추가 | 새 토큰 수, 출력, 큐 상태 |
| 새 입력 길이 | 동일 이력에 짧은 조회 결과와 긴 문서 추가 | 기존 KV 길이와 적중 상태 |
| 재사용 기회 | 캐시 끔, 첫 요청, 즉시 후속 요청, 다른 세션이 들어온 뒤 재개 | GPU, KV 총 메모리 예산, 워크플로 |
| 동시 부하 | 단독 요청과 다른 세션이 최종 답변을 생성 중인 경우 | 모델·입력·출력 구간과 도구 대기 |

프롬프트 문자열 대신 채팅 템플릿 적용 후의 토큰 ID로 공통 prefix 길이를 구한다. 이전 턴에서 실제 게시할 수 있었던 연속 prompt 블록과 이번 요청의 마지막 토큰 제외 규칙을 적용해 재사용 상한을 계산한다. 응답의 `usage.prompt_tokens_details.cached_tokens`와 비교하고, 미게시·퇴출·다른 프로세스·템플릿 변경을 구별한다. `prompt_tokens - cached_tokens`에는 처음 들어온 도구 결과도 포함되므로 그 값 전체를 낭비로 집계하지 않는다.

## 측정 결과가 정하는 구현 순서

| 관측 | 첫 후보 | 진행 전 반증 실험 |
|---|---|---|
| 도구 대기 뒤 게시된 블록을 잃음 | 제한된 KV 예산에서 다음 턴의 재개 가능성을 고려한 보존 | 같은 예산의 기존 LRU와 비교. 다른 세션 대기·퇴출도 합산 |
| 적중이 충분해도 전송·렌더링·토큰화가 큼 | 이전 턴 참조와 새 메시지를 받는 선택적 연속 호출 | 기존 전체 이력 API와 렌더링 토큰 ID, 경계 토큰화, 출력 비교. 참조 만료·분기·취소 시 전체 이력 복구 |
| 신규 입력의 GPU 실행이 지배 | 실제 이력 길이·추가 토큰 수에서 비싼 연산 하나를 개선 | 요청별 GPU 임계 경로에 관측 가능한 최대 절감량을 대입. 해당 시간을 전부 제거해도 목표 변화가 작으면 보류 |

**산출물과 통과.** 각 셀에 총 입력·신규 토큰·재사용 가능 및 실제 적중 토큰·큐·CPU·GPU 시간과 종단 시간을 기록한다. 가장 큰 비용 하나만 바꾼 후보를 기존 API와 같은 출력 조건에서 다시 실행한다. 01의 최종 답변 시작·완료와 혼합 부하에서 효과가 관측되고 결과 정확도·메모리 예산을 지키면 03의 기준 후보로 넘긴다. 효과가 작은 후보는 기각하고 비용 분해표와 현재 Riley 구성을 넘긴다.

## 첫 재사용량 검산

캐시를 켠 두 실행 모두 15개 호출의 입력 합계 7,295토큰 중 3,472토큰이 실제 적중했다. 보존된 합성 fixture와 모델이 생성한 호출 ID·인자로 요청을 재구성해 원본 요청 해시와 사용량을 대조했다. Riley의 동일 템플릿과 토크나이저로 계산한 선행 완료 요청의 연속 prefix 상한과 각 호출의 실제 적중량이 일치했다. 앞선 실행이 동시에 진행 중이면 그 실행에서 방금 게시된 블록도 사용 가능하므로 이 상한의 범위는 **이미 끝난 요청**이다. [요청별 검산](../../benchmarks/evidence/20261124-agentic-serving/on-b/prefix.json) · [재구성 도구](../../benchmarks/live/audit_agent_prefix.py)

긴 도구 결과를 넣은 최종 요청은 입력 2,546토큰 중 16토큰만 재사용했다. 이 fixture는 마지막 호출에서 `tool_choice=none`을 사용한다. Qwen 템플릿의 앞쪽에서 도구 설명이 빠져 공통 prefix가 짧아진다. 이 경우 캐시 보존 시간을 늘려도 16토큰보다 많이 재사용할 수 없다. 같은 입력이 그대로 반복된 별도 셀의 높은 적중률은 실제 운영 세션의 적중률로 일반화할 수 없다. 첫 후보는 긴 신규 입력이 있고 활성 decode가 없을 때만 넓은 prefill 스텝을 허용하는 기존 옵션 조합이다. 보류 시드의 짧고 긴 대화 이력에서 같은 후보를 대조한다. [후보와 채택 조건](../../benchmarks/evidence/20261124-agentic-serving/prefill-registration.json)

A100 6번의 별도 진단에서 긴 결과가 들어온 최종 요청은 짧은 이력 조건에서 2,530행·10개 혼합 스텝, 긴 이력 조건에서 5,277행·21개 혼합 스텝에 참여했다. 두 경우 모두 모든 prefill 스텝에 다른 요청이 참여했다. GPU 이벤트로 합산한 그 스텝들의 실행시간은 각각 252.6ms·435.8ms였고, 제출 측 토큰화 경로는 1.26ms·2.15ms였다. GPU 시간에는 같이 수행한 decode가 포함되므로 단일 요청의 독점 연산시간으로 해석하면 안 된다. 이 중첩 사례에서는 순수 prefill만 넓히는 후보가 직접 바꿀 스텝이 없다. 비계측 비교에서의 실제 이득과 회귀를 별도로 판정한다. [짧은 이력 추적](../../benchmarks/evidence/20261124-agentic-serving/trace-0.json) · [긴 이력 추적](../../benchmarks/evidence/20261124-agentic-serving/trace-200.json)

## 보류 시드 결과와 03으로 넘기는 구성

A100 7번에서 256행 기준 → 넓은 후보 → 넓은 후보 → 256행 기준 순서로 서버를 새로 시작했다. 후보는 긴 prefill이 대기하고 decode 대기 행이 0개일 때만 최대 1,024행을 허용한다. 40개 작업과 120개 모델 호출에서 대응 도구 인자와 최종 답변이 일치했고, 매 셀에서 요구한 혼합 도착과 정상 종료 후 자원 회수를 확인했다. 표는 인접한 기준 대비 두 후보 비교의 변화율이다.

| 이력 | 최종 답변 시작 p95 | 최종 콘텐츠 수신 p95 | 답변별 간격 p95의 작업 간 p95 |
|---|---:|---:|---:|
| 추가 이력 없음 | −2.61% / −0.40% | −0.81% / −0.11% | −2.66% / +0.19% |
| 200개 항목의 이전 이력 | −6.11% / −6.04% | −2.57% / −2.51% | −0.60% / −0.17% |

짧은 이력의 두 후보 실행에서 256행을 넘는 스텝은 0회였다. 이 셀의 차이를 넓은 스텝의 효과로 보지 않는다. 긴 이력에서는 기준에 없는 넓은 스텝이 실행됐고 완료까지 약 0.10초를 줄였다. 한 실행당 5개 작업으로 계산한 p95이다. 03에는 기준 구성과 긴 이력 후보를 함께 넘긴다. 혼합 prefill 자체와 vLLM decode 동등성은 다음 단계에서 판정한다. ### 도구를 기다리는 동안 준비할 수 있는 최종 입력

Qwen 템플릿이 최종 턴에서 도구 정의를 제거하면서 긴 이력까지 다시 계산한다. 실제 두 번째 도구 결과가 도착하기 전에 알고 있던 메시지만으로 최종 턴 형식의 prefix를 만들어 Riley 토크나이저로 비교했다. 긴 결과가 오는 보류 사례에서 실제 최종 입력은 5,312토큰이고 기존 경로의 적중은 32토큰이었다. 미리 계산 가능한 완전한 prefix는 2,912토큰으로, 추가 적중의 상한은 **2,880토큰**이다. 즉시 재요청과 지연 후 동일 재요청은 이미 3,056토큰을 재사용해 이 방법의 추가 이득이 0이었다. [요청별 토큰 검산](../../benchmarks/evidence/20261124-agentic-serving/tool-wait-prefix.json) · [재현 코드](../../benchmarks/live/agent_tool_wait_prefix.py)

이 후보는 실제 최종 요청의 템플릿과 도구 사용 규칙을 그대로 유지할 수 있다. 채택 여부는 도구 대기 동안 GPU가 여유로운지, 결과가 돌아오기 전에 몇 블록을 완성했는지, 다른 사용자의 decode를 얼마나 늦췄는지로 판단한다. 이미 뜨거운 요청과 대기가 짧은 요청을 포함해야 한다. 위 수치는 미리 계산 가능한 토큰 수이며 가속 실측은 후속 실험에 해당한다.

도구 대기 후보의 실제 HTTP 실험은 독립 기동 네 번을 끔→켬→켬→끔 순서로 고정했다. 이미 검증한 두 번째 도구 호출 직후, 그때 알던 메시지만으로 최종 형식의 1토큰 요청을 비동기 제출한다. 실제 도구 결과가 오면 이 요청의 완료를 기다리지 않고 원래 최종 요청을 보낸다. 대기 0·100·500ms, 이미 캐시된 동일 이력, 다른 사용자가 읽는 구간을 각각 기록한다. [등록 조건](../../benchmarks/evidence/20261124-agentic-serving/tool-wait-registration.json) · [실행 드라이버](../../benchmarks/live/tool_wait_trial.py)

### 도구 대기 중 prefix 준비의 첫 GPU 대조

같은 A100과 넓은 순수 prefill 구성에서 준비 요청을 끈 기동과 켠 기동을 한 번씩 비교했다. 다섯 조건 모두 최종 답변 텍스트가 같았고 정확성 검사를 통과했다. 지연은 클라이언트에서 측정했다.

| 조건 | 최종 요청 캐시 적중, 끔 → 켬 | 도구 결과 준비부터 최종 첫 콘텐츠, 끔 → 켬 | 최초 요청부터 최종 완료 시간 변화 |
|---|---:|---:|---:|
| 대기 0ms | 32 → 1,056토큰 | 376 → 493ms | +124ms |
| 대기 100ms | 32 → 2,080토큰 | 371 → 323ms | −41ms |
| 대기 500ms | 32 → 2,912토큰 | 371 → 190ms | −177ms |
| 대기 500ms, 이미 따뜻한 동일 이력 | 5,296 → 5,296토큰 | 17 → 16ms | +4ms |
| 대기 500ms, 다른 사용자가 스트리밍 중 | 32 → 2,912토큰 | 449 → 226ms | −254ms |

대기가 없을 때는 준비 요청과 실제 최종 요청이 같은 GPU를 놓고 경쟁했다. 일부 캐시 적중이 생겨도 최종 완료는 늦어졌다. 상대 사용자가 있는 500ms 사례에서 그 사용자의 콘텐츠 간격 p95는 21.16 → 20.98ms였다. 이 결과는 조건별 한 쌍으로 측정한 값이다. 역순 기동으로 반복한다. [대조 원본](../../benchmarks/evidence/20261124-agentic-serving/first-interventions.tar.gz) · [조건별 검산](../../benchmarks/evidence/20261124-agentic-serving/prefix-first-pair.json)

조건부 후보는 호출자가 도구 실행 전에 알고 있는 대기 예측값이 350ms 이상이고 관측 문맥이 1,024토큰 이상일 때만 예열한다. 동일 테넌트·복제본의 준비 요청은 한 번에 하나로 제한하고, 성공한 문맥 리비전을 잠시 기억해 중복 제출을 줄인다. 새 시드에서는 긴 대기로 예측했지만 실제로 50ms 만에 돌아오는 사례도 포함한다. 이 임계값은 첫 실측에서 도출한 시험용 값이다. [후보 정책](../../benchmarks/live/tool_wait_policy.py) · [예측 오류 포함 실험 등록](../../benchmarks/evidence/20261124-agentic-serving/wait-policy-registration.json)

역순의 독립 기동에서도 다섯 답변의 텍스트와 정확성 판정이 같았다. 500ms 대기 시 첫 콘텐츠는 183ms 빨라졌고 최종 완료도 183ms 단축됐다. 상대 스트림이 있는 500ms 사례는 최종 완료가 213ms 빨랐다. 대기 0ms에서는 완료가 116ms 늦어졌다. 두 쌍 모두 긴 대기에서 2,880토큰을 추가 재사용했다. 따라서 모든 도구 호출을 예열하는 방식은 채택하지 않고, 대기 예측 오차를 포함한 조건부 정책을 별도로 판정한다. [두 쌍 전체 검산](../../benchmarks/evidence/20261124-agentic-serving/prefix-verified.json) · [독립 기동 원본](../../benchmarks/evidence/20261124-agentic-serving/agent-interventions-raw.tar.gz)

### 대기 예측을 사용한 실제 호출

기동 3회에서 보류 시드 두 개를 대조·후보 사이에 교차 배정했다. 원래의 두 도구와 최종 답변까지 36개 작업 전부가 정확성 검사를 통과했다. 500ms 대기 중 다른 사용자가 답변을 받는 경우 완료가 같은 입력의 대조보다 184~263ms 빨라졌다. 상대 스트림의 간격 p95는 대조 21.49~21.58ms, 후보 21.30~21.54ms였다. 상대가 없는 500ms 대기에서 단축 폭은 0.5~317ms였고, 추가 적중도 128~2,880토큰으로 차이가 컸다. 긴 대기를 예측했지만 실제로 50ms에 돌아온 경우에는 최종 완료가 57ms 빨라진 비교부터 4.3ms 늦어진 비교까지 있었다. 짧은 대기와 이미 예열한 문맥을 건너뛴 경우 추가 적중은 0이었다.

제한된 실험용 클라이언트에서 대기 예측·중복 제거를 함께 쓰는 방식을 유지한다. 여기서 사용한 힌트는 사전에 부여한 값이다. 실제 서비스의 예측 오차와 GPU 과부하에서의 비용을 제품 적용 전에 검증해야 한다. 같은 기동을 공유하는 비교값을 독립 반복으로 세지 않았다. ### 공개 표본의 이전 문맥을 이어받은 Qwen 32K 결과

별도 A100 7번에서 차가운 기준, 1,536블록 보존, 2,048블록 보존 순으로 새 서버를 기동했다. 8개 표본의 최종 요청은 모든 구성에서 같은 입력과 출력 토큰 수로 완료됐다. 두 보존 구성 간에는 각 답변의 텍스트 해시도 같았다. 이전 문맥을 이미 처리한 뒤 후속 요청을 보내면, 2,048블록 구성의 첫 콘텐츠가 차가운 기준보다 2.43~21.15초 빨랐다. 8개 모두 토크나이저로 사전 계산한 16토큰 단위 재사용 상한까지 적중했다.

| 22,743 / 21,274 | 12.92초 | 1.41초 | 1.41초 |

30,828토큰 요청에서는 보존량을 늘리자 실제 적중이 24,576에서 30,256토큰으로 높아졌다. 2,048블록에서 차가운 기준 대비 마지막 콘텐츠도 21.15초 빨랐다. 반면 재사용할 이력을 오직 이 한 요청을 위해 직전에 새로 만든다고 가정하면, 선행 요청 시작부터 후속 응답 완료까지는 8개 모두 차가운 기준보다 17~58ms 더 걸렸다. 따라서 이 결과가 지지하는 설계는 **이미 필요해서 실행한 이전 턴의 KV를 보존하고, 다음 턴에 그 KV가 있는 가용 복제본을 쓰는 것**이다. 모델·GPU 한 종류와 표본별 한 번의 순차 측정이다. 동시 장문 세션에서 보존량을 늘릴 때의 용량 비용은 별도 판정 대상이다. ### 명시적인 ID 조회에서 도구 반환값을 줄이는 방법

사용자가 요청한 ID와 도구의 고유 키가 정해진 경우, 클라이언트가 도구의 원본 반환값에서 해당 레코드 전체를 골라 최종 답변 호출에 넘긴다. 선택기는 금액이나 정답을 입력받지 않는다. 선택한 레코드의 필드·출처·순서를 보존하고, 조회 ID가 없거나 중복·누락·형식 오류가 있으면 전체 반환값을 돌려준다. 모집단의 평균·예외 탐색·자유 검색처럼 어떤 레코드가 필요한지 사전에 정할 수 없는 작업에는 전체 반환값을 사용한다. 동일한 등록부의 두 ID를 조회하는 과제로 두 A100에서 실행 순서를 뒤집어 비교한다. | 원본 레코드 + 출력 스키마, page / fixed-tile | 3/3 · 3/3 | 0/3 · 0/3 | 0/3 · 0/3 |
| 행 배열 + 자유 출력, page / fixed-tile | 0/3 · 2/3 | 0/3 · 1/3 | 0/3 · 0/3 |
| 행 배열 + 출력 스키마, page / fixed-tile | 2/3 · 3/3 | 0/3 · 0/3 | 0/3 · 0/3 |

25,028토큰 조회에서는 사용자가 이미 지정한 두 ID만 스키마의 필수 속성으로 선언하고 두 금액은 모델이 원본에서 찾도록 했다. 양쪽 경로가 같은 37토큰 정답을 생성했고, 마지막 콘텐츠는 page의 15.89~15.90초에서 fixed-tile의 3.28초로 앞당겨졌다. 행 배열과 스키마를 함께 쓰면 같은 조회가 18,810토큰, 약 2.37초였다. 그러나 다른 조회에서는 행 배열이 page의 정확도를 떨어뜨렸다. 전체 최댓값 검색은 890건 입력을 25,921→19,703토큰으로 줄여도 모든 조합에서 실패했다. 스키마는 알려진 키의 중복 출력을 막는 데 도움이 됐고, 새로운 출처를 찾아 순위를 판단하는 정확성은 별도 문제로 남았다. 일반 장문 프로파일의 채택 기준은 미달이다.

### 독립 모델 실행으로 attention 경로의 출력 차이 확인

위 시험의 기존 ID 조회 3건과 890건짜리 상태 검색·최댓값 검색을 자유 출력으로 다시 실행했다. Riley 양쪽 경로에서 입력 토큰 해시와 실제 생성 토큰을 수집하고, 같은 체크포인트의 4개 가중치 파일과 설정·토크나이저 등 총 9개 파일의 SHA-256을 검증했다. Hugging Face Transformers 5.22.1과 PyTorch 2.13.0+cu129에서 BF16 SDPA·greedy로 실행했고 입력 토큰 전체 해시가 두 Riley 경로와 일치하는지 확인했다. |---|---|---|---|---|
| ID 조회, 5,988토큰 | 실패 | 성공 | 성공 | fixed-tile |
| ID 조회, 17,468토큰 | 성공 | 성공 | 성공 | 양쪽 |
| ID 조회, 25,028토큰 | 성공 | 실패 | 실패 | fixed-tile |
| 상태 검색, 25,937토큰 | 실패 | 실패 | 실패 | 양쪽 |
| 최댓값 검색, 25,921토큰 | 실패 | 실패 | 실패 | fixed-tile |

25,028토큰에서 독립 실행도 같은 ID를 중복 출력했다. 두 Riley 경로가 처음 달라진 32번째 출력 위치에 똑같은 직전 토큰까지 넣었을 때, 독립 실행의 최대 logit은 fixed-tile의 선택과 일치했고 page가 고른 토큰과의 차이는 3.25였다. 5,988토큰 조회에서는 5번째 위치에서 차이가 32.3125였다. 이 두 값은 독립 모델의 공통 접두사에서 잰 logit 차이다. Riley 내부의 어느 레이어에서 차이가 생겼는지는 이 자료로 특정할 수 없다.

이 결과에 따라 두 판단을 따로 기록한다. **수치 재현**은 이 다섯 입력에서 fixed-tile이 5/5, page가 2/5였다. **서비스 정확성**은 두 Riley 경로와 독립 실행 모두 2/5였다. 긴 입력에서 기존 모델 동작을 재현하려는 후속 실험은 fixed-tile을 우선한다. 일반 장문 검색의 운영 채택에는 별도의 정답 기준을 계속 적용한다.

### 자유 형식 장문 검색에서 관련 원본만 전달

질문에 출처 ID가 들어 있지 않아도 질문과 각 원본 문단의 단어 일치도를 BM25로 계산해 상위 8개 문단을 고른다. 문단의 전체 본문과 출처 ID를 원본 순서로 유지하고, 모델이 자연어로 수치와 연결된 출처를 답한다. 선택기에는 질문과 허용된 문단만 들어간다. 전체를 읽어야 하는 최댓값·건수 질의는 전체 입력 경로를 사용한다. [근거 선택과 요청 구성](../../examples/long_search.py)

11월 27일 AWS A100 6번 한 장에서 Qwen2.5-7B-Instruct BF16, 문맥 32,768, 256토큰 스텝, 빈 prefix 캐시로 비교했다. 24개 영어 질문에는 초기·최종 승인액 중 하나 또는 두 값을 찾는 요청을 섞고, 출처 위치와 프로젝트명이 같은 별도 기록을 바꿨다. 두 attention 모드에서 각각 원문 전체와 BM25 선별 입력을 같은 질문과 답변 지시로 재생했다. 요청은 한 번에 하나씩 보내고, 완료는 입력 준비 전부터 SSE `[DONE]`까지 측정했다. 완료 스트림은 오답도 p95에 포함한다. ### 전체 레코드를 읽어야 하는 정형 질의의 최종 답변

최댓값을 요구하면 도구가 전체 행의 정수 필드를 비교하고, 상태별 조회를 요구하면 전체 행에서 지정한 상태를 찾는다. 어느 경우든 조회 전에 정답 출처나 금액을 알 필요가 없다. 유일한 최댓값이나 유일한 상태별 행이 결정될 때 원본 행의 필드를 보존한다. 동점·누락·잘못된 자료형처럼 계약을 충족할 수 없는 입력은 원래 경로로 돌린다. 자유 형식 질의에서 연산을 추측하는 기능은 이 실험에 포함하지 않았다. [정수 최댓값 연산](../../benchmarks/live/agent_tool_aggregate.py) · [교차 시험 등록](../../benchmarks/evidence/20261124-agentic-serving/register-reduction-registration.json)

- 두 A100 각각에서 page attention의 자유 생성은 전체 목록을 받았을 때 8건 중 0건, 조회가 선택한 전체 원본 행을 받았을 때 7건을 맞혔다. 890건 최댓값의 최종 완료는 약 16.80초에서 0.41초, 890건 상태 검색은 17.66~17.67초에서 0.91초로 줄었다. 두 경우 모두 선택 후에 출처와 금액이 맞았다. 측정은 전체 도구 응답 JSON이 준비된 시점부터 첫·마지막 가시 콘텐츠까지다. [32개 요청 원본](../../benchmarks/evidence/20261124-agentic-serving/register-reduction-raw.tar.gz) · [정답·CPU 준비 시간 검산](../../benchmarks/evidence/20261124-agentic-serving/register-reduction-verified.json)
- 실패한 상태 검색에서는 모델이 실제 ID `F9167-0198`에 0을 하나 더 붙였다. 같은 입력에서 도구가 반환한 출처만 출력 스키마의 허용 목록에 넣고 금액·상태별 연결은 모델이 읽도록 했다. 새 4건을 포함한 12건에서 양쪽 GPU 모두 자유 생성 10/12, 스키마 11/12였다. 실패한 답은 존재하는 다른 출처를 두 상태에 중복 연결했다. 출처가 허용 목록 안에 있다는 검사만으로는 근거가 맞는지 판단할 수 없다. [후속 48개 요청 원본](../../benchmarks/evidence/20261124-agentic-serving/register-provenance-raw.tar.gz) · [결과별 검산](../../benchmarks/evidence/20261124-agentic-serving/register-provenance-verified.json)

**사용자가 요구한 JSON이 연산과 필드로 완전히 결정되는 경우**에는 도구의 선택 결과로 최종 JSON을 직접 만드는 클라이언트 함수를 추가했다. 예를 들어 유일한 최대 승인 금액을 찾고 같은 원본 행의 출처와 금액을 그대로 반환할 수 있다.

```python
from agent_tool_result import exact_tool_result

answer = exact_tool_result(
    records,
    operation="unique_integer_max",
    key="approved",
    fields={"source": str, "approved": int},
)
```

함수는 값이 확정되면 사전을, 계약에 맞지 않으면 `None`을 반환한다. 호출하는 서비스가 명시적인 정형 질의에서 이 경로를 선택한다. 110~1,100행의 18개 입력에서 독립적으로 확인한 출처·금액과 모두 일치했고, 8개 예외 입력에서는 결과 생성을 건너뛰었다. 로컬 Darwin arm64·Python 3.12.7의 450회 측정에서 전체 JSON 바이트 파싱부터 결과 바이트 생성까지 입력별 p95는 0.045~0.449ms였다. 네트워크와 외부 도구 실행 시간은 별도이며, 이 수치는 서버 전체 응답 시간이 아니다. [클라이언트 함수](../../benchmarks/live/agent_tool_result.py) · [재현 절차](../../benchmarks/evidence/20261124-agentic-serving/verify_exact_result.py) · [측정 원본과 소스 지문](../../benchmarks/evidence/20261124-agentic-serving/exact-result-verified.json)

### 장문 입력과 생성 중 수치 차이의 위치

5,988·25,028토큰 원본 레코드 조회에서 마지막 prefill과 최초로 출력이 달라진 decode를 따로 포착했다. 두 요청에서 첫 레이어의 실제 Q·K·V를 모두 비교한 결과, 큰 attention 차이는 생성 행의 점수 반올림으로 재현됐다. 따라서 긴 입력 경로를 고를 때는 첫 콘텐츠 시간과 함께 **동일한 이력에서 이후 생성이 갈리는지, 최종 답의 출처와 금액이 맞는지**를 각각 확인한다. [03의 레이어별 재계산과 실험 기준](03-mixed-scheduling.md#최종-답변-토큰이-달라진-위치에서-attention-수치-재현)

### 도구 호출 허용과 도구 설명 표시를 분리한 최종 턴

Qwen2.5-7B가 긴 이력에서 최종 답변을 작성할 때, 클라이언트는 `tool_choice=none`을 계속 보내면서 앞선 턴과 같은 도구 설명을 템플릿에 남겼다. 별도의 예열 요청이나 도구 추가 호출은 없었다. 비교 대상도 동일한 두 A100에서 도구 설명 숨김·유지 두 가지로 각각 실행했다. 엔진 2개 × 표시 방식 2개 × GPU 2개로 8번 새로 기동했고, 160개 작업·480개 모델 호출을 완료했다. 각 요청의 실제 입력 토큰 ID 전체 지문이 독립적으로 복원한 Riley 토크나이저 결과와 일치했다. ### 긴 도구 결과에만 적용한 시험과 답변 품질

도구 결과 JSON이 4,096바이트 이상인 최종 호출에만 설명을 유지했다. 두 번째 후보는 같은 선택 조건에 더해 결과를 원본 레코드 전체와 p95의 정의를 담은 객체로 전달했다. 두 조건을 A100 두 장에서 반대 순서로 실행했다. 네 기동의 80개 작업·240개 모델 호출을 모두 원래 입력에서 재구성해 실제 프롬프트 토큰과 대조했다. 모든 작업이 기존 자동 검사를 통과했고 예상 밖의 최종 도구 호출은 없었다. 각 그룹의 나머지 네 작업은 최종 입력·생성 토큰이 기존 숨김 경로와 같았다. | 긴 이력의 시드 | 기존 작업 완료 | 긴 결과에서만 유지 | 긴 결과에서 유지하고 p95 정의도 전달 |
|---|---:|---:|---:|
| 761 | 3.793~3.823초 | 3.513~3.516초 | 3.071~3.080초 |

긴 이력에서 얻은 서로 다른 최종 설명 6개를 숫자·출처·백분위 해석·단어 수로 검토했다. 각 답변은 두 보고서와 세 숫자를 맞혔지만, **6개 모두** 원본이 뒷받침하지 않는 주장이나 해석 오류를 포함했다. 예를 들어 59→24ms 사례에서 정의를 함께 전달하자 각 기간의 임곗값은 맞게 설명했으나 두 p95 값으로 개선의 지속성을 단정했다. 50→16ms 사례에서는 p95를 ‘가장 느린 95%’로 잘못 설명했다. 요청한 90단어 설명의 실제 길이는 수치 헤더 제외·공백 기준 79~116단어였으며 정확히 90단어인 답은 없었다. 따라서 두 선택 정책은 측정한 장문에서 지연·스트리밍 기준을 통과했고 자유 서술의 품질 인수는 보류한다. 4,096바이트는 이 실험의 선택 기준이다. ### 채팅 프롬프트 준비 중 도구 스키마 복사 제거

`POST /v1/chat/completions`의 요청 정규화 경로를 변경했다. 요청이 소유한 메시지·도구·템플릿 인자를 렌더링 문맥에 옮기고, 함수 이름과 형식을 검증할 때는 원래 스키마를 참조한다. 이름을 지정한 도구 호출에서 선택하지 않은 함수의 파라미터를 복제하던 비용도 제거했다. 도구 선택, 강제 문법, 모델, 토큰화와 GPU 스케줄링은 기존 경로를 사용한다. [서버 구현](../../crates/riley-server/src/chat.rs)

CPU 시험은 긴 이력의 실제 요청에서 복원한 60건과 합성 144건을 섞어 각 호스트에서 기존·변경 실행 파일을 네 쌍으로 번갈아 기동했다. 호스트당 정규화 1,632회를 실행했고, 모든 입력의 토큰 ID 배열이 변경 전후에 같았다. 아래는 각 기동에서 조건별 중앙값을 구한 뒤 네 번의 중앙값을 다시 취한 값이다. JSON 본문 역직렬화 이후부터 완성된 프롬프트까지의 CPU 시간이며, 토큰화는 별도로 측정했다.

| 입력 조건 | AWS Linux x86_64 기존→변경 | 로컬 Darwin arm64 기존→변경 |
|---|---:|---:|
| 도구 32개, 자동 선택 | 400→181µs | 124→65µs |
| 도구 32개, 이름 지정 | 443→199µs | 141→69µs |
| 도구 96개, 이름 지정 | 1,446→597µs | 409→195µs |
| 실제 연쇄의 두 번째 도구 호출 | 89→62µs | 28→19µs |
| 실제 연쇄의 최종 답변 요청 | 58→45µs | 18→14µs |

AWS의 변경 후 토큰화 중앙값은 도구 32개 지정 시 약 973µs, 실제 연쇄의 최종 요청에서 약 1,036µs였다. 도구 스키마가 많은 요청의 CPU 절감과 긴 이력의 GPU prefill은 서로 다른 구간이다. [시험 사전 등록](../../benchmarks/evidence/20261124-agentic-serving/chat-cpu-registration.json)

실제 A100 두 장에서 서버 기동 순서를 뒤집어 도구 없음·자동·이름 지정·숨김·장문 결과 6조건의 첫 요청, 순차 재요청, 동시 8개 요청을 측정했다. 정상 응답 336개에서 같은 GPU의 기존·변경 쌍 모두 입력 토큰, 생성 토큰, 답변 본문, 호출한 함수·인자, 종료 사유가 같았다. 오류 입력 8건의 HTTP 400 본문도 일치했다. 캐시 사용량을 보고한 조건과 그 값도 같았다. 도구 32개의 순차 재요청에서는 두 GPU 모두 자동 선택 26.83~26.91→26.45~26.63ms, 이름 지정 289.64~289.88→289.45~289.50ms였다. 전체 조건을 합친 요청 완료 중앙값은 GPU 6에서 36.71→36.61ms, GPU 7에서 35.97→36.30ms로 방향이 달랐다. 서버 코드에는 CPU 비용을 줄이는 변경을 적용했고 전체 서빙의 응답 시간 단축 판정은 보류했다.

Qwen·Llama 3의 실제 템플릿과 토크나이저로 도구 인자의 객체·문자열, 스키마 참조, 숨긴 도구와 템플릿 인자, 충돌·오류 입력 등 17개 조합을 각각 검사했다. 모델별로 허용 11개의 토큰 배열과 거절 6개의 오류가 기존과 같았다. Llama 검사는 CPU의 프롬프트 준비 범위다. ## 긴 prefill을 청크로 나눌 때 KV 캐시 순서 갱신 비용

Riley는 16토큰 KV 블록을 게시한 뒤, 그 블록과 모든 조상을 최근 사용 목록의 끝으로 옮긴다. 한 세션에 청크가 추가될 때마다 앞서 방문한 조상을 다시 읽고 연결을 고쳤다. 첫 변경은 직전에 갱신한 경로의 양 끝을 기억했다. 새 블록에서 그 경로에 닿으면 연결 한 구간을 옮겨 같은 퇴출 순서를 만든다. 다른 세션이 중간에 들어와도 이미 자식→부모 순서로 연결된 구간은 한 번에 옮긴다. [스케줄러 구현](../../crates/riley-scheduler/src/prefix_cache.rs)

첫 후보는 직전 경로만 기억했다. 단일 경로의 32K 입력·256토큰 청크에서 CPU 게시 중앙값은 0.68→0.12ms였지만, 서로 다른 두 경로를 교대로 연장하면 1.64→1.85ms였다. 이 결과를 보고 여러 경로의 기존 연결 순서를 활용하는 후속 실험을 등록했다. 전체 순·역방향 목록과 독립 기준 목록을 3,000번의 삽입·갱신·퇴출·초기화 뒤에 비교했다. 스케줄러 테스트 146개가 통과했다. [첫 후보 실측](../../benchmarks/evidence/20261124-agentic-serving/prefix-recency-first-verified.json) · [후속 시험 조건](../../benchmarks/evidence/20261124-agentic-serving/prefix-recency-range-registration.json) · [테스트 기록](../../benchmarks/evidence/20261124-agentic-serving/prefix-recency-local-checks.json)

AWS 시험 호스트의 CPU 한 코어에 고정해 원본→후보→후보→원본 순으로 측정했다. 표본마다 새 캐시에 실제 블록 핸들을 넣었으며, 각 구성의 예열을 제외한 10회 중앙값이다. 게시 시간은 호스트에서 블록을 색인에 추가하고 최근 사용 순서를 갱신한 합계다. 교대 시험은 두 독립 경로 각각이 표시된 길이까지 자라므로 한 경로 시험보다 처리한 토큰 수가 두 배다.

| 경로당 토큰 | 청크 | 단일 경로 게시 시간, 기존 → 수정 | 두 경로 교대 게시 시간, 기존 → 수정 |
|---:|---:|---:|---:|
| 8,192 | 32 | 0.312 → 0.037ms | 0.758 → 0.626ms |
| 8,192 | 256 | 0.061 → 0.028ms | 0.164 → 0.154ms |
| 32,768 | 32 | 4.768 → 0.264ms | 11.365 → 9.387ms |
| 32,768 | 256 | 0.680 → 0.120ms | 1.654 → 1.502ms |
| 131,072 | 32 | 73.378 → 1.155ms | 268.070 → 267.933ms |
| 131,072 | 256 | 9.603 → 0.621ms | 27.970 → 26.632ms |

128K·32청크에서 두 경로를 교대로 연장하면 이전 경로의 지름길을 쓰기 어려워 차이가 0.1% 미만이다. 단일 경로에서 관측한 배율을 동시 세션이나 GPU 전체 prefill에 적용할 수 없다.

Qwen2.5-7B-Instruct BF16의 실제 GPU 검증은 5,137~5,312토큰 입력으로 했다. 한 호스트의 A100 두 장에서 기존·수정 바이너리를 바꿔 기동하고 각각 13개 요청을 보내 총 52건을 확인했다. 동일 이력 반복, 이력 연장과 분기, 다른 이력 일곱 개로 캐시를 채운 뒤 원래 이력을 다시 요청했다. 각 요청의 입력 토큰 지문·생성 토큰 전체·종료 사유·답변·사용량이 네 실행에서 모두 일치했다. 매 실행에서 22,320토큰이 적중하고 1,384블록이 퇴출됐다. 종료 뒤 활성·대기 요청과 할당 KV 블록은 모두 0이었다.

| A100 | 첫 콘텐츠 중앙값, 기존 → 수정 | HTTP 완료 중앙값, 기존 → 수정 |
|---|---:|---:|
| GPU 6 | 414.29 → 414.19ms | 534.01 → 534.15ms |
| GPU 7 | 413.06 → 413.05ms | 532.88 → 531.44ms |

이번 변경은 캐시 게시의 CPU 비용과 동작 보존으로 판정했다. 이 GPU 표본의 완료 지연은 일관되게 줄지 않았다. 32K·128K는 이 시험에서 CPU 색인 길이이며 해당 길이의 GPU 서비스 지연은 별도 지표다. #### 첫 KV 블록이 다른 긴 경로를 교대로 게시할 때

11월 25일 후속 변경은 첫 KV 블록마다 마지막으로 갱신한 경로를 기억한다. 서로 다른 첫 블록 아래의 경로는 최근 사용 목록에서 위치가 바뀌어도 내부 연결 순서가 유지된다. 같은 첫 블록 아래의 분기는 갱신할 때 조상 연결을 확인하고, 기억한 경로의 끝 블록이 퇴출되면 부모부터 이어지는 구간을 기억한다. 기존 항목에 32비트 인덱스 두 개를 추가했다. [스케줄러 구현과 회귀 시험](../../crates/riley-scheduler/src/prefix_cache.rs)

Apple M4에서 직전 구현과 후속 변경을 각각 네 번 새로 실행했다. 기동마다 예열 뒤 다섯 번 측정했고, 기동별 중앙값의 중앙값을 비교했다. 아래 시간에는 두 경로의 블록 삽입과 최근 사용 순서 갱신이 모두 들어 있다.

| 경로당 토큰 | 청크 | 두 독립 경로 교대 게시 시간, 직전 → 후속 |
|---:|---:|---:|
| 8,192 | 32 | 0.271 → 0.028ms |
| 8,192 | 256 | 0.050 → 0.019ms |
| 32,768 | 32 | 7.314 → 0.117ms |
| 32,768 | 256 | 0.929 → 0.080ms |
| 131,072 | 32 | 125.435 → 0.494ms |
| 131,072 | 256 | 15.906 → 0.341ms |

단일 경로 여섯 조건의 중앙값 차이는 0.004ms 이내였다. 보존된 Coder-7B 요청으로 정상·역순 도착과 준비 취소를 포함한 72개 스케줄러 조건을 재생했다. 캐시 적중 토큰, 배정 행, 퇴출 수, 완료 순서가 직전 구현과 기존 기록에 모두 일치했다. 시간 비교는 첫 KV 블록이 다른 합성 경로의 CPU 측정이다. [측정값과 재생 지문](../../benchmarks/evidence/20261124-agentic-serving/prefix-recency-per-root-verified.json)

#### AWS A100 두 장의 32K 프로파일 교차 검증

11월 26일 Qwen2.5-7B-Instruct BF16과 256토큰 청크로 AWS A100 5·6번의 기동 순서를 반대로 배치했다. GPU마다 기준·후보를 두 번씩 새로 기동했다. 30,030토큰과 30,032토큰 입력은 첫 KV 블록이 달랐고, 첫 콘텐츠가 나오기 전에 두 요청이 동시에 활성 상태였음을 확인했다. 이어서 이력을 연장한 후속 요청 두 개와 약 5.1K 토큰의 반복·분기·퇴출 요청 13개를 보냈다. 두 긴 경로를 보존할 수 있도록 물리 KV 4,608블록과 prefix 캐시 4,096블록을 지정했다.

136개 응답에서 같은 입력의 프롬프트 토큰 지문, 생성 토큰 전체, 본문, 종료 사유, 사용량이 일치했다. 긴 후속 요청은 개별 실행에서 각각 30,016토큰을 재사용했다. 기동 예열 계수를 빼면 모든 실행에서 85,792토큰 적중, 2,259블록 퇴출, 101,477행 prefill이 일치했다. 정상 종료 후 활성·대기 요청과 할당 KV 블록은 모두 0이었다.

### Coder-7B 최종 호출의 신규 prefill 비용

Qwen2.5-Coder-7B-Instruct의 두 도구 호출과 최종 자연어 답변을 재생했다. 같은 호스트의 A100 40GB 두 장에서 page와 fixed-tile의 기동 순서를 뒤집었다. 두 모드의 최종 입력 토큰 지문, 캐시 적중량, 청크 크기와 위치가 일치했다. 아래는 긴 도구 결과를 받은 시드 762의 진단 빌드에서 측정한 시간이다. 최종 호출 대기는 해당 HTTP 제출부터 첫 콘텐츠까지, 전체 작업은 첫 도구 호출 요청부터 최종 콘텐츠까지다. [원본 검산](../../benchmarks/evidence/20261124-agentic-serving/coder-prefill-trace-verified.json)

| A100 | 최종 호출 대기, page → fixed-tile | 그중 prefill GPU 시간 | 전체 작업, page → fixed-tile |
|---|---:|---:|---:|
| GPU 6 | 397.2 → 177.7ms | 393.3 → 174.7ms | 2.746 → 2.461초 |
| GPU 7 | 395.6 → 179.0ms | 392.6 → 176.1ms | 2.740 → 2.458초 |

page의 추가 대기 중 GPU prefill 차이가 각각 99.6%, 100.0%(반올림)를 설명했다. 별도 장문 시드 네 개에서도 두 GPU의 여덟 비교 모두 사전에 정한 80% 기준을 넘었다. 이 결과는 두 attention 경로를 바꾼 결과이며, 특정 CUDA 커널이 차이를 전부 차지하는지는 개별 커널 측정이 필요하다. 실험의 varlen 프로파일은 이미 fixed-tile을 선택한다.

**도구 대기 중 미리 계산할 수 있는 양은 작업마다 달랐다.** 시드 762는 3,888토큰 중 1,344개가 이미 적중했다. 두 번째 도구 결과가 시작되기 전까지 추가로 준비할 수 있는 완전한 KV 블록은 176토큰이었고, 경계 블록에서 끝까지 2,368토큰이 남았다. 반면 시드 833·861·902는 같은 경계까지 1,488토큰을 더 준비할 여지가 있었다. 도구를 기다리며 이력을 준비하는 후보와 새 도구 결과를 빠르게 처리하는 후보는 이 두 입력군에서 따로 비교한다. 이 수치는 토큰 위치로 계산한 상한이다. 실제 예열 비용과 적중 지속 시간은 별도 측정이 필요하다. [토큰 경계](../../benchmarks/evidence/20261124-agentic-serving/coder-tool-boundary-verified.json)

**page에서 prompt 타일을 직접 집계하는 옵션은 채택 기준에 미달했다.** GPU별로 같은 서버 바이너리를 한 번씩 더 기동했다. 시드 762의 첫 콘텐츠 대기는 397.2→310.9ms, 395.6→310.3ms로 줄었고 장문 다섯 입력 모두 빨라졌다. 짧은 시드 761은 최종 답변이 99→130토큰으로 늘어 전체 완료가 2.043→2.390초, 2.064→2.383초로 늦어졌다. 긴 이력의 기존 독자도 한 GPU에서 고정 길이 토큰당 시간이 5.49% 늘어 5% 한도를 넘었다. 이 옵션은 각 GPU에서 마지막에 실행했다. 자연 종료·기본 정답 검사와 고정 길이 스트리밍을 함께 보아 공통 설정 승격을 보류했다. [실험 조건](../../benchmarks/evidence/20261124-agentic-serving/coder-prefill-direct-registration.json) · [답변과 속도 비교](../../benchmarks/evidence/20261124-agentic-serving/coder-prefill-direct-verified.json)

### Coder-7B에서 도구 대기 100ms를 실제 prefill에 사용한 결과

두 번째 도구 호출을 모델이 완성한 시점에 같은 복제본으로 1토큰 준비 요청을 보냈다. 한 방식은 이미 받은 메시지 이력을 최종 답변 형식으로 준비했다. 다른 방식은 모델이 방금 확정한 호출과 비어 있는 도구 결과까지 포함했다. 준비 요청의 출력은 버렸고 실제 도구 결과가 도착하면 즉시 원본 최종 요청을 보냈다. Coder-7B, fixed-tile, A100 두 장에서 준비 끔·이력 준비·호출 포함 준비를 각각 새 서버로 실행했다. 양 끝 조건의 순서는 GPU별로 반대로 두었고 이력 준비는 두 GPU 모두 가운데에 두었다. 최종 요청의 토큰 지문을 확인하고 준비 비용을 포함한 전체 GPU 실행 시간을 스텝별로 검산했다. [실험 등록](../../benchmarks/evidence/20261124-agentic-serving/coder-wait-registration.json) · [원본](../../benchmarks/evidence/20261124-agentic-serving/coder-wait-raw.tar.gz)

| 최종 호출 전 상태 | 호출 포함 준비로 늘어난 적중 | 최종 호출 첫 콘텐츠 변화 | 전체 작업 완료 변화 |
|---|---:|---:|---:|
| 장문 이력에서 이미 1,344토큰 적중, 시드 762 | +176토큰 | 0.2~1.7ms 단축 | 0.3~14.2ms 단축 |
| 장문 이력에서 32토큰 적중, 시드 833·861·902 | +1,488토큰 | 89.8~93.0ms 단축 | 68.6~102.7ms 단축 |
| 다른 사용자가 답변을 읽는 동안 32토큰 적중, 시드 946 | +1,264토큰 | 70.1~72.1ms 단축 | 60.4~68.7ms 단축 |

**적중 토큰이 어느 GPU 스텝을 덜어 주는지가 중요했다.** 시드 762의 최종 prefill은 1,024·1,024·496행에서 1,024·1,024·320행으로 바뀌었고 세 스텝이 모두 남았다. 시드 833은 1,024·1,024·1,024·781행에서 1,024·1,024·317행으로 줄어들었고, 최종 prefill GPU 시간은 267.7~269.9ms에서 176.7~177.5ms가 됐다. 시드 946은 도구 결과가 준비 요청보다 약 27ms 빨리 돌아와 일부 KV만 사용했다. 최종 요청이 준비 요청의 완료를 기다리도록 하면 이 겹침을 잃는다. [요청별 청크·GPU 시간·최종 완료](../../benchmarks/evidence/20261124-agentic-serving/coder-wait-verified.json)

준비 요청의 토큰과 GPU 시간도 전체 비용에 포함했다. 시드 833·861·902에서 호출 포함 준비는 최종 호출의 신규 행을 각각 1,488개 줄였지만, 준비 요청까지 합치면 전체 prefill 행은 오히려 19~22개 늘었다. 전체 GPU 실행 시간도 0.36~0.74% 증가했다. 여기서 회수한 것은 외부 도구가 일하는 동안의 사용자 대기 시간이다. 포화 서비스의 처리량 개선은 이 결과에서 산출할 수 없다.

기존 이력 준비만으로도 장문 이력 세 작업의 완료가 78.1~108.4ms 빨라졌다. 호출을 추가하면 이 세 작업에서 완전한 KV 블록 두 개(32토큰)를 더 재사용했지만 일관된 추가 단축은 없었다. 두 방식 모두 등록한 지연·GPU 시간·독자 간격 보호 조건을 통과했다. 기본 수치·출처 검사는 대상 48개와 독자 12개에서 통과했고, 같은 GPU·시드의 최종 답변 본문은 세 방식 모두 같았다. 대상 답변에서 정확히 90단어를 쓴 설명은 0/48개였다. 이 결과는 이력 재사용의 효과를 검증하며 정밀한 길이 지시 준수는 남은 품질 과제다.

서비스 적용 후보는 이력 준비를 기본 비교점으로 두고, 도구 대기 안에 회수할 수 있는 prefill 스텝과 동시 스트림 간격을 기준으로 선택한다. 기존에 재사용한 토큰이 많거나 진행 중인 독자가 있을 때는 같은 긴 프롬프트에서도 이득이 작거나 첫 콘텐츠가 늦어질 수 있다. 이번 장문 대조는 같은 서버에서 처리하는 한 작업 또는 독자 한 명을 동반한 조건까지다.

### 한 복제본에서 다음 세션의 준비 요청을 허용하는 시점

여러 세션이 한 준비 예약을 공유할 때 기존 재생 클라이언트는 원래 사용자의 최종 답변이 끝난 뒤 예약을 반환했다. 준비 요청 자체는 그보다 먼저 끝날 수 있다. 조건부 재생 클라이언트에 `--release-on-preview`를 추가해 준비 요청의 실제 종료 시점에 다음 세션을 받을 수 있게 했다. 실패한 준비는 재사용 가능한 이력으로 기록하지 않는다. 기본 동작은 원래 워크플로가 끝날 때까지 예약을 보유한다. 최초 교차 시험에서 한 A100당 4·8개 세션을 300ms 간격으로 도착시켜 동일 복제본의 예약을 공유했다. 두 GPU에서 각각 다섯 번, 이전 준비가 끝나고 그 사용자의 워크플로가 아직 진행 중일 때 다음 준비가 시작됐다. 동시에 준비 요청 두 개가 실행된 사례는 없었다. 두 방식의 48개 작업이 모두 기본 정답과 시간 목표를 충족했지만, 8개 도착의 최종 완료 p95는 두 입력군에서 5.72→6.04초, 5.65→6.05초로 늘었다. 예약 반환 주기가 짧아지면 더 많은 작업이 미리 처리될 수 있고, 이미 실행 중인 작업과 GPU를 더 많이 공유한다. 실제 준비 종료, 미리 준비하는 작업 수, 사용자의 최종 완료를 각각 지표로 둔다. [최초 교차 시험](../../benchmarks/evidence/20261124-agentic-serving/coder-release-verified.json) · [실행 원본](../../benchmarks/evidence/20261124-agentic-serving/coder-release-raw.tar.gz)

최종 공개 옵션도 같은 클라이언트 소스에서 새 시드로 실행한 작업 48개으로 확인했다. 4개가 도착한 두 입력군에서는 기본·옵션의 준비 요청 수가 1→3개, 전체 완료 p95는 4.40→4.11초와 4.21→4.16초였다. 8개가 도착하면 1→4개로 늘고 전체 완료 p95도 5.57→6.00초와 5.60→5.99초로 길어졌다. 전부 기본 정답·지연 목표 안에서 끝났고 두 GPU 각각 다섯 번 이전 사용자의 워크플로가 끝나기 전에 다음 준비가 시작됐다. 독립 회귀 검사 세 개는 기본 예약 유지, 성공한 준비의 조기 반환, 연결이 끊긴 준비의 반환·재시도 가능 상태를 확인한다. ### 동시 도구 반환 후 최종 턴이 다시 처리한 입력

03의 Coder-7B 단일 GPU 포화 시험에서 긴 작업 24개의 최종 입력 합계는 127,472토큰이었다. GPU 슬롯 8개·HTTP 워커 8개에서 각 GPU가 실제 계산한 최종 prefill은 121,232·118,480토큰이었다. 각 요청의 커밋된 prefill 행 수가 `prompt_tokens - cached_tokens`와 정확히 일치했다. HTTP 워커를 16개로 늘려도 115,728·116,896토큰을 계산했다. 도구를 기다린 두 번의 호출 이후에도 긴 최종 입력의 **90.8~95.1%**가 실제 GPU에 도달했다. 여기에는 도구가 새로 돌려준 토큰도 들어간다. 이 비율 전체를 이력 재사용으로 절감할 수는 없다. [턴별 요청·캐시·실행 토큰](../../benchmarks/evidence/20261124-agentic-serving/http-worker-queue-verified.json)

**같은 세션 이력을 오래 보관할 때의 상한도 계산했다.** 두 교차 시험의 8개 기동에서 긴 작업의 최종 호출 192건(서로 다른 입력 48개)을 원래 서버의 Coder 토크나이저 메타데이터로 재구성했다. 요청마다 전송 해시와 실제 입력 길이가 일치했다. 각 최종 호출과 같은 작업의 이전 두 완료 프롬프트가 앞에서부터 공유한 완전한 블록은 모두 **16토큰 한 블록**이었다. 실제 적중량이 모든 요청에서 이미 16토큰 이상이어서, 이전 두 프롬프트의 KV를 추가로 보존해 절약할 수 있는 최종 prefill은 이 표본에서 0토큰이다. 앞선 도구 호출에는 도구 선언이 렌더링되고 최종 호출은 `tool_choice: "none"`으로 시작 부분이 바뀐다. 다른 세션이나 앞서 같은 형태로 렌더링한 최종 프롬프트는 별도의 적중을 만들 수 있다. [워커 시험의 요청별 상한](../../benchmarks/evidence/20261124-agentic-serving/http-worker-session-prefix.json) · [GPU 슬롯 시험의 요청별 상한](../../benchmarks/evidence/20261124-agentic-serving/engine-slots-session-prefix.json)

따라서 이 부하에서는 동일 세션의 직전 KV를 더 오래 남기는 설계를 우선하지 않는다. 후속 C16 시험에서는 요청한 레코드가 명확한 경우의 선택 효과를 아래에서 검증했다. **최종 호출과 동일한 형식**의 이력을 도구 대기 중 준비하는 방식과 레코드 선택을 결합한 효과는 별도 판정 대상으로 남는다. 작업당 실제 재계산 토큰, 준비에 쓴 GPU 시간, 기본 정답과 정확한 형식, 독자 간격, 기한 내 완료 건수로 순이익을 판정한다.

### Coder-7B에서 여러 세션이 동시에 카탈로그를 읽을 때

이전 부하에서 도구는 요청한 보고서 두 개만 반환했다. 그 구조에 기존 ID 선택기를 적용한 33개 입력에서 반환 내용은 같았다. 이번에는 백엔드가 권한 범위 안의 보고서 64개를 반환하고, 사용자는 그중 두 ID의 지연시간을 비교하는 별도 부하를 구성했다. 두 방식 모두 첫 도구에서 목록을 조회하고 두 번째 도구를 실제 호출한다. 후보는 모델이 유효한 도구 인자로 요청한 두 ID에 대응하는 레코드의 **모든 필드**를 원래 순서로 넘겼다. 사용자 요청·도구 원본·최종 전송 입력의 해시를 작업별로 검산했다. [부하와 사전 기준](../../benchmarks/evidence/20261124-agentic-serving/coder-catalog-registration.json)

### 긴 Qwen 도구 입력의 CPU 토큰화

Coder-7B 카탈로그의 확정된 두 도구를 앱이 실행해도, 최종 호출 때 Riley는 요청 전체를 토큰화한다. Qwen 토크나이저가 NFC 정규화 후 나눈 같은 문자열 조각에 같은 BPE 병합을 반복하는 비용을 측정했다. 변경한 경로는 4,096바이트 이상인 연속 일반 텍스트에서 3바이트 이상 조각의 토큰 범위를 최대 1,024개까지 기억한다. 다시 만난 조각은 이 요청에서 앞서 계산한 토큰 ID를 복사한다. 문맥 안에 삽입된 특수 토큰은 기존 토크나이저가 처리하고, 캐시는 일반 텍스트 구간이 끝나면 해제한다. 요청이나 테넌트 사이에 텍스트를 보존하지 않는다.

첫 후보는 고유 단어만 들어간 입력에서 기존보다 Darwin 5.002%, Linux 약 5.1% 느렸다. 후속 후보는 처음 128개의 서로 다른 대상 조각에서 재사용이 한 번도 없으면 해당 구간의 조회를 중단한다. 새 고유 단어 입력과 고유 단어로 시작해 반복 JSON으로 이어지는 혼합 입력을 추가했다. 두 호스트 모두 사전 등록한 긴 이력·JSON의 10% 이상 단축과 나머지 조건의 5% 이내 회귀 기준을 통과했다. [최초 등록](../../benchmarks/evidence/20261124-agentic-serving/piece-cache-registration.json) · [후속 등록](../../benchmarks/evidence/20261124-agentic-serving/piece-cache-followup.json)

토큰화 시작부터 ID 배열 완성까지 측정했다. 입력마다 기동당 10회, 호스트마다 4쌍의 새 프로세스에서 순서를 뒤집었다. 표의 시간은 각 조건의 프로세스 중앙값들의 중앙값이고, 백분율은 같은 기동 쌍 비율의 중앙값이다. 두 호스트에서 9개 후속 조건 모두 토큰 ID 전체가 기존과 일치했다. 별도로 이전 A100 카탈로그의 제출 528건(서로 다른 HTTP 본문 200건)을 해시로 재구성해 기존·후속의 644,377개 토큰 ID와 당시 서버가 보고한 토큰 수를 검산했다. [측정값·구간별 검산](../../benchmarks/evidence/20261124-agentic-serving/piece-cache-verified.json) · [원본과 빌드 자료](../../benchmarks/evidence/20261124-agentic-serving/piece-cache-raw.tar.gz)

이 변경은 현재 소스의 Qwen 토큰화 경로에 적용했다. Linux에서 실제 긴 이력 요청당 CPU 절감은 약 0.35ms였다. 26.8K JSON은 토크나이저 단독 시험이며 GPU의 문맥 수용이나 동일 입력의 생성 속도를 검증하지 않았다. 최종 완료가 수 초 지연되는 혼합 부하에는 GPU에서 재처리하는 입력을 줄이는 실험을 계속 우선한다. 서비스 배포와 A100 종단 지연 판정은 열려 있다.

### 첫 도구를 기다리며 최종 답변의 이력을 준비하는 경우

두 도구를 앱이 직접 결정하는 Coder-7B 카탈로그 연쇄에서, 첫 도구를 시작하는 시점에도 최종 답변의 긴 이력이 이미 있다. 기존 A100 두 장의 선택형 카탈로그 제출 88건을 재구성했다. 두 도구의 호출 인자와 결과를 대조하고, 각 시점에 이미 알려진 메시지와 완료된 호출·빈 결과만으로 준비 요청을 만들었다. 최종 요청 전체의 토큰 ID가 당시 모델 호출 경로와 일치하는지 확인한 뒤 16토큰 단위로 공통 prefix를 셌다.

긴 작업 66건 모두 첫 도구 시점에 **2,896토큰**, 두 번째 시점에 **2,944토큰**을 준비할 수 있었다. 첫 500ms 대기를 활용하면 두 번째 단계에서 추가로 알려지는 분량은 48토큰이다. 동시 도착 16건 중 긴 작업 12건의 첫 prefix를 전부 보존하려면, 같은 테넌트 안의 공통 블록을 완벽하게 공유해도 1,806블록이 필요하다. 당시 설정은 전체 KV 4,096블록, 재사용 캐시 1,536블록이었다. 다른 작업이 전혀 없어도 전부 보존 가능한 긴 prefix는 최대 10개다. 단일 16토큰 블록의 모델 KV 데이터는 BF16 기준 896KiB다. 이 계산에는 실행기 오버헤드가 들어가지 않는다. [입력별 공통 토큰·용량 검산](../../benchmarks/evidence/20261124-agentic-serving/first-tool-capacity-verified.json)

**실제 CPU 체크포인트에서 KV를 이어 쓴 결과.** 첫 번째 도구 콜백에서 별도 스레드가 준비를 시작하고 실제 최종 요청이 오면 새 청크를 중단했다. 체크포인트의 첫 최종 forward에 들어간 토큰 수, 이전에 저장한 생성 ID 전체, HTTP로 받은 마지막 콘텐츠와 종료 토큰을 대조했다. 긴 입력 3,072토큰에서 각각 0.5초인 도구 두 개는 CPU의 첫 청크보다 빨리 끝났다. 계산한 16토큰을 이어 사용했지만, 최종 요청을 보낼 때 완성된 블록은 0개였고 진행 중인 청크는 그 뒤 1.83초에 끝났다. 최종 토큰화 뒤에도 0.63초를 기다렸다. 빈 이력 308토큰은 준비를 건너뛰었다. 최초 실행은 참조 라이브러리 캐시 길이 조정 호출에서 오류가 발생해 교정 후 두 입력 전체를 다시 실행했다. [실행 원본](../../benchmarks/evidence/20261124-agentic-serving/named-first-kv-raw.tar.gz) · [입력·생성·대기 검산](../../benchmarks/evidence/20261124-agentic-serving/named-first-kv-verified.json)

같은 긴 입력에서 앱이 총 5초의 대기를 사전에 알려주고 두 도구가 각각 실제 2.5초를 기다린 후속 사례도 측정했다. 청크당 2.5초의 예산을 적용해 남은 시간 안에 끝낼 수 있는 준비만 시작했다. 최종 요청 전 32토큰이 준비됐고, 첫 최종 forward는 나머지 3,040토큰만 계산했다. 원래 생성한 **88개 출력 토큰 ID가 모두 일치**했고 정상 종료했다. 두 실행 모두 원래의 출처 누락도 그대로 보였다. 이는 CPU FP32 참조 경로에서의 실제 KV 재사용이다. GPU의 청크 실행시간이나 운영 응답 시간은 따로 측정해야 한다. ### 토큰 예산을 지켜 일반 HTTP 요청으로 준비한 결과

스케줄러 재생에서 시험한 작업별 제한을 공개 재생 클라이언트에 연결했다. 먼저 서빙 체크포인트의 Riley 템플릿과 토크나이저로, 도구 시작 시점에 이미 있는 정보만 담은 준비 요청을 렌더링한다. 전체가 허용량 안이면 그대로 쓴다. 초과하면 앞선 시스템·개발자 메시지를 유지하고 첫 사용자 문자열의 앞부분을 512문자 단위로 탐색한다. 완성된 후보를 다시 인코딩해 예산과 알려진 원문의 일치 블록을 확인한다. 맞는 블록이 없거나 준비 중 최종 요청이 도착하면 준비를 생략한다. 도구가 반환한 실제 데이터와 최종 요청은 그대로 보낸다. 이전 A100 카탈로그 88건에서 실제 클라이언트가 고른 요청이 스케줄러 재생의 후보와 전부 일치했다. [선택 검산](../../benchmarks/evidence/20261124-agentic-serving/bounded-http-verified.json)

아래는 Linux CPU의 실제 Qwen2.5-Coder-7B-Instruct에 별도 HTTP 요청 두 개를 보내 확인한 결과다. 첫 요청은 모델 forward 1회로 KV를 만들고 출력 토큰 1개 사용을 보고했다. 두 번째 요청은 전체 최종 입력을 독립적으로 렌더링하고 일치하는 16토큰 블록만 이어 썼다. 두 도구의 이름·인자·호출 순서, 서버에서 사용한 최종 입력, 생성 ID 전체, 스트리밍 자연 종료를 준비 없는 이전 실행과 대조했다.

| 이력·시드 | 준비 예산 / 실제 입력 | 실제 재사용 | 최종 전체 입력 → 첫 forward에 남은 토큰 | 대조군과 일치한 생성 토큰 |
|---|---:|---:|---:|---:|
| 긴 이력 17101 | 256 / 164 | 160 | 3,072 → 2,912 | 88/88 |
| 빈 이력 17104 | 256 / 149 | 128 | 308 → 180 | 109/109 |

두 답변은 전후값과 차이를 맞히고 기존의 출처 누락도 유지했다. CPU 실험의 도구 대기는 긴 이력에서 15초씩, 빈 이력에서 6초씩으로 정했다. 준비 비용과 도구 대기의 겹침을 확인한 사례로, GPU 지연이나 고객 대기 시간 단축량을 추정할 수는 없다. [긴 이력 원본](../../benchmarks/evidence/20261124-agentic-serving/bounded-http-raw.tar.gz) · [빈 이력 검산](../../benchmarks/evidence/20261124-agentic-serving/bounded-http-short-verified.json)

Qwen과 Llama 3의 실제 템플릿에서도 한글·분해형 문자·이모지가 섞인 입력을 확인했다. 예산 초과, 유효 블록 부족, 준비 중 취소 시 최종 원문을 바꾸지 않았다. 같은 프로파일러에서 잘못된 요청 하나를 거절한 뒤 다음 정상 요청을 처리했다. [모델별 확인 결과](../../benchmarks/evidence/20261124-agentic-serving/bounded-planner-edges.json)
