# 04. 복제본 라우팅과 고객별 격리

[전체 이정표](README.md) · 선행 [단일 GPU 검증](03-mixed-scheduling.md) · 다음 [다중 노드와 운영](05-production-qualification.md)

**시작 조건.** 한 GPU에 맞는 동일 모델과 고정된 Riley 구성 두 개를 각각 별도 GPU·프로세스에 올린다. 기존 A100 두 장의 텐서 병렬 실측은 모델 하나를 나눠 실행한 기록이다. 이번에는 각 프로세스가 전체 모델과 독립 KV를 소유한다. [기존 두 GPU 측정](../serving-validation.md#two-gpus)

## 다음 턴을 보낼 서버 선택

같은 도구 결과를 세 방식으로 라우팅한다. 첫째는 순차 분배(round-robin), 둘째는 같은 세션을 같은 서버로 보내는 방식, 셋째는 **예상 대기 + 미재사용 입력의 prefill 시간**이 작은 서버를 고르는 방식이다. 셋째에서는 이미 생성 중인 최종 답변의 간격 목표를 위반할 것으로 예상되는 선택에 비용을 추가한다. 라우터 시간, 잘못 예측한 캐시 적중, 후보 선택 시점과 실제 입장 시점의 부하 차이까지 기록한다.

1. 두 서버를 같은 상태로 준비한 뒤 한쪽에 특정 세션의 prefix를 만들고, 그 서버의 대기열과 반대편의 여유를 독립적으로 바꾼다. 따뜻하지만 바쁜 서버와 비었지만 다시 계산해야 하는 서버의 지연이 역전되는 지점을 찾는다.
2. 여러 세션이 다른 시점에 도구 대기에서 돌아오도록 하고, 도착률을 올리며 처리량·거절률·p95·GPU 시간당 목표 충족 완료 수를 측정한다. 라우팅 정책마다 동일한 두 GPU와 총 KV 예산을 사용한다.
3. 테넌트는 인증된 호출 주체에서 결정한다. 현재 캐시에 테넌트 구분이 없으므로 초기 실험은 신뢰 경계별 풀 분리로 시작한다. 공유 풀 후보에서는 인증된 테넌트·모델 리비전·실제 토큰 prefix로 재사용 범위를 결정한다. 다른 테넌트가 같은 입력을 보냈을 때 교차 재사용 0건, 같은 테넌트의 후속 턴에서는 재사용 가능함을 함께 검사한다. [현재 캐시의 범위](../prefix-cache.md#limits)
4. 한 테넌트의 장문 폭주 중 다른 테넌트의 최종 답변을 스트리밍한다. 테넌트별 대기 한도와 입장 정책을 적용해 거절, 대기, 완료, 취소 후 KV 회수를 대조한다. 라우터는 기존 JSON 지표를 활용하고 예상 대기와 prefix 위치에 필요한 추가 정보만 노출한다. [현재 서버 지표](../api.md)

**산출물과 통과.** 세 정책의 부하별 용량 곡선과 선택 로그, 테넌트별 지연 분포·실패 분모·격리 결과를 남긴다. 비용 기반 정책은 단순한 두 대조군에 비해 목표 충족 작업 수나 종단 지연에서 반복 가능한 이득이 있고, 다른 사용자의 최종 답변과 격리 기준도 지킬 때 채택한다. 단순한 정책이 더 좋으면 그대로 05에 넘긴다. 두 복제본의 수치는 해당 장비와 부하의 검증 범위로 기록한다.

## 두 A100에서 실행하는 실험

03의 후보 승격 전에도 비교 가능한 256행 기준 구성을 고정했다. 같은 호스트에서 각 GPU가 전체 7B 모델, 4,096개 KV 블록, 독립된 인증 키를 갖는다. 실험 클라이언트가 요청마다 라우팅하고, 서버별 미완료 요청·예상 캐시 적중·결정 소요시간과 실제 토큰 적중을 기록한다. 동시 도착 세션을 1·2·4·8개로 늘리고 같은 입력으로 정책 순서를 뒤집는다. 테넌트 검사는 독립 키를 가진 전용 프로세스에서 실행한다. 인증 교차 요청, 첫 요청과 재요청의 캐시 적중, 다른 테넌트가 읽는 동안의 장문 폭주와 클라이언트 취소를 검사한다. [실험 조건](../../benchmarks/evidence/20261124-agentic-serving/replica-registration.json) · [라우팅·부하 드라이버](../../benchmarks/live/replica_workflow.py)

첫 순차 분배 실행은 15개 워크플로 중 13개가 정확성과 등록 지연 목표를 함께 충족했다. 4개·8개 동시 도착 조건에서 각각 한 답변이 값·인용·종료 검사를 실패했다. 두 전용 프로세스 모두 같은 입력의 첫 요청 적중은 0이고 재요청은 1,424토큰이었다. 다른 프로세스의 키로 보낸 요청은 HTTP 401을 받았다. 보호 대상의 최종 답변이 실제 스트리밍 중일 때 반대쪽에 17개 요청을 제출했고, 한 연결을 중간에 닫았다. 보호 대상 답변은 정확성 검사를 통과했고 가시 콘텐츠 간격 p95는 11.93ms였다. 취소·연결 해제 계수가 각 1 증가했고 종료 후 활성·대기 요청과 활성 KV 블록은 0이었다. 이 파동에서 HTTP 429는 관측되지 않았다. ## 여섯 번의 교차 실행 결과

같은 15개 작업을 순차 분배→세션 고정→비용 기반→비용 기반→세션 고정→순차 분배 순서로 재생했다. 90개 제출 중 78개가 도구·최종 답변·지연 목표를 함께 통과했다. 모든 실행에서 시드 783과 797의 최종 답변이 수치를 맞히고도 요청한 두 보고서 이름을 모두 빠뜨렸다. 아래 p95는 답변 검사를 통과한 작업 기준이며, 4개 동시 제출에서는 3개, 8개에서는 7개가 그 분모다.

| 라우팅 | 동시 4개 최종 완료 p95, 두 기동 | 동시 8개 최종 완료 p95, 두 기동 | 전체 할당 GPU·시간당 SLO 완료 수 |
|---|---:|---:|---:|
| 순차 분배 | 3,899 / 3,892ms | 4,140 / 4,141ms | 182.7 / 179.6 |
| 세션 고정 | 3,892 / 3,877ms | 4,134 / 4,127ms | 185.6 / 168.9 |
| 예상 대기·미적중 비용 | 3,818 / 3,699ms | 4,238 / 4,053ms | 182.0 / 182.9 |

전체 할당 시간에는 기동·유휴 시간과 같은 예약에서 수행한 격리·취소 시험도 들어간다. 비용 기반 후보는 4개 동시 제출에서 완료가 빨랐고, 8개에서는 순차 분배 대비 한 번 느리고 한 번 빨랐다. 목표를 충족한 작업 수는 모든 기동에서 13개였다. 이번 부하에서는 비용 기반 정책을 승격할 근거가 부족해 05의 합성 운영 시험은 순차 분배를 기준으로 한다.

여섯 기동 모두 전용 키 교차 사용은 401, 독립 풀 간 초기 적중은 0, 같은 풀 재요청 적중은 1,424토큰이었다. 17개 요청을 반대편에 제출하는 동안 정상 사용자의 최종 답변이 완료됐고, 매번 실제 연결 해제와 취소가 1회씩 증가했으며 활성 KV가 회수됐다. 이 부하에서는 모든 폭주 요청이 HTTP 200으로 입장했으므로 과부하 거절 한계는 추가 측정 대상이다. 별도 실험에서 한쪽에만 같은 프롬프트를 워밍하고 활성 스트림이 0·4·8개일 때 양쪽으로 동일 입력을 동시에 제출한다. 또한 16·64·160개 동기화된 제출에서 거절과 복구 시점을 측정해 초기 시험에서 관측하지 못한 포화 한계를 확인한다. [경계 측정 등록](../../benchmarks/evidence/20261124-agentic-serving/crossover-registration.json)

### 같은 prefix를 가진 복제본을 기다릴 조건

같은 3,190토큰 입력을 두 A100으로 동시에 보냈다. 따뜻한 복제본은 항상 3,184토큰을 재사용했고, 반대편 적중은 0~16토큰이었다. 두 번 반복한 결과는 다음과 같다.

| 따뜻한 복제본에서 실제로 스트리밍 중인 요청 수 | 따뜻한 복제본 첫 콘텐츠 | 유휴 복제본 첫 콘텐츠 |
|---:|---:|---:|
| 0 | 16~18ms | 244~252ms |
| 4 | 23~24ms | 245~247ms |
| 8 (활성 한도) | 2,285~2,286ms | 245ms |

모든 기존 스트림이 새 요청 제출 시각에 진행 중이었다. 8개일 때는 유휴 GPU에서 처음부터 계산해도 약 2.04초 빨랐다. 이를 이용한 선택적 `capacity` 정책은 클라이언트가 추적한 진행 요청 수가 해당 복제본의 설정 한도에 도달하면, 여유가 있는 복제본들에서 예상 비용을 비교한다. 여러 라우터가 한 풀을 공유할 때는 전역 입장 상태가 더 필요하다. 독립 반복의 종단 결과를 보기 전까지 운영 기준은 순차 분배다. [교차 원본과 과부하 기록](../../benchmarks/evidence/20261124-agentic-serving/crossover-raw.tar.gz) · [결과](../../benchmarks/evidence/20261124-agentic-serving/crossover-verified.json)

한 테넌트에 동시에 16·64·160개를 보냈을 때 각 파동에서 정상 종료는 16·64·136개였고, 160개 파동의 나머지 24개는 HTTP 429였다. 세 번 모두 별도 테넌트의 진행 중 답변과 폭주 이후 시험 요청은 정상 완료됐다. 같은 시험에서 추가한 배포 인벤토리 재생 7개는 원격에 남아 있던 구버전 HTTP 클라이언트가 URL을 중복 조립해 전송하지 못했다. 최신 클라이언트 전체를 함께 배포한 재시험을 별도로 기록한다.

### 활성 슬롯을 반영한 라우팅 재시험

최신 HTTP 클라이언트를 포함해 서로 다른 두 실제 엔드포인트로 7개 워크플로를 보냈다. 도구와 최종 답변까지 21개 요청이 모두 HTTP 200이었고 6개 작업이 출력·지연 기준을 충족했다. 한 작업은 앞서 관측한 시드 783의 답변 검사를 통과하지 못했다. 단일 호스트이며 운영 인벤토리의 URL 처리와 분배를 실제로 확인한 범위다.

새로운 5,745토큰 문맥으로 순서를 바꿔 시험했다. 기존 비용 계산은 활성 스트림 8개에서 여전히 따뜻한 복제본을 골라 첫 콘텐츠까지 2,285·2,286ms가 걸렸다. `capacity`는 여유가 있는 복제본을 골라 458·464ms에 첫 콘텐츠를 전달했다. 4개와 7개일 때는 두 정책 모두 따뜻한 복제본에서 약 23ms였다. 제출 당시 관측한 동시 스트림 수와 실제로 겹친 스트림 수가 8개 시험에서 모두 일치했다. 이 결과는 한 요청의 배치 선택을 검증한다. 같은 효과가 여러 라우터와 혼합 부하의 전체 완료 용량에서 유지되는지는 별도 판정이 필요하다. ### Coder-14B에서 짧은 답변 전용 복제본의 비용

두 A100에 같은 Coder-14B BF16 서버를 한 개씩 두고, 긴 RAG 64건의 실제 도착 시각표에 4초 뒤부터 짧은 C32 192건의 도착 시각표를 겹쳤다. 같은 입력, GPU 두 장, KV 용량과 배치 예산을 유지했다. 두 기동 내에서 6개 측정 구간을 진행하고 후반에 GPU 역할을 바꿨다. 1,536개 응답 모두 기존 Riley 원본의 토큰 길이·종료 사유·본문 해시와 일치했고, 요청 유형별 도착 오차 p95는 최대 3.29ms였다.

| 배치 방식 | 짧은 답변 완료 p95 | 긴 RAG 첫 콘텐츠 p95 | 긴 RAG의 요청별 스트림 간격 p95의 p95 |
|---|---:|---:|---:|
| 두 GPU에 순차 분배 | 2.51~2.52초 | 1.00초 | 43.2~43.3ms |
| 짧은 요청에 한 GPU 전담 | 1.90~1.92초 | 2.54~2.64초 | 83.4~83.5ms |
| 짧은 요청이 몰리는 동안만 한 GPU 전담 | 1.93~2.41초 | 2.47~2.49초 | 81.6~82.9ms |

두 후보 모두 긴 RAG의 첫 콘텐츠와 스트리밍 보호 기준에 실패했다. 순차 분배의 두 측정에서는 각각 짧은 요청 192개 중 16개 도착 시점에 상대 복제본에 첫 콘텐츠를 기다리는 긴 입력이 없었다. 그 16개 모두 상대 복제본에서 이미 진행 중인 요청 수가 더 많았다. 이 부하에서는 복제본을 통째로 나누면 다른 사용자의 대기를 옮겨 놓는 비용이 크다. 캐시가 있고 한 복제본의 슬롯이 모두 찬 경우에 확인한 7B 라우팅 이득과 구분한다. ### 이력이 길어질 때 복제본 선택의 CPU 비용

재생 클라이언트는 이전 요청과 일치하는 메시지 이력을 찾아 어느 복제본에 KV가 남아 있을지 추정한다. 기존 구현은 메시지 하나를 추가할 때마다 앞의 모든 메시지와 도구 정의를 다시 JSON으로 직렬화하고 해시했다. 같은 SHA-256 상태에 각 메시지를 한 번씩 추가하고, 이력 경계에서 상태를 복사해 해당 prefix의 키를 완성하도록 바꿨다. 순차 분배, 세션 고정, 비용 기반, 활성 슬롯 기반 정책이 같은 키를 사용한다. [변경한 라우터](../../benchmarks/live/replica_workflow.py)

두 A100에서 실행했던 90개 작업의 HTTP 요청 270건을 원래 도구 응답 ID까지 복원해 HTTP 클라이언트가 전송 직전에 계산한 정규화 JSON 지문과 대조했다. 메시지 경계 1,350곳의 키가 모두 일치했다. 같은 완료 순서와 기록된 활성 요청 수를 적용한 네 정책의 로컬 재생에서 1,080개 결정의 목적지·재사용 추정·점수가 같았다. 실제 기록은 한 메시지 안에 이력 100줄이 들어 있어 요청당 메시지는 3·5·7개였다. 별도로 긴 대화에서 메시지 수 자체가 증가하는 경우도 측정했다. ### 서로 다른 클라이언트가 한 복제본을 채울 때

이전 슬롯 실험에서는 라우터가 진행 중인 요청을 모두 알고 있었다. 이번에는 별도 프로세스가 한 GPU에 192토큰 스트림을 4·7·8개 열었다. 라우터는 독립된 입장 상태를 가지고 5,745토큰 입력을 한 토큰까지 이어서 생성할 위치를 골랐다. 12개 배치의 전송 시점 모두 목표한 상대 스트림이 실제 콘텐츠를 보내고 있었다. GPU 역할과 정책 순서를 바꿔 반복했다. [사전 등록](../../benchmarks/evidence/20261124-agentic-serving/cross-router-registration.json) · [원본 기록](../../benchmarks/evidence/20261124-agentic-serving/cross-router-raw.tar.gz)

재생 클라이언트에 선택형 `--policy observed-capacity`를 추가했다. 각 복제본에 백그라운드로 `/readyz`를 조회해 활성·대기 요청 수와 수신 가능 상태를 읽고 표본 나이를 기록한다. GPU 슬롯 수는 인벤토리의 `max_active_sequences`에서 읽는다. 같은 요청을 두 번 세지 않도록 서버 활성 수와 로컬 요청 수 중 큰 값을 사용한다. 500ms 이내의 표본이 없으면 해당 복제본의 로컬 정보로 돌아간다. 서버가 수신 불가를 알린 복제본은 새 표본이 유효한 동안 제외한다. 실제 입장 시점의 전역 슬롯은 보장되지 않는다. [부하 조회](../../benchmarks/live/replica_load.py) · [배치 결정](../../benchmarks/live/replica_workflow.py)

**기존 서버에서 드러난 한계.** 4·7개의 스트림에서는 외부 활성 수를 읽었지만, 8개가 차자 서버가 8개 HTTP 워커를 스트리밍에 모두 쓰고 있었다. GPU 6·7 모두 결정 시점의 마지막 표본은 248·279ms 전에 읽은 활성 0개였다. 로컬 정책과 조회 정책 모두 캐시가 있는 GPU로 보냈고 첫 콘텐츠에 2.10~2.11초가 걸렸다. 보호 스트림의 콘텐츠 간격은 6개 비교 모두 5% 기준 안이었다. GPU 7의 7스트림 비교에서 후속 요청 첫 콘텐츠는 19.4→20.6ms로 5% 기준을 넘었다. 정상 인벤토리 진입점으로 실행한 별도 에이전트 작업은 7건 중 6건이 정답과 지연 기준을 충족했다. [원본 재집계](../../benchmarks/evidence/20261124-agentic-serving/cross-router-verified.json)

**HTTP 워커 하나를 추가한 교차 시험.** GPU의 활성 슬롯 8개·대기 한도 2개와 동일 입력을 유지하고, 실험 바이너리에서 일반 HTTP 워커만 8→9개로 늘렸다. 양쪽 라우팅 정책 모두 이 바이너리를 사용했다. 캐시가 있는 GPU가 포화되자 조회 정책은 35·40ms 전의 활성 8개를 보고 유휴 GPU를 선택했다. 같은 5,745토큰 후속 요청의 첫 콘텐츠는 GPU 역할을 바꾼 두 비교에서 각각 2,096→463ms, 2,095→463ms였다. 로컬 정책은 5,744토큰을 재사용했다. 다른 GPU에서는 한 실행이 캐시 수치를 생략했고 다른 실행은 16토큰을 재사용했다.

4·7개 외부 스트림에서는 두 정책이 모두 캐시가 있는 GPU에 머물렀다. 이 네 쌍의 첫 콘텐츠 회귀는 최대 3.1%였다. 6개 비교의 상대 스트림 콘텐츠 간격 p95도 모두 5% 보호 한도 안이었다. 이 결과는 이미 알고 있는 같은 입력에 한 토큰을 생성하는 배치 결정의 효과다. 추가 워커는 모든 HTTP 요청을 처리하므로 더 큰 생성 폭주에서는 상태 조회가 다시 기다릴 수 있다. 실험 패치를 공통 서버 기본값으로 승격하려면 그 조건에서의 입장·거절과 장시간 부하를 추가 검증해야 한다. ## 일반 혼합 부하에서 보류가 실제로 필요한 빈도

보류 후보가 두 대조군을 각각 여섯 입력군에서 만난 12개 비교 중 7개에서 첫 콘텐츠·마지막 콘텐츠·콘텐츠 간격 p95 중 하나가 5% 한도를 넘었다. 보류를 발동한 요청이 없어 이 차이를 보류 동작의 비용으로 해석할 수 없다. 각 입력군은 여덟 작업이다. 기동부터 반환까지 포함한 전체 할당 GPU 시간 기준은 세 기동에서 시간당 592~600개였다. 일반 부하에서는 기본 정책을 유지하고, 보류 효과는 앞에서 재현한 과부하 조건에 한정한다. ### Coder-7B에서 같은 16개 도착을 한 복제본과 두 복제본으로 처리한 비용

### 첫 요청의 이력 길이로 복제본 편중을 줄인 재시험

두 A100의 복제본을 새로 기동해 이력 길이 기반 후보를 시험하고, 두 복제본을 다시 기동해 순차 배분으로 반복했다. 각 조건에 108개 워크플로를 제출했다. 후보는 첫 모델 요청에 이미 들어 있는 메시지 목록의 직렬화 크기가 4,096바이트 이상인지 판단한다. 해당 크기군을 적게 받은 복제본을 택하고 동률이면 전체 배정 수가 적은 곳을 고른다. 후속 턴은 처음 택한 복제본으로 보낸다. 어느 복제본에서 도구 결과가 먼저 돌아올지 또는 최종 답변이 얼마나 길지는 선택 시점에 주어지지 않는다. ### 복제본별 준비 요청 예산과 최종 요청 배치

`agent_fleet_replay.py`에서 복제본별 준비 예산을 설정할 수 있다. 여러 복제본을 쓰는 경우 준비와 최종 요청을 같은 세션 복제본으로 보내고, 그 복제본에 지정한 인증을 두 연결 모두에 적용한다. 각 워크플로는 준비를 시작할 때 블록을 예약하고 최종 요청과 준비 요청이 모두 정리되면 반환한다. 여러 워크플로가 동시에 대기해도 각 복제본의 예약 총량은 설정값 안에 머문다. 예산이 소진되면 도구 실행과 최종 요청은 계속한다. 이는 재생 프로세스가 맡은 미완료 작업의 예약량이다. 서로 다른 라우터 프로세스의 예약과 GPU 캐시에 실제로 남아 있는 블록은 별도로 관측해야 한다.

두 개의 인증된 로컬 HTTP 리스너와 실제 Coder 토크나이저로 4·8·16·16개 작업을 재생했다. 복제본당 80블록, 작업당 40블록(640토큰)을 허용했다. 앱이 직접 도구를 실행한 대조군과 후보 모두 **44/44개 최종 요청을 완료했고 모든 최종 입력 ID가 일치**했다. 후보는 각 복제본에 12개씩 총 24개 준비 요청을 보냈다. 준비 입력은 600~603토큰이었고, 나머지 20개는 예산이 소진돼 준비를 건너뛰었다. 두 복제본 모두 예약 최고치는 80블록이었고 종료 후 80블록 전부 반환됐다. 별도로 도구 결정을 모델에 맡긴 두 워크플로에서도 3회의 모델 호출과 준비 1회를 각각 처리했다. 이 복제본 시험의 답변은 HTTP fixture가 생성했다. [수신 요청·예산 기록](../../benchmarks/evidence/20261124-agentic-serving/bounded-fleet-raw.tar.gz) · [집계](../../benchmarks/evidence/20261124-agentic-serving/bounded-fleet-verified.json)

한 리스너가 준비 입력 길이를 다르게 보고하고 다른 리스너가 같은 길이의 다른 토큰 ID를 보내는 시험도 실행했다. 각 복제본에서 불일치가 확인된 뒤 새 준비 예약을 중단했고, 4개 최종 답변은 모두 종료했다. 서버가 ID를 제공하지 않는 경우 비교 가능한 값은 입력 길이다. 정확한 예산에는 서비스와 같은 템플릿·토크나이저가 필요하다.
