# Riley 목표 (초안, 2026-11-04)

## 1. 목표

> **Riley는 지원하는 모든 모델과 GPU에서, 실제 서비스 워크로드 전반에 걸쳐 vLLM과 같거나 더 빠르다. 동시에 배치 불변성과 출력 품질은 vLLM보다 낮아지지 않는다.**

지금까지는 주로 짧은 프롬프트(closed/open-loop)로 모델을 검증했습니다. 앞으로는 이 목표를 **긴 프롬프트·부하·API 기능·다중 GPU**까지 넓히고, 모든 qualified 모델에 같은 기준을 적용합니다.

## 2. 범위

| 구분 | 포함 | 제외 (별도 목표로 다룸) |
|---|---|---|
| 모델 | qualified 24개 단일 GPU 모델, Qwen2.5-32B(TP=2) | MoE, 비전 입력, 양자화, speculative decoding |
| GPU | A100-SXM4-40GB (주 대상), RTX 4090 (보조) | 4·8 GPU, 다중 호스트 (장비 확보 전까지) |
| 워크로드 | 짧은 프롬프트, RAG(2K~6K), 긴 출력(reasoning), 부하(open/burst), prefix 공유 | 실제 프로덕션 트레이스 (확보 전까지) |
| API | completions, chat, structured output, tools, logprobs, LoRA 병합 | Hermes·Llama JSON 이외의 tool 형식 |

## 3. 달성 기준

비율은 모두 **Riley / vLLM**입니다. TTFT·TPOT은 낮을수록, 처리량은 높을수록 좋습니다. 같은 빌드를 GPU만 바꿔 돌려도 1~3% 흔들리므로, **±3%는 동률(tie)**로 봅니다.

### 3.1 성능 (A100, 24개 모델 전부에 적용)

### 3.2 정확성 (가드레일: 하나라도 어기면 그 변경은 기각)

| 항목 | 기준 |
|---|---|
| 배치 불변성 | 같은 요청은 배치 구성과 무관하게 같은 토큰 (장문 검사 54/54, 모든 모델의 불변성 검사 통과) |
| 출력 바이트 | 성능 변경은 이전 빌드와 바이트가 같아야 함. 수치가 바뀌는 변경은 **사전 승인 + 모델 재검증**을 거침 |
| HF 일치 | 모델별로 vLLM의 HF BF16 일치 범위 이상. 7B 긴 프롬프트 12/18처럼 vLLM(16/18)보다 낮은 항목은 원인을 규명하는 대상으로 등록 |
| 과제 품질 | GSM8K가 vLLM 대비 −1.2점 이내 (토크나이저 결함 모델은 예외로 명시) |
| 회귀 금지 | 짧은 프롬프트 셀은 2% 이상, 디코드 TPOT은 1% 이상 나빠지지 않음 |

### 3.3 운영 품질

| 항목 | 기준 |
|---|---|
| 안정성 | 30분 혼합 soak: 오류 0, 메모리 증가 0, 지연 드리프트 ≤ 5% |
| API | api_check 전체 통과, OpenAI 호환 필드 문서화 |
| 기동 | 32B 포함 기동 시간 기록, 실패 시 원인을 명확히 출력 |

2026-11-05 갱신: 0단계(24개 모델 기준선)를 마쳤다(`benchmarks/evidence/20261104-goal/base0`). burst 수치는 `--batch-token-budget 1024` 등 opt-in 설정의 값이다(serving-validation의 Prompt steps of 1,024 rows). 3.2 가드레일: 출력 바이트는 모든 변경에서 이전 빌드와 같았고, GSM8K는 3개 모델에서 vLLM 대비 −0.23~+0.53점, 장문 검사 54/54. 3.3: 30분 혼합 soak 오류 0·RSS 증가 0.7 MiB, api_check 40/40.

2026-11-05 저녁 갱신: KV chunk 512를 기본값으로 채택(사용자 승인)하고 24개 모델 재검증(불변성 54/54, HF 첫 토큰 17–18/18, GSM8K 3개 모델 모두 vLLM 이상). 토크나이저를 토큰 ID 병합으로 바꿈(같은 ID, 출력 바이트 동일): 작은 Qwen 모델의 긴 프롬프트 격차와 shared-c32 격차의 주원인이었다. 14B reason-c32 격차는 측정 도구가 Riley에 vLLM보다 적은 KV를 준 탓이었다(1,859 → 2,576 블록, 메모리 36.9 vs 37.1 GB). api_check 40/40 (lp13, 7B·Qwen3-4B).

2026-11-08 갱신: KV head 2개 이하 모델(Qwen2.5-0.5B/1.5B/3B, Coder-1.5B/3B, R1-Distill-Qwen-1.5B)에서 생성 토큰만 256으로 나누고 프롬프트 토큰은 512를 유지(사용자 승인, lp16). 전부 256(lp15)은 rag-c1 +4%, rag6k +6% 비용이 있어 §6에 따라 기본값에서 제외했다. 재검증: 불변성 54/54(8·32 클라이언트), HF 첫 토큰 17–18/18, GSM8K vLLM 대비 −1.13~+0.45점. R1-Distill-Qwen-1.5B의 GSM8K 격차(−5점)는 vLLM 환경의 Transformers가 BOS를 넣지 않은 탓이었다(BOS를 넣으면 vLLM 62.40, Riley 62.85). burst 설정의 rag 셀은 lp13과 같거나 나음(rag-c1 0.87–1.04).

## 4. 측정 방법 (고정)

1. **장비:** A100 GPU 6·7. vLLM이 GPU 4·5에서는 느린 문제가 있어 비교 수치는 6·7에서만 씁니다. 다른 GPU는 Riley 단독 측정에만 씁니다.
2. **순서:** Riley·vLLM을 순서를 바꿔 각 2회씩 돌리고 평균합니다. 셀마다 워밍업 32건, 측정 192건입니다.
3. **셀 세트:** `closed-c8/c32`, `mid-r16`, `rag-c1/c8/r3`, `rag6k-c1`, `reason-c8/c32`와 TTFT 곡선(110~5,800토큰). 모델 qualify에는 기존 8셀 매트릭스를 그대로 씁니다.
4. **커널 주장:** 서버 nsys 프로파일(`--cuda-graph-trace=node`)로 확인합니다. 독립 벤치마크나 무작위 데이터로 잰 시간만으로는 채택하지 않습니다.
5. **근거:** `benchmarks/evidence/<날짜>-<주제>/`에 스크립트·원본 JSON·요약을 남기고, 결과는 `docs/`에 반영합니다.

## 6. 운영 규칙

- **채택:** 기준 지표가 나아지고, 가드레일을 모두 지키고, 근거가 남은 변경만 기본값으로 채택합니다. 이득이 있어도 다른 셀에 비용이 있으면 opt-in 옵션으로 둡니다.
- **종료:** 한 항목에서 가드레일을 지키는 레버를 연속 두 개 시도했는데 각각 2% 미만이면, 근거와 함께 "현재 구조의 한계"로 닫고 다음 항목으로 넘어갑니다.
- **기준 변경:** 목표 숫자는 측정 결과를 보고 임의로 낮추지 않습니다. 바꿀 때는 이유와 함께 이 문서에 기록합니다.
- **진행 보고:** 단계가 끝날 때마다 기준표의 "현재" 열을 갱신합니다.

2026-11-12 갱신: 남은 rag-c1 최종 기준(큰 모델 6개 1.07–1.11)은 사용자 결정으로 구조 한계로 닫았다. 0.1.0 후보(lp16, Qwen2.5-3B, 공유 GPU 7): api_check 40/40(기본·burst), 30분 혼합 soak 오류 0·overload 0·RSS 증가 0.7 MiB·종료 시 KV 블록 0(`stage16/`). 0.1.0 릴리스.
